# 风控系统后端详细设计

## 1. 目标

风控系统承接支付平台中的限额控制、危险支付拦截、黑名单、人工复核和交易监控，不再继续由 `payment-core` 的过渡控制页承载完整风控域。

## 2. V1 边界

V1 支持风险策略、限额规则、黑名单、拦截事件、人工复核单和监控规则的查询与治理，并提供人工复核的通过/拒绝动作。2026-08-04 新增 `payment-core -> risk-control-system` 的支付准入评估接口，已支持支付提交前按黑名单、限额规则和基础高危策略做 `PASS / REVIEW / INTERCEPT / REJECT` 决策；同日继续补齐 `ops-config-system -> risk-control-system` 的有效配置快照消费链路，支持按运营配置下发的大额支付复核阈值参与准入决策。真实实时决策、复杂评分模型、流式检测和规则引擎下发仍待后续补齐。

## 3. 分层

采用 `controller / service / serviceimpl / dao / mapper / mapper.xml / entity` 标准分层。`serviceimpl` 负责启停校验、人工复核动作、支付准入决策和总览口径；MyBatis 负责风控台账查询、决策命中留痕和状态回写。

## 4. 关键设计

- 风险策略与限额规则分离，前者负责拦截逻辑，后者负责金额/频次限制。
- 黑名单维护设备、手机号、商家等高风险主体；命中后可直接拦截或转人工。
- 支付准入评估优先复用已有人工复核结果：已通过则放行、已拒绝则直接拒绝、待审则继续保持待审。
- 人工复核动作仅允许处理 `PENDING` 状态复核单，已通过或已拒绝单据禁止重复审核，避免复核结论被后续误覆盖。
- 人工复核状态流采用 `PENDING -> APPROVED / REJECTED` 单向闭环，数据库更新同样附带 `status = 'PENDING'` 门禁，保证并发场景下只有首个审核动作生效。
- 支付准入评估当前执行顺序为：人工复核历史结果 -> 黑名单 -> 运营配置系统控制项 -> 本地限额规则 -> 基础高危策略。
- 拦截事件负责沉淀 `已拦截 / 转人工复核` 的事实留痕，便于支付核心、风控台和后续监控统一追踪。
- 人工复核单为支付核心、结算系统等上游提供统一人工审核闭环基础台账。
- 监控规则负责风险告警阈值和通知策略，为后续接消息告警做准备。

## 5. 运营配置联动设计

### 5.1 设计目标

1. 避免大额支付复核阈值继续写死在风控域本地代码或种子数据中。
2. 让运营配置域输出统一系统控制项，风控域只负责执行命中判断与审核闭环。
3. 为后续限额配置、严格模式、灰度发布和规则审批流联动打基础。

### 5.2 当前生效控制项

当前已接入的第一项跨系统控制为：

1. `CONTROL_BIG_AMOUNT_REVIEW`

命中逻辑：

1. `risk-control-system` 按 `payScene + sceneCode + terminal` 调用 `ops-config-system` 有效配置快照接口。
2. 若快照中存在已启用的 `CONTROL_BIG_AMOUNT_REVIEW` 控制项，则读取 `controlValue` 作为金额阈值。
3. 当交易金额超过阈值时，直接返回 `REVIEW`，并生成或复用人工复核单与拦截事件。

### 5.3 当前边界

1. 当前只消费控制项，不反向修改运营配置域。
2. 当前读取失败或未启用时，风控域退回到本地限额规则与策略判断，不阻塞支付主链路。
3. 当前还未接入配置版本治理、灰度发布时间窗和审批流留痕。

## 6. 后续生产化方向

补齐规则版本治理、审批流、实时决策接口、风控评分、跨系统事件订阅、告警派发、审计日志和 MySQL 实库迁移；在这些能力完成前，V1 仍属于风控治理联调基线。
