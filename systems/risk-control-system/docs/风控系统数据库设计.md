# 风控系统数据库设计

## 数据库

独立数据库：`housekeeping_risk_control`。

## 表设计

| 表名 | 说明 |
| --- | --- |
| `t_risk_policy` | 风险策略 |
| `t_risk_limit_rule` | 限额规则 |
| `t_risk_blocklist` | 黑名单 |
| `t_risk_intercept_event` | 风险拦截事件 |
| `t_risk_review_order` | 人工复核单 |
| `t_risk_monitor_rule` | 监控规则 |

所有表统一包含状态字段，复核单额外包含审核人；完整字段备注见 [schema.sql](/Users/abc123/workspace/home-service-payment-system/systems/risk-control-system/database/schema.sql)。

## 风控拒绝追踪边界

1. 人工复核拒绝继续由 `t_risk_review_order.review_no` 关联审核事实，不额外创建虚构风险事件。
2. 策略直接拒绝复用 `t_risk_intercept_event`，以 `decision_result=已拒绝` 保存事件，并按支付单号、命中策略和处置结果查询最新事件以实现重复评估复用。
3. 本轮未新增表、字段、索引或迁移；H2 测试不证明生产 MySQL 已执行或历史数据已完成追踪键补齐。

## 风控事件型终态引用边界

1. `t_risk_intercept_event` 同时承载直接拦截和策略直接拒绝事件，分别以 `decision_result=已拦截 / 已拒绝` 区分终态，并保留事件号和命中编码。
2. 对外返回事件型终态时必须同时提供 `eventNo + hitCode`；人工复核拒绝仍由 `t_risk_review_order.review_no` 关联，不为统一结构额外写事件。
3. 本轮只收紧服务契约与说明语义，未新增表、字段、索引或迁移；H2 测试不证明生产 MySQL 数据完整性、历史事件已补齐或跨系统运行态一致。

## 人工复核请求上下文绑定（2026-10-06）

新建复核单的 `request_fingerprint` 保存 `v2:` 加无填充 Base64URL SHA-256（共 46 字符，适配现有 `VARCHAR(64)`），覆盖业务单号、来源系统、来源应用、风控/支付场景、支付方式、渠道、商户、终端、IP、设备、付款手机号和数值归一化金额；字段按长度编码，避免拼接歧义。读取待审或已批准复核时必须与本次请求逐项对应的当前版本摘要一致，不能仅凭业务单号放行。人工拒绝仍维持拒绝终态，不因上下文变化转为通过。该摘要不对外返回，也不能替代审核人实际核实原请求材料。

新增列先经受控变更执行 `database/migrations/2026-10-06-add-risk-review-request-fingerprint.sql`，再部署依赖新列的服务；全新建库基线 `database/schema.sql` 与后端 H2 schema 同步。迁移保留历史行 `NULL`，**不得从当前请求或推测数据自动回填**：历史空摘要及部署前生成的 64 字符十六进制 v1 摘要均不能批准或放行；可人工拒绝待审单，继续支付需核实并发起新的支付单/复核。正式库须先按状态盘点空值、无版本旧摘要及异常格式的数量，备份与审批、评估锁/负载和回滚窗口，再执行 DDL 与发布。不自动把 v1 摘要转换为 v2，因为其未绑定来源应用。本轮仅在隔离 H2 上运行迁移回归，未连接目标 MySQL 8 或执行正式迁移。

## 风控追踪编号碰撞边界（2026-10-06）

新复核号和风险事件号分别采用 `REVIEW-` / `RISK-EVT-` + 毫秒时间戳 + 32 位 UUID 十六进制后缀，约 53/55 字符，适配原有 `VARCHAR(64)` 与唯一键；历史短编号原样保留，无 DDL 或回填。此变更避免仅毫秒时间戳在同毫秒并发创建不同业务单时复用编号，但不解决同业务单并发各建一张待审复核单的问题；后者仍需独立的原子业务键约束与并发验收。

## 同业务单复核唯一键（2026-10-06）

后续新增可空 `business_key BINARY(32)` 与唯一索引 `uk_risk_review_business_key`。新复核单按去首尾空白后的原业务单号 UTF-8 字节计算 SHA-256，不受 `business_no` 大小写不敏感排序规则影响；相同业务键只能插入一张新单。历史行仍为 `NULL`，可保留已有重复行，不自动猜测或回填；原复核号和摘要校验仍需执行。并发插入撞唯一键时，服务以业务键锁定读回胜出单，只在其仍为 `PENDING` 且原请求摘要完全一致时复用；上下文变化或状态终结均失败闭合。风险事件的同业务键/策略并发唯一性不在本次约束范围。

在依赖新列的应用上线前，须经审批、备份与维护窗口先执行 `database/migrations/2026-10-06-add-risk-review-business-key.sql`，并确保已完成前述 `request_fingerprint` 迁移；不可让旧版仍写空键的实例与新版长期混跑，否则唯一性只约束新版写入。正式库须盘点历史空键/重复业务单，核对索引容量、锁等待、回滚和目标 MySQL 8 下的二进制键/当前读行为，不得在未验收时自动补标或发布。本轮仅以 H2 模拟迁移与并发，没有连接目标 MySQL 8。

## 风险事件精确组合键（2026-10-06）

后续新事件保存可空 `event_key BINARY(32)`，以长度编码的原支付单号、策略编码、处置结果和有效来源系统（缺省 `payment-core`）及 `risk-event:v2` 域分隔计算 SHA-256；原始字节不裁剪，避免大小写不敏感列、尾部空白或跨来源系统合并不同事件。`uk_risk_event_key` 原子约束同组合事件，冲突方 `FOR UPDATE` 读回并逐字段精确比对，只有完全同身份才复用原事件号。历史事件的键维持 `NULL`，已有重复行不自动去重或回填；原查询也要求来源系统及处置结果精确一致。该键不替代复核单原业务键，也不表示不同处置结果必须共用一个事件。

在新代码上线前须受控执行 `database/migrations/2026-10-06-add-risk-event-key.sql`，并与前述复核摘要和业务键迁移协调顺序、备份、历史空键/重复组合盘点、索引容量和混跑窗口；旧实例仍写空键时无法承诺并发唯一性。本轮只在隔离 H2 验证迁移及并发，未连接目标 MySQL 8；其事务隔离、唯一键碰撞处理与执行计划仍须现场验收。
