# 运营配置系统后端详细设计

## 1. 目标

运营配置系统承接支付平台中偏运营、偏业务编排的配置域，不再继续把协议、路由、收银台模板和支付类型堆进 `payment-core`。

## 2. V1 边界

V1 支持协议模板、业务线、支付类型、收银台模板、渠道档案、路由规则和系统控制的查询与启停，并新增“有效配置快照”只读接口，供 `payment-core`、后续 `risk-control-system` 等下游系统消费。真实渠道证书、密钥、接入权限仍由 `gateway-access` 负责，限额、拦截、风险评分仍由 `risk-control-system` 负责。

## 3. 分层

采用 `controller / service / serviceimpl / dao / mapper / mapper.xml / entity` 标准分层。`serviceimpl` 负责启停编排和异常处理；MyBatis SQL 负责台账查询和状态回写。

## 4. 关键设计

- 协议模板和业务线作为上游配置入口，为收银台、支付路由和签约流程提供统一业务口径。
- 渠道档案只维护渠道台账、退款 SLA、风控标签和商户模板，不维护真实证书。
- 路由规则只沉淀运营编排，后续由支付核心或路由引擎读取并执行。
- 系统控制用于统一维护超时关闭、回调严格模式、大额复核等控制项。
- 启停操作统一使用 `ToggleRequestDTO`，方便后续接审批流和操作日志。

## 5. 有效配置快照设计

### 5.1 设计目标

1. 避免 `payment-core` 再把默认支付方式、渠道优先级和系统控制硬编码在本地。
2. 为不同业务线、支付类型、终端组合提供统一的配置下发视图。
3. 为后续灰度发布、配置版本、跨系统配置同步打基础。

### 5.2 查询维度

快照查询维度固定为：

1. `businessCode`
2. `payType`
3. `terminalType`

其中：

1. 收银台模板负责输出默认支付方式。
2. 路由规则负责输出优先/备选渠道档案和路由策略描述。
3. 系统控制负责输出当前已经启用的统一控制项列表。

### 5.3 服务编排

`OpsConfigServiceImpl.effectiveSnapshot(...)` 的编排顺序如下：

1. 校验业务线、支付类型、终端类型不能为空。
2. 校验 `businessCode` 对应业务线必须处于启用状态。
3. 校验 `payType` 对应支付类型必须处于启用状态。
4. 根据 `terminalType` 读取已启用收银台模板，缺失则直接失败。
5. 根据 `businessCode + payType` 读取已启用路由规则，缺失则直接失败。
6. 校验路由依赖的主渠道、备选渠道档案均处于启用状态。
7. 读取全局启用的系统控制项。
8. 组装 `OpsConfigEffectiveSnapshotDTO` 返回给下游。

### 5.4 快照门禁原则

1. 有效配置快照不是“尽量返回部分配置”，而是“只返回可执行配置”。
2. 若业务线、支付类型、收银台模板、路由规则或渠道档案存在关键缺失，则由 `ops-config-system` 直接返回业务异常，不把半成品配置下发给 `payment-core`、`risk-control-system` 等消费方。
3. 这样可以把配置错误前置收敛在配置域，而不是让下游系统在支付提交、风控准入或渠道出站时才被动暴露。

### 5.5 当前下游落地

截至 2026-08-04，已落地的直接消费方是 `payment-core`：

1. 当支付提交请求未显式传 `paymentMethod` 时，使用 `defaultPayMethod` 自动补齐。
2. 当支付提交请求未显式传 `channelCode` 时，使用 `primaryChannelProfileCode` 自动补齐渠道决策输入。
3. 支付核心后续可继续基于 `enabledSystemControls` 做超时关闭、大额复核和严格模式开关联动。

## 6. 后续生产化方向

补齐审批留痕、版本发布、配置快照、灰度发布时间窗、跨系统配置下发、限额配置联动和真实操作审计；在这些能力完成前，V1 仍属于运营配置联调基线。
