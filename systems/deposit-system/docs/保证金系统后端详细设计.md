# 保证金系统后端详细设计

## 1. 目标

保证金系统独立承载家政服务者、商家和平台主体的保证金账户与资金动作，不在订单系统或支付核心中直接维护余额。

## 2. V1 边界

支持开户、收取、冻结、解冻、扣罚、退还、抵扣欠款、账户查询和流水查询。真实收款、退款、账务记账和欠款来源由跨系统接口后续接入。

## 3. 分层

`controller` 负责参数绑定和响应包装；`service` 定义业务能力；`serviceimpl` 负责状态校验、事务和流水编排；`dao` 负责数据访问编排；`mapper`/`mapper.xml` 负责 MyBatis SQL；`entity` 对应数据库表。

## 4. 余额规则

- `balance` 是账户总余额。
- `frozen_amount` 是冻结余额。
- `available_amount = balance - frozen_amount`，不得小于 0。
- 收取、退还为余额增加动作；扣罚、欠款抵扣为余额减少动作。
- 冻结、解冻只改变冻结额，不改变总余额。
- 每次动作必须在同一事务内完成条件更新和流水写入。
- 更新 SQL 携带期望余额和期望冻结额，条件不满足时返回并发冲突。

## 5. 状态与幂等

V1 账户状态为 `OPEN`。流水号由数据库生成，查询接口只读。

1. 同一 `ownerId + ownerType` 只允许存在一个 V1 保证金账户，重复开户直接返回业务错误。
2. `referenceNo` 用于接入支付单、欠款单、处罚单等外部业务号。
3. 当前 V1 已增加轻量幂等保护：
   - 同一 `accountNo + flowType + referenceNo` 不允许重复执行
   - 若 `referenceNo` 为空，则视为后台人工动作，不做幂等保护
4. 正式跨系统接入时仍应进一步补：
   - 幂等表
   - outbox 事件
   - 重试补偿与审计台账

## 6. 失败处理

账户不存在、金额非正、可用余额不足、冻结余额不足、并发更新失败均返回业务错误。真实外部资金动作不得直接复用后台模拟接口，必须由收款/退款/账务系统提供带幂等号的内部接口。

## 7. 后续生产化

切换 MySQL 迁移、增加动作幂等表、操作审计、权限校验、账务事件 outbox、定时对账、冻结超时释放和跨系统补偿；在这些能力和真实依赖演练完成前，不作为冻结版发布依据。

## 8. V2 方向：总保证金账户

V2 不再沿用“一个主体一个账户”的简化模型，而是引入“总保证金账户 + 规则绑定”的合并结构。

这一调整来自 V1 交付后的结构性痛点：不同业务线、品类和规则需要归集到统一资金承载层，但又不能丢失原始规则、历史余额和追溯链路，因此必须单独演进为 V2。

1. 一个主体可存在一个总保证金账户，多个保证金规则共同绑定到该账户。
2. 账户负责资金承载，规则负责品类/业务线/应缴口径控制。
3. 存量旧品类账户需要支持结转到总账户，保留映射和流水追溯。
4. 工作台和详情页需要展示已关联规则数、规则明细、结转状态和总账户汇总。

## 9. V2 痛点收敛与执行路径

这一轮架构演进不是“为了升级而升级”，而是为了解决 V1 在真实家政业务里逐步暴露的结构性问题：

1. 同一阿姨或商家可能同时命中多个保证金规则，继续拆成多个独立账户会导致余额分散、补缴判断重复、运营解释成本高。
2. 欠款抵扣、扣罚和退还如果仍按旧品类账户各自处理，会出现“一个主体多处冻结、多处不足、总额充足但单账户不足”的资金体验断层。
3. 财务和运营在核对时更关心“主体维度总保证金敞口”，而不是先理解多个历史账户再手工汇总。
4. 后续若接入钱包、账务和风控，仍沿用多账户模型会把跨系统接口、对账口径和补偿链路一起复杂化。

因此 V2 的推荐推进顺序固定为：

1. 先交付只读预览：验证总账户汇总、规则归集和旧账户迁移候选口径是否正确。
2. 再交付规则绑定落库：把“规则归属”和“资金承载”正式解耦。
3. 再交付旧账户迁移执行：支持从多个历史保证金账户结转到一个总账户，并沉淀迁移映射、迁移流水和回滚保护。
4. 最后交付总账户下的实动作业：冻结、解冻、扣罚、退款、欠款抵扣逐步切到总账户口径，同时保留历史账户追溯链路。

这也意味着后续版本评审时，凡是涉及“多个保证金账户合并为一个主体总账户”的需求，都应优先纳入 V2，而不是继续在 V1 上做局部缝补。
