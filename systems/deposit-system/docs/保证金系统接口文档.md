# 保证金系统接口文档

基础地址：`/api/deposits`。响应统一为 `{code,message,data,requestId}`，`code=0` 表示成功。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/overview` | 查询保证金概览工作台 |
| GET | `/accounts` | 查询账户列表 |
| GET | `/accounts/export` | 导出账户列表快照 |
| GET | `/accounts/{accountNo}` | 查询账户详情工作台 |
| POST | `/accounts` | 开立保证金账户 |
| POST | `/accounts/{accountNo}/collect` | 收取保证金 |
| POST | `/accounts/{accountNo}/freeze` | 冻结保证金 |
| POST | `/accounts/{accountNo}/unfreeze` | 解冻保证金 |
| POST | `/accounts/{accountNo}/deduct` | 扣罚保证金 |
| POST | `/accounts/{accountNo}/refund` | 退还保证金 |
| POST | `/offset-debt` | 保证金抵扣欠款 |
| GET | `/accounts/{accountNo}/flows` | 查询账户流水 |
| GET | `/accounts/{accountNo}/flows/export` | 导出账户流水快照 |
| GET | `/v2/overview` | 查询 V2 演进概览 |
| GET | `/v2/total-accounts` | 查询总保证金账户列表预览 |
| GET | `/v2/total-accounts/{totalAccountNo}` | 查询总保证金账户详情预览 |
| GET | `/v2/migrations` | 查询旧账户结转预览 |

```json
  "ownerCount": 12,
  "totalBalance": 6800.00,
  "totalFrozenAmount": 1100.00,
  "totalAvailableAmount": 5700.00,
  "fullyPaidAccountCount": 8

```

## 账户列表查询参数

| 参数 | 说明 |
| --- | --- |
| `ownerType` | 主体类型，支持 `WORKER / MERCHANT / PLATFORM` |
| `status` | 账户状态，V1 默认 `OPEN` |
| `keyword` | 按账户号或主体编号的字面量子串筛选 |

账户列表、分页总数和导出共用相同查询口径；`%`、`_`、`!`、反斜杠与引号只表示原字符，服务端对绑定的 LIKE 参数编码并显式使用 `ESCAPE '!'`。主体类型与账户状态仍为精确条件；该读侧筛选不改变开户或资金动作的主体归属判断。

## 流水查询参数

| 参数 | 说明 |
| --- | --- |
| `flowType` | 按流水类型筛选 |
| `referenceNo` | 按业务关联号字面量子串筛选 |

账户流水列表、分页总数和导出共用字面量条件；`%`、`_`、`!`、反斜杠和引号仅表示原字符，不扩大匹配范围。服务端对绑定的 LIKE 模式编码并显式使用 `ESCAPE '!'`；账户号及流水类型仍为精确条件，写入时的关联号幂等判定继续使用原值而非转义模式。

金额必须大于 0；账户余额、冻结额和流水变化由服务端计算，客户端不能传入变更后余额。

补充约束：

1. 同一 `ownerId + ownerType` 重复开户会直接返回业务错误。
2. 当资金动作携带 `referenceNo` 时，同一账户下相同 `flowType + referenceNo` 只允许成功一次，重复提交会返回“该业务关联号已处理，请勿重复提交”。
3. 账户详情工作台会返回流水笔数、最近流水时间、是否已缴达标和待补缴金额，用于前端运营台直接展示。
4. 账户列表和账户流水都必须支持按当前筛选条件导出快照，便于运营留档、财务复盘和测试排障。

## V2 演进预览

V2 围绕“总保证金账户 + 规则绑定 + 旧账户结转”展开，当前已先交付只读预览，正式写库迁移与规则绑定动作后续再进入可执行阶段。

当前这部分的产品定位已经明确为“V2 架构变更预览”，重点承接以下痛点：

1. 一个主体存在多个保证金账户时，运营和财务难以直接判断主体维度的总应缴、总冻结和总可用。
2. 欠款抵扣、扣罚和退还分散在多个历史账户时，容易出现局部不足、整体充足但无法顺滑处理的情况。
3. 后续若接入钱包、账务、风控和结算，继续沿用多账户并行模型会让接口和补偿链路变得更重。

因此 V2 后续会继续补三类可执行接口，但在正式落库前不会伪装成“已投产能力”：

| 规划类型 | 目标 |
| --- | --- |
| 规则绑定执行接口 | 把多个保证金规则正式挂到同一总账户 |
| 旧账户迁移执行接口 | 把历史保证金账户余额、冻结额和映射关系结转到总账户 |
| 总账户动作接口 | 让冻结、解冻、扣罚、退款、欠款抵扣逐步切到总账户口径 |
