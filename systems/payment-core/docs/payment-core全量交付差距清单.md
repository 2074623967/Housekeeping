# payment-core 全量交付差距清单

## 1. 文档定位

本文档不是从“当前代码已经做了什么”出发，而是从以下四类资料反推 `payment-core` 在完整支付系统中的目标边界，再对照当前仓库实现，形成真实差距清单：

1. `/Users/abc123/图稿`
2. `/Users/abc123/笔记`
3. `/Users/abc123/workspace/支付相关`
4. `chentianyuzhou.com` 所代表的支付专家方法论与系统拆分视角

适用对象：

- 支付产品经理
- 财务产品经理
- 前端开发
- 后端开发
- 测试工程师
- 系统架构师

## 2. 当前结论

截至 `2026-07-23`，当前 `payment-core` 的真实状态应调整为：

1. 已完成 `支付交易闭环 V1` 的一部分前后端实现
2. 已完成 `后台核心查询页 + 用户端收银台/结果页` 的基础联调
3. 还没有完成“完整支付系统”在 `PC / APP / H5 / 配置管理 / 网关管理 / 日终处理 / 监控管理` 层面的全量前端与全量后端交付
4. 已补齐异常 SLA 巡检之后的本地告警派发骨架，但尚未达到生产级通知中心能力
5. 之前若将当前版本理解为“完整支付系统前端后端已基本完成”，这个判断不准确

更准确地说：

- 当前代码是 `支付核心域最小可运行版`
- 不是 `完整支付平台冻结版`

## 7. 五角色二次评审结论

### 7.1 财务产品经理视角

当前 `payment-core` 只能支撑：

- 基础支付结果查看
- 部分运营排查

尚不能支撑：

- 资金归口管理
- 完整退款、结算、对账、保证金处理
- 财务审批与审计闭环

### 7.2 架构师视角

当前 `payment-core` 的系统边界是合理的，但范围被误读了。

正确理解应为：

- 当前是 `支付核心域 V1`
- 不是 `完整支付平台`

### 7.3 后端视角

当前后端适合继续作为：

- 支付核心主链路基线
- 下游账户、清分、结算、对账系统的上游事件来源

但不适合被定义为：

- 完整充值/提现/转账/协议/网关管理平台

### 7.4 前端视角

当前前端最大问题不是代码风格，而是页面范围没有按完整资料基线做全量实现。

也就是说：

- 不是“几个页面不够精致”
- 而是“整批页面还没做”

### 7.5 测试视角

当前测试基线适合：

- 支付主链路联调
- 基础页面构建验证

但不适合：

- 按完整支付平台做全量验收

3. 当前只证明本地格式转换和回归测试通过，不代表真实供应商响应样本、生产字段分级授权或隐私验收完成。

### 8.9 2026-09-09 异常告警传输异常摘要最小化进展

1. IM、SMS、EMAIL 三类 Webhook 传输异常不再把底层异常文本写入 `providerDeliveryMessage`，统一输出 `transportError=[REDACTED]`。
2. 派发服务对自定义通知器返回的 `transportError=` 摘要执行二次截断，并对通知器抛出的运行时异常生成固定运营摘要；原始故障仍只保留在内部回执快照。
3. 当前仍缺生产敏感原文受控查看、访问审计、保留期限和真实供应商异常样本验收，不能将本地最小化等同于完整安全治理。

### 8.10 2026-09-09 支付事件与死信任务出参最小化进展

1. 支付事件列表、CSV 和重发后的刷新列表已改为返回脱敏副本；事件原始载荷继续留在 Mapper 与数据库事实中，不因展示转换被覆盖。
2. 死信任务列表、待重放、人工结案和重放响应已脱敏载荷与消息头快照；实际重放仍使用持久化原始载荷，避免脱敏结果改变消费者输入。
3. 统一脱敏规则新增 `Authorization`、访问令牌、API/访问密钥、密钥、签名、私钥和 Cookie 等凭据字段；连字符、下划线与大小写变体统一归一，畸形载荷或消息头 JSON 失败闭合为 `[REDACTED]`。
4. 重放发送失败的可见处置说明固定为 `重放发送失败：[REDACTED]`，不扩散消息代理异常原文；当前仍缺生产 IAM、字段级授权、原文访问审计、保留期限和隐私验收。

### 8.11 2026-09-09 未知系统异常出参与日志最小化进展

1. 全局异常处理器不再将任意未预期异常的 `exception.getMessage()` 作为 `PAYMENT-500` 响应文案，对外统一返回 `system error` 和请求追踪号。
2. 服务端错误日志只记录与响应一致的 `requestId` 和异常类型，不记录异常消息或堆栈，避免数据库地址、端点、SQL 或凭据片段从响应转移到普通日志。
3. 明确的 `BusinessException` 继续返回业务错误码与业务提示，`IllegalArgumentException` 继续返回参数校验提示；当前最小化不能替代受控错误详情存储、日志访问权限、保留期限或生产观测验收。

### 8.12 2026-09-09 请求追踪号并发安全进展

1. `RequestIdHolder` 已从共享静态 `SimpleDateFormat` 改为 JDK 8 线程安全的 `DateTimeFormatter`，消除并发格式化数据竞争。
2. 原每毫秒 900 个随机数的有限后缀改为 8 位 UUID 十六进制后缀，保留 `REQ + 17 位时间` 可读前缀，并降低同进程及多实例碰撞风险。
3. 已新增并发生成 10,000 个请求号的格式与唯一性测试；当前仍未形成跨服务追踪上下文透传、集中检索、生产峰值压测或全局唯一性的形式化证明。

### 8.13 2026-09-09 MyBatis 参数日志默认关闭进展

1. 应用配置已显式使用 MyBatis `NoLoggingImpl`，即使普通日志根级别被临时调到 DEBUG，也不会输出 SQL 语句和绑定参数，降低支付配置、凭据与个人信息进入普通日志的风险。
2. 13 个绕过 Spring Boot 自动配置、手工创建 MyBatis `Configuration` 的 Mapper 集成测试已应用同一规则，并新增 `application.yml` 配置契约测试，避免测试日志形成旁路或默认值被误删。
3. 该安全默认值会牺牲 MyBatis SQL 文本和参数级诊断能力；生产排障应使用受控指标、链路追踪、慢查询设施或独立治理工具，当前不据此宣称生产日志 IAM、隐私或可观测性验收完成。

### 8.14 2026-09-09 主动查单失败快照最小化进展

1. 主动查单捕获 `BusinessException` 后写入通知日志的 `responsePayload` 不再复制任意异常消息，只保留受控错误码和固定 `channel query failed` 文案。
2. 原业务异常继续向调用方抛出，查单失败状态、失败计数、自动补偿退避与处理日志口径不变；本轮只关闭异常原文进入持久化响应快照的旁路。
3. 已用包含模拟数据库地址和令牌的异常验证原文不落入通知快照；当前不据此宣称生产历史数据清理、字段级权限、访问审计或真实渠道故障验收完成。

### 8.15 2026-09-09 Mapper 原始字符串替换禁用进展

1. 当前 22 份 MyBatis Mapper XML 均使用 `#{...}` 参数绑定或 `<choose>` 固定 SQL 分支，不存在 `${...}` 原始字符串替换入口。
2. 已新增 classpath 级契约测试，自动枚举全部 `mapper/*.xml` 并拒绝 `${` 标记；后续新增 Mapper 无需维护固定文件清单即可进入检查。
3. 该规则降低动态字段、排序和条件直接拼接造成的 SQL 注入风险，但不替代数据库账号最小权限、业务授权、存储过程审计、真实攻击测试或生产数据库安全验收。

### 8.16 2026-09-09 三端收银台 URL 令牌最小化进展

1. APP、H5、PC 业务入口不再把支付接入令牌放入路由 query，改为按来源应用写入当前标签页 `sessionStorage`；收银台提交时从对应会话键读取。
2. 收银台到结果页、结果页返回收银台均不再透传令牌；旧版含令牌链接仍可一次性迁移到会话存储，并立即通过 `router.replace` 清除当前 URL 中的 `accessToken`。
3. 会话存储不可用时业务入口失败闭合，不退回 URL 传参；本轮仅降低浏览器历史、复制链接和 Referer 扩散风险，演示令牌仍存在于前端构建产物，不能据此认定可信认证、服务端会话、XSS 防护或生产密钥治理完成。

### 8.17 2026-09-09 运营查询分页边界进展

1. 16 个分页查询 DTO 已统一把页码限制为 `1..1000`、Mapper 每页参数限制为 `1..100`，最大 offset 收敛为 `99,900`，避免极大页码导致 `int` 溢出为负数。
2. 统一边界位于 DTO 层，现有 Service 归一化、列表返回页码与 Mapper offset 使用同一结果；任务日志和死信任务的特殊分页形态也已纳入。
3. classpath 测试自动发现分页 `*QueryDTO` 并要求至少覆盖当前 16 个对象；该保护不能替代索引治理、游标分页、查询超时、生产数据量压测或数据库容量验收。

## 9. 最终结论

当前 `payment-core` 已经具备一定的真实工程基础，但它距离你期望的“完整支付系统前后端”仍有明显差距。

这次最重要的纠偏结论是：

1. 当前实现不是完整支付平台
2. 当前实现只是支付核心域的部分交付
3. 后续开发必须先按四类资料重建页面矩阵和模块边界
4. 再决定哪些继续补在 `payment-core`，哪些拆去后续系统
