# payment-core 全量交付差距清单

## 1. 文档定位

本文档不是从“当前代码已经做了什么”出发，而是从以下四类资料反推 `payment-core` 在完整支付系统中的目标边界，再对照当前仓库实现，形成真实差距清单：

1. `/Users/abc123/图稿`
2. `/Users/abc123/笔记`
3. `/Users/abc123/workspace/支付相关`
4. `chentianyuzhou.com` 所代表的支付专家方法论与系统拆分视角

适用对象：

- 支付产品经理
- 财务产品经理
- 前端开发
- 后端开发
- 测试工程师
- 系统架构师

## 2. 当前结论

截至 `2026-07-23`，当前 `payment-core` 的真实状态应调整为：

1. 已完成 `支付交易闭环 V1` 的一部分前后端实现
2. 已完成 `后台核心查询页 + 用户端收银台/结果页` 的基础联调
3. 还没有完成“完整支付系统”在 `PC / APP / H5 / 配置管理 / 网关管理 / 日终处理 / 监控管理` 层面的全量前端与全量后端交付
4. 已补齐异常 SLA 巡检之后的本地告警派发骨架，但尚未达到生产级通知中心能力
5. 之前若将当前版本理解为“完整支付系统前端后端已基本完成”，这个判断不准确

更准确地说：

- 当前代码是 `支付核心域最小可运行版`
- 不是 `完整支付平台冻结版`

## 7. 五角色二次评审结论

### 7.1 财务产品经理视角

当前 `payment-core` 只能支撑：

- 基础支付结果查看
- 部分运营排查

尚不能支撑：

- 资金归口管理
- 完整退款、结算、对账、保证金处理
- 财务审批与审计闭环

### 7.2 架构师视角

当前 `payment-core` 的系统边界是合理的，但范围被误读了。

正确理解应为：

- 当前是 `支付核心域 V1`
- 不是 `完整支付平台`

### 7.3 后端视角

当前后端适合继续作为：

- 支付核心主链路基线
- 下游账户、清分、结算、对账系统的上游事件来源

但不适合被定义为：

- 完整充值/提现/转账/协议/网关管理平台

### 7.4 前端视角

当前前端最大问题不是代码风格，而是页面范围没有按完整资料基线做全量实现。

也就是说：

- 不是“几个页面不够精致”
- 而是“整批页面还没做”

### 7.5 测试视角

当前测试基线适合：

- 支付主链路联调
- 基础页面构建验证

但不适合：

- 按完整支付平台做全量验收

### 8.74 2026-09-10 gateway-access 支付查单代理边界进展

1. `gateway-access` 已提供真实存在的 `POST /api/gateway/payment-orders/query`，并在代理前校验调用凭证、接入应用、权限归属、渠道网关、有效证书和当前环境启用路由；支付核心默认地址从误指 reconciliation-system 的 `18150` 修正为 gateway-access 的 `8090`。
2. 访问密钥和微信、支付宝、银行查单上游 URL 均默认留空，任一必要配置缺失即失败闭合；代理只接受上游响应码为 `0` 且包含明确 `tradeStatus` 的结果，不读取本地支付状态或样例网关地址制造交易事实。
3. gateway-access 全量 `30` 个测试、payment-core 全量 `635` 个测试通过，Spring/H2/MyBatis 运行态启动及默认拒绝响应完成冒烟；审计只保存调用应用、网关、操作类型、来源 IP、结果和稳定风险码，不保存密钥或上游异常原文。

### 8.75 2026-09-10 gateway-access 支付提交代理边界进展

1. `gateway-access` 已补 `POST /api/gateway/payment-orders/submit`，复用支付查单的凭证、应用、权限、网关、有效证书和发布路由门禁；微信、支付宝和银行提交 URL 默认均为空，不会访问样例地址或生成模拟受理事实。
2. `payment-core` 已补默认关闭的 gateway-access 支付提交适配器；配置完整时传递稳定业务标识和幂等键，只接受包含渠道交易号、尝试状态、状态类型和渠道返回码的明确受理响应。失败统一返回 `PAYMENT-1048`，已准备提交的尝试进入“结果未知，待查单”，不自动重提。
3. gateway-access 默认 H2/MyBatis Mapper 日期兼容问题已由真实 Spring 上下文集成测试覆盖；全量测试分别为 `36` 和 `638` 个。本地 `8090 -> 19090` 受控上游冒烟验证了成功转发与错误凭证拒绝，但不属于微信、支付宝或银行真实联调。

### 8.76 2026-09-10 gateway-access 退款查单代理边界进展

1. `gateway-access` 已补 `POST /api/gateway/refunds/query`，复用交易代理治理门禁并要求明确的退款状态和完全匹配的渠道退款号；三个渠道上游 URL 默认留空，不从 H2 台账或本地退款状态制造查询事实。
2. `payment-core` 退款查单适配器已补应用/访问凭证请求头，凭证为空时不生效，默认 URL 从错误的 `18150` 修正为 gateway-access `8090`；网关业务拒绝、空结果和字段非法继续以 `PAYMENT-1046` 失败闭合并进入既有退避历史。

4. 退款查单代理代码边界已闭合，仍缺微信、支付宝和银行真实退款协议与报文映射、签名验签、商户应用绑定、生产密钥托管与轮换、来源 IP 白名单、真实网络故障验证、退款到账、渠道账单对账、会计核对和财务验收。

## 9. 最终结论

当前 `payment-core` 已经具备一定的真实工程基础，但它距离你期望的“完整支付系统前后端”仍有明显差距。

这次最重要的纠偏结论是：

1. 当前实现不是完整支付平台
2. 当前实现只是支付核心域的部分交付
3. 后续开发必须先按四类资料重建页面矩阵和模块边界
4. 再决定哪些继续补在 `payment-core`，哪些拆去后续系统
