# 第一阶段B-支付交易闭环测试方案

## 1. 文档定位

本文档作为 `payment-core` 一期支付交易闭环 V1 的正式测试方案，约束测试范围、测试重点和验收标准。

## 2. 测试目标

确保从订单发起支付到支付结果收口的全过程满足：

1. 主流程可执行
2. 页面与接口字段一致
3. 日志轨迹可追溯
4. 状态变更可验证
5. 旧查询页面不回退

## 3. 测试范围

### 3.1 接口范围

1. 创建预付单
2. 获取收银台
3. 提交支付
4. 模拟回调
5. 主动查单
6. 关闭支付单
7. 支付详情查询

### 3.2 页面范围

1. 工作台
2. 订单中心
3. 支付单管理
4. 支付单详情
5. 收银台
6. 支付结果页

### 3.3 数据范围

1. 支付单
2. 账单
3. 预付单
4. 支付尝试
5. 路由日志
6. 回调日志
7. 事件日志

### 3.4 自动化回归范围

1. 已成功或已关闭支付单的重复/迟到回调不得再次更新状态。
2. 缺少交易状态或渠道交易号的回调必须被拒绝。
3. 超时关单任务必须同时更新支付单、支付尝试、预付单并写入关闭事件。
4. 开启签名校验后，缺少签名字段或签名错误的渠道回调必须被拒绝。
5. 同一订单在预付单未失效且支付单未收口时重复创建预付单，必须复用原预付单与支付单。
6. 同一预付单在支付单已进入 `WAIT_CALLBACK`、`SUCCESS` 或 `CLOSED` 后重复提交，必须直接幂等返回，不再新增路由和尝试记录。

4. 管理端输入 `¥50.00`、带千分位金额和空值时，验证本页合计不出现 `NaN`，并以币种符号和两位小数展示；前端构建必须通过。
5. 核对双全量 schema 与增量迁移中的 `(payment_order_id, status)` 联合索引；生产继续补真实 MySQL `EXPLAIN`、大分页数据量、渠道到账和财务核销验证。

### 4.77 退款申请与失败重试额度并发

1. 使用两个独立事务对同一 `100.00` 支付单分别申请 `60.00` 退款，验证后到事务在先到事务提交前等待，提交后重新汇总活动退款并以超额失败，最终只有一笔 `60.00` 申请。
2. 预置一笔 `FAIL 60.00` 退款，让替代 `REVIEWING 60.00` 退款先持有支付单锁；并发重试旧退款应等待替代退款提交，再因 `60.00 + 60.00 > 100.00` 被拒绝。
3. 拒绝重试后验证旧退款仍为 `FAIL`、替代退款仍为 `REVIEWING`、活动退款合计为 `60.00`，且状态更新、操作日志和渠道调用均无重试副作用。
4. 分别覆盖人工重试、任务重试、零活动金额、额度刚好用尽、失败退款状态变化以及金额快照缺失或非法的失败闭合路径。
5. H2 双事务通过后，生产继续覆盖 MySQL 多实例锁等待、死锁选择与重试、锁超时、连接池占用、热点支付单吞吐和真实渠道退款验收。

### 4.78 退款渠道下发 outbox 与结果未知补偿

1. 在事务提交前执行退款审核，验证退款状态、操作日志和 `REFUND_SUBMIT` 事件处于同一事务，且渠道服务未被调用；触发 `afterCommit` 后才允许进入独立派发事务。
2. 对同一 `refundOrderId` 重复写入事件，验证只保留一个稳定事件号；失败退款重试将原事件重新激活为 `PENDING`，并保持事件退款单号和支付单号一致。
3. 派发时覆盖事件 `SUCCESS` 幂等短路、退款已非 `PROCESSING` 收口、事件/退款快照不一致、非法金额、空渠道、渠道抛错和空渠道退款号；只有获得有效受理号时标记事件成功。
4. 结果未知时验证退款仍为 `PROCESSING`、额度不释放、操作日志为未知结果，事件按上限进入 `FAILED/DEAD_LETTER`；到期 `PENDING/FAILED` 可被自动扫描，未实现派发的其他 `PENDING` 事件不应反复入队。
5. 本地模拟渠道验证相同退款单返回相同渠道退款号。生产继续覆盖真实 MySQL 多实例竞争、渠道幂等键与查单语义、网络超时后的真实受理状态、退款到账、告警及人工恢复。

### 4.79 退款渠道受理事实绑定与展示

1. 渠道返回有效退款号时，验证退款单保存实际渠道、渠道退款号和首次受理时间，之后才写渠道提交日志并标记事件成功。
2. 对同一退款单再次绑定不同渠道退款号，验证条件更新返回 `0` 且原事实不变；对另一退款绑定相同 `(channel_code, channel_refund_no)` 时验证唯一键拒绝。
3. 构造事件为 `FAILED`、退款仍为 `PROCESSING` 且已保存受理号，验证补偿只校验渠道并标记事件成功，不调用渠道、不重写受理时间；渠道不一致时失败闭合。
4. 渠道退款号覆盖空白、首尾空格、`128/129` 字符和控制字符边界；非法结果不得写入受理字段，退款保持处理中并进入事件补偿。
5. 退款详情验证三项新增字段与数据库一致，管理端空值显示 `-`、有值展示原渠道事实。生产继续验证 MySQL 增量迁移、真实渠道退款号唯一性、回调/查单绑定和到账核验。

### 4.80 退款可信回调验签与终态收口

1. 分别按 HMAC-SHA256 和既有 RSA2 基线构造退款签名原文，验证渠道小写规范、时间窗、nonce 防重和 `REFUND + refundOrderId` 落库；支付回调继续断言 `PAYMENT + paymentOrderId`，防止兼容回归。
2. 构造 `PROCESSING` 且已绑定渠道受理号的退款，验证成功/失败回调锁定退款单、校验渠道与渠道退款号、CAS 更新终态并以 `channel-callback` 记录日志。
3. 覆盖相同终态幂等、相反终态冲突、非 `PROCESSING` 拒绝、退款单不存在、渠道不匹配、渠道退款号不匹配，以及字段缺失、超长、控制字符和非法状态。
4. Mapper 集成验证锁定快照和 `PROCESSING` 单向 CAS；检查 `/api/refunds/success`、`/api/refunds/fail` 及管理端模拟按钮均已移除。

### 4.81 退款人工主动查单与并发收口
