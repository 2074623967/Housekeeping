# payment-core 页面矩阵与系统归属清单

## 1. 文档定位

本文档用于在 `2026-07-25` 这个基线时点冻结 `payment-core` 的真实页面边界，并将四类资料中出现的相关页面、模块和运营能力，明确归属到后续独立系统，避免继续把完整支付平台的全部内容误堆到 `payment-core`。

## 2. 冻结结论

`payment-core` 不是完整支付平台，也不是资金平台全集。

从资深财务产品经理、资深架构师、资深后端、资深前端、资深测试五个角色交叉评审后，当前冻结结论如下：

1. `payment-core` 只保留 `正向支付交易主链路` 与 `支付核心运营查询能力`
2. 与 `资金归属、账务记账、清分、结算、退款闭环、对账、保证金、钱包、配置、风控` 强相关的页面，不再继续塞进 `payment-core`
3. `payment-core` 后续可以继续增强，但增强范围必须围绕：
   - 订单发起支付
   - 预付单生成
   - 收银台展示
   - 渠道提交
   - 支付回调
   - 状态查询
   - 关闭支付单
   - 支付请求与支付日志留痕
   - 支付运营排查与基础监控

## 3. payment-core 保留边界

### 3.0 当前真实路由盘点

截至 `2026-07-25`，`payment-core/frontend` 不是单一后台，而是已经存在四套实际工程：

1. `admin-web`：当前真实路由包括 `/dashboard`、`/orders`、`/bills`、`/payment-flows`、`/payment-flows/:flowSource/:flowNo`、`/payment-routes`、`/payment-routes/:routeNo`、`/payment-events`、`/payment-issues`、`/payment-issues/:issueNo`、`/payment-issue-alerts`、`/cashier-sessions`、`/payment-requests`、`/payment-requests/:requestNo`、`/payment-logs`、`/payment-logs/:logNo`、`/payment-records/*`、`/payments/*`、`/refunds/*`、`/payment-config`、`/payment-monitor`、`/payment-task-center`、`/payment-day-end`、`/worker-settlements`
2. `app-web`：当前真实路由包括 `/recharge`、`/withdraw`、`/transfer`、`/balance-pay`、`/cashier/:prepayOrderNo`、`/payment-result/:paymentOrderId`
3. `h5-web`：当前真实路由包括 `/recharge`、`/withdraw`、`/transfer`、`/balance-pay`、`/cashier/:prepayOrderNo`、`/payment-result/:paymentOrderId`
4. `pc-web`：当前真实路由包括 `/recharge`、`/withdraw`、`/transfer`、`/balance-pay`、`/cashier/:prepayOrderNo`、`/payment-result/:paymentOrderId`
5. `mini-program`：当前原生页面包括四类业务入口、收银台和支付结果
6. `api-client`：当前命令包括预付、收银台、提交、支付详情、主动查单和关单

因此后续做边界判定时，不能只看资料里的“目标页面”，还要同时看当前仓库里“已经先落在 payment-core”的实际页面。下面的归属结论，都是在这个真实路由事实之上做的。

| 权限与审批 | PC 后台 | `ops-config-system` | 否 | 通常与运营后台平台能力一并建设 |
| 风控拦截与监控台 | PC 后台 | `risk-control-system` | 否 | 风险策略、拦截、告警是独立风险域 |

补充说明：

- 当前仓库里 `admin-web:/payment-config` 已经真实存在，它承担的是“先把渠道、路由、协议、返回码、网关和值班路由治理台账跑起来”的过渡职责。
- 后续不应继续把所有配置都沉到 `payment-core`；其中网关接入治理优先拆向 `gateway-access`，更泛化的运营配置再拆向独立配置域。

### 5.4 支付请求唯一详情

2. 路由事实只按 `attempt_no` 关联；历史路由缺少尝试号时展示未关联，不复用同一支付单的其他路由。
3. 页面提供标准订单、账单、支付单、支付记录、收银台会话、支付流水、路由结果、处理日志和用户收银台联查，缺少关联或快照陈旧时失败关闭。

### 5.5 支付流水唯一详情

1. 管理端路由 `/payment-flows/:flowSource/:flowNo` 对应 `GET /api/payment-flows/{flowSource}/{flowNo}`，以来源类型和来源编号共同标识事实。
2. 四类来源为 `PAYMENT_ATTEMPT`、`CHANNEL_NOTIFY`、`ROUTE_RECORD`、`BUSINESS_EVENT`；列表和导出必须同时展示来源与编号。
3. 回调、事件没有确定预付单/请求归属时保持空值；路由仅在 `attempt_no` 可精确匹配时开放请求联查。
4. 页面只提供订单、账单、支付单、请求、同支付单流水和处理日志等只读联查，不承接账务、清分、结算、对账或资金作业。

### 5.6 支付路由执行唯一详情

1. 管理端路由 `/payment-routes/:routeNo` 对应 `GET /api/payment-routes/{routeNo}`，以路由记录号作为唯一实体标识。
2. 详情展示路由记录号、支付请求号、支付单、业务订单、预付单、客户、金额、支付方式、渠道、规则、结果、配置快照、终端、IP、幂等键和请求/响应报文。
3. 请求上下文仅按 `attempt_no` 精确关联；历史空尝试号路由不猜测归属，只保留路由事实。
4. 页面提供支付单、支付请求、路由流水、同支付单流水和处理日志联查；首次失败或刷新失败陈旧快照均禁止继续导航。

### 5.7 支付交易异常唯一详情

1. 管理端路由 `/payment-issues/:issueNo` 对应 `GET /api/payment-issues/{issueNo}`，以异常编号作为唯一实体标识。
2. 详情展示异常事实、责任组、处理状态、SLA、升级建议、告警派发摘要、供应商投递摘要和最近处理动作。
3. 页面提供支付单、处理日志、支付流水、支付事件、告警明细和推荐入口联查；业务订单号仅作为异常事实展示，不直接推导标准订单详情，缺少关联或快照陈旧时失败关闭。
4. 详情页只读，不执行批量处理、确认回执、重发事件或修改支付状态。

## 7. 对后续开发的强约束

自本文档冻结后：

1. 任何新页面在进入开发前，必须先确认归属系统
2. 不允许因为参考图稿里“看起来像支付后台”就直接放进 `payment-core`
3. `payment-core` 若新增页面，必须同时满足：
   - 直接服务正向支付主链路
   - 属于支付核心对象管理
   - 不与账务、清分、结算、退款、对账、钱包、保证金职责冲突
4. 若页面同时涉及多个系统，优先拆成：
   - `payment-core` 只读入口
   - 独立系统完整作业页
