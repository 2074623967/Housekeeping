# 第一阶段B-支付交易闭环需求清单

## 1. 文档定位

本文档当前作为 `payment-core` 一期支付交易闭环 V1 的需求冻结清单，区分：

1. 已落地需求
2. 仍需增强需求
3. 后续系统承接需求

## 2. 已落地需求

### 2.1 业务需求

1. 订单可发起支付
2. 支付过程可创建账单
3. 账单可生成预付单
4. 用户可在收银台完成支付提交
5. 回调可更新支付状态
6. 后台可查看支付轨迹

### 2.2 产品需求

1. 收银台展示订单摘要和应付金额
2. 收银台展示支付方式
3. 支付结果页可展示成功、处理中、关闭态
4. 后台可查看支付单与支付详情
5. 后台可执行查单、回调、关闭操作

### 2.3 技术需求

1. 独立数据库已拆出
2. MyBatis + mapper.xml 已落地
3. `serviceimpl` 已承担业务编排
4. 支付事件、回调日志、路由日志已落库
5. `t_payment_attempt` 作为独立支付请求事实，保存一次渠道提交的请求、响应、幂等键、终端和状态
6. `t_payment_process_log` 作为独立不可变处理日志事实，统一承接支付提交、路由、回调和业务事件，并支持存量回填；通用日志只保存最小必要摘要，不复制请求、响应或事件原始载荷
7. 支付请求、支付流水、路由执行、支付单、统一支付记录、订单、账单、收银台会话、退款、服务者结算和支付异常列表，以及对应已有 CSV 出参统一最小化姓名、用户引用和请求上下文等敏感字段；支付、统一支付记录与退款详情、退款动作响应及异常告警确认响应同样输出脱敏副本；供应商回执需兼容 `HTTP_RESPONSE:{...}` 受控来源前缀，传输异常摘要不得包含底层异常原文，非结构化内容失败闭合，不覆盖 Mapper 原始事实或内部交易输入
8. 支付路由执行结果支持按当前筛选和排序条件导出全量脱敏 CSV，与列表复用同一查询口径且不受页面分页限制
9. 支付事件列表、CSV、重发刷新及死信任务列表与处置动作响应只返回载荷和消息头的脱敏副本；授权头、令牌、密钥、签名、私钥和 Cookie 等凭据及畸形 JSON 失败闭合，实际死信重放继续使用持久化原始载荷，消息代理异常原文不得进入可见处置说明
10. 未预期系统异常只返回固定 `PAYMENT-500 / system error` 和 `requestId`，普通错误日志只保留同一请求号与异常类型；业务异常和参数校验继续提供明确提示，后续受控错误详情必须补可信权限、加密、审计和保留期限
11. 请求号生成必须线程安全并具备足够碰撞空间，成功与失败响应统一生成 `REQ + 毫秒时间 + 随机唯一后缀`；前端按不透明字符串使用，后续跨服务追踪另行补入口透传、消息传播和集中检索
12. MyBatis SQL、结果集与绑定参数日志默认关闭，且手工创建的测试配置遵循同一规则；提高普通日志级别不得恢复支付密钥、令牌或个人信息输出，生产诊断由受控指标、链路追踪、慢查询或独立治理工具承接
13. 主动查单失败通知快照只保存受控错误码和固定失败文案，不持久化任意异常消息；调用方业务错误、失败状态、补偿退避与统计口径保持不变，历史数据清理和生产原文诊断另行治理
14. 所有 MyBatis Mapper XML 禁止 `${...}` 原始字符串替换，业务值使用 `#{...}` 参数绑定，排序等结构位置使用固定 SQL 分支；classpath 契约测试自动覆盖新增 Mapper，数据库最小权限与生产 SQL 审计另行验收
15. APP、H5、PC 收银台接入令牌不得进入 URL query，页面间跳转使用标签页会话存储承接并兼容清理旧链接；存储不可用时失败闭合，生产仍需以可信认证、服务端会话或短期凭据替换前端演示令牌
16. 所有运营分页查询统一限制页码 `1..1000`、每页 `1..100`，避免整数溢出和无界深分页；分页元数据与 Mapper 使用同一归一化结果，生产索引、游标分页和容量压测另行完成

### 2.4 告警通知供应商配置治理

1. 支持供应商 CREATE/UPDATE/STATUS_CHANGE 完整候选提交、查询、批准和驳回。
2. 候选批准前不得改变自动派发读取的运行配置；同一供应商只允许一条待复核申请。
3. 批准时复验供应商存在性或完整运行配置指纹，并由不同的自声明复核人处理。
4. 管理端提供完整新增/编辑表单、启停申请身份与原因、复核身份与意见，以及加载、空、失败和已处理状态。
5. 当前身份仅为 `SELF_DECLARED`，真实供应商配置、接收人核验、送达回执和正式审批仍为外部验收项。

## 3. 仍需增强需求

### P0

1. `PC / H5 / APP` 收银台页面矩阵补齐到参考稿口径
2. 支付请求管理已基于独立尝试事实查询，支付处理日志已升级为独立事实表并完成通用摘要数据最小化，支付排障与运营查询出参已统一基础脱敏；后续继续补日志归档、可信身份、按角色字段分级授权和外部检索平台
3. 提交支付、回调、查单、关闭支付的异常码与失败态展示增强

本批已补齐告警派发失败快照最小化：传输异常和通知器运行时异常不再把底层异常原文写入普通业务表；历史数据清理、可信权限、访问审计和独立受控诊断设施仍待生产治理。

本批已补齐告警供应商正常回执落库脱敏：业务字段先解析，普通告警日志仅保存结构化脱敏副本；历史快照清理、真实供应商字段盘点和独立原始凭证设施仍待生产治理。

本批已补齐告警供应商结果字段容量保护：内置与自定义通知器结果在落库前统一对齐当前 schema，超长主通道失败结果不再阻断备用通道；生产数据库模式和真实供应商容量仍待验收。

本批已补齐告警供应商诊断码最小化：普通投递说明只保留受控 ASCII 标识符，外部自由文本和换行内容统一遮蔽；真实供应商码表和生产日志安全仍待验收。

本批已补齐超时支付逐笔关单隔离：单笔失败只回滚该支付单并继续批次，任务日志记录准确计数和有限失败标识，失败单可由后续轮次自然重试；生产数据库事务、真实渠道关单、多实例调度和容量仍待验收。

本批已补齐失败退款真实重提与逐笔隔离：任务重试复用退款领域状态机并重新提交渠道，单笔失败不再中断整批，任务日志保留准确计数和有限失败标识；真实渠道幂等、超时查单、防重复退款、生产事务和多实例调度仍待验收。

本批已补齐失败事件逐条重发隔离：人工任务处理全部失败事件、自动任务只处理到期失败事件，受控投递失败提交失败或死信状态，单条意外异常回滚后继续批次，任务日志保留准确计数和有限失败事件号；生产 MQ/HTTP、订阅方幂等、生产事务、多实例调度和容量仍待验收。

本批已补齐告警派发与回执逐条事务隔离：单条派发日志和源状态、单条回执和源确认分别保持本地原子，任一告警异常不再中断整批，任务日志保留准确计数和有限失败告警号；真实供应商幂等、回执乱序、生产事务、多实例租约和容量仍待验收。

本批已补齐支付主链路业务编号碰撞保护：账单、支付单、预付单、路由、尝试、事件、通知/查单日志和告警任务日志不再仅依赖毫秒时间，随机后缀降低同毫秒并发唯一键冲突风险；生产多实例容量、冲突监控、时钟异常和随机源仍待验收。

本批已补齐异常 SLA 告警逐条生成隔离：初次告警与升级告警单条失败不再回滚整批，任务日志记录真实失败计数和有限异常引用；人工并发触发的数据库级原子防重、生产事务、多实例竞争和容量仍待补齐。

本批已补齐异常 SLA 告警数据库级生成幂等：初次活动告警按异常号唯一、确认后释放，升级告警按来源告警号永久唯一，并发重复记为跳过而非失败；真实 MySQL 存量迁移、锁影响、唯一键冲突监控、并发压测和外部供应商防重仍待验收。

本批已补齐本地模拟渠道交易号碰撞保护：微信 H5、支付宝 H5、线下银行和兜底适配器统一使用毫秒时间加完整 UUID 随机段，并验证高频样本与响应快照一致性；真实渠道流水、供应商幂等、超时未知结果查单和生产并发仍待真实接入验收。

本批已补齐支付提交幂等键输入边界：最终键在任何控制、风控、持久化、并发占位或渠道副作用前完成非空、`128` 字符和控制字符校验，请求及风控 JSON 快照统一安全转义；真实渠道幂等字段映射、生产数据库索引、多实例并发和超时未知结果恢复仍待验收。

本批已补齐支付提交本地事务与外部渠道副作用隔离：渠道调用前提交路由、令牌和幂等尝试，渠道调用置于事务外，结果事务失败后保留“结果未知，待查单”与活跃令牌，禁止直接重提；真实渠道受理/超时语义、生产数据库传播、进程崩溃、多实例竞争和对账恢复仍待验收。

本批已修正主动查单首次等待时钟：人工批量补查、自动补偿及其积压计数统一以最新支付尝试时间为准，旧支付单上的新鲜提交不会立即并发查单，无支付尝试的异常记录失败闭合排除；真实 MySQL 执行计划、存量数据、多实例调度和峰值容量仍待验收。

本批已补齐过期支付不确定结果保护：本地过期任务只关闭从未产生渠道提交事实的 `PREPAY_CREATED`，已提交交易在收银台过期后继续按退避查单，历史过期误关仅能由可信渠道成功恢复，普通人工关闭保持终态；真实渠道关单/撤销、生产存量误关盘点、关闭与成功竞态及资金对账仍待验收。

本批已补齐人工关闭渠道提交保护：关闭接口仅允许无渠道流水、无支付尝试的未提交状态并以条件更新处理并发，已提交或结果未知返回 `PAYMENT-1029` 且保留提交令牌；四端关闭入口、先查单提示和收银台支付单号已同步，真实渠道关闭/撤销、生产存量误关盘点、MySQL 并发和资金对账仍待验收。

本批已补齐支付回调渠道绑定保护：完成渠道级验签后必须与支付单实际路由渠道一致，跨渠道或未绑定渠道返回 `PAYMENT-1030` 且不产生状态、资金、事件或令牌副作用；后台模拟回调改用实际渠道，真实渠道商户/应用/证书/网络来源绑定和生产回调安全仍待验收。

本批已补齐支付回调渠道交易号绑定保护：支付单已有渠道交易号时回调必须精确一致，不一致返回 `PAYMENT-1031` 且不得覆盖或产生资金副作用；本地无交易号时保留可信同渠道首次绑定以恢复未知结果，真实商户订单号映射、历史串单扫描和渠道对账仍待验收。

本批已补齐支付回调验签默认失败闭合：基础配置和服务注入兜底均默认开启验签，仅 demo profile 显式关闭以支持本地模拟回调，并以配置契约测试防止默认值回退；真实渠道密钥托管、证书轮换、网络来源控制和生产报文验收仍待完成。

本批已补齐支付回调渠道凭证隔离：移除全局共享回调密钥配置与服务回退，HMAC/RSA2 只能使用 URL 渠道对应的密钥或公钥，渠道凭证缺失返回 `PAYMENT-1006`；专用密钥托管、版本化轮换、吊销和生产审计仍待完成。

本批已补齐支付回调算法运行时白名单：渠道算法仅精确接受 `HMAC-SHA256 / RSA2`，空值或未知值返回 `PAYMENT-1032` 且不写 nonce 或进入支付状态处理；真实渠道算法参数、密钥规格、证书链和轮换兼容仍待验收。

本批已补齐支付回调时间戳溢出保护：时间窗改用精确减法和正负边界比较，`Long.MIN_VALUE` 等极端输入返回 `PAYMENT-1008` 且不消耗 nonce 或进入支付状态处理；真实渠道时间单位、NTP 漂移和生产延迟窗口仍待验收。

本批已补齐 RSA2 回调异常分类：畸形签名返回 `PAYMENT-1005`，损坏公钥材料返回 `PAYMENT-1033`，均不再误报通用系统异常或产生 nonce/支付副作用；真实证书链、密钥版本、轮换吊销和渠道签名向量仍待验收。

本批已补齐回调时间窗与防重 TTL 配置失败闭合：渠道验签窗口为空或非正返回 `PAYMENT-1034` 且不再回退全局值，nonce TTL 非正阻止服务启动，并直接覆盖合法 Base64 错误长度 RSA 签名；生产配置中心、真实数据库 TTL、多实例重放与 NTP 基线仍待验收。

本批已补齐回调 nonce 全签名有效期覆盖：对称时间窗下强制 `nonce TTL > 2 × notifySignWindowSec`，等号边界返回 `PAYMENT-1034`，默认组合调整为 `300/601` 秒；真实 MySQL 到期端点、多实例竞争、配置热变更和渠道未来时间戳分布仍待验收。

本批已补齐支付回调不可信字段边界：业务字段按数据库列宽和控制字符在验签前拒绝，安全字段在配置查询与密码计算前限制体量，渠道规范化贯穿验签与审计且 JSON 快照完整转义；真实渠道协议、网关请求体/WAF、生产字符集和恶意流量压测仍待验收。

本批已补齐回调 nonce 持久化 SQL 契约：到期时间改用与原 `DATE_ADD` 业务语义等价的 `TIMESTAMPADD`，并以 H2 MySQL 模式验证大小写查询、小写落库、`601` 秒 TTL、唯一键和到期清理；真实 MySQL 执行计划、锁行为、时钟精度、多实例竞争和生产容量仍待验收。

本批已补齐回调 nonce 请求清理与历史清理解耦：回调事务只清理当前过期同名记录，后台默认每五分钟按稳定顺序限量清理 `1000` 条历史记录，并验证过期复用、活跃防重和批次上界；生产 MySQL 执行计划、多实例租约、积压监控、告警和容量校准仍待验收。

本批已修正自动任务租约 owner 隔离：任务中心、告警派发/回执和 nonce 清理使用实例唯一 owner，禁止有效租约同 owner 重入，并以 owner 条件阻止过期旧任务释放新租约；真实多实例故障切换、长任务续租、数据库锁压测和生产监控仍待验收。

本批已补齐自动任务长执行续租：租约获取、续期和释放改为独立短事务，获取成功后按租期三分之一后台续期，只有当前未过期 owner 可延长；任务中心、告警派发/回执和 nonce 清理已统一接入。真实 MySQL 双实例长任务、网络分区、JVM 暂停、租约丢失监控和强 fencing 仍待验收。

本批已补齐支付提交共享数据库限流：接口范围按来源应用、终端和客户端 IP，来源支付方式范围按来源应用和支付方式，通过摘要唯一桶和原子条件更新消除多实例先查后写穿透；权限、令牌、自检与幂等恢复顺序保持失败闭合。真实 MySQL 锁行为、热点容量、可信代理 IP、网关联合限流和生产多实例压测仍待验收。

本批已补齐支付提交客户端 IP 可信边界：HTTP 入口强制覆盖请求体 IP，默认忽略转发头，仅对显式可信直接代理按右向左规则解析数值 IP 链，畸形链路失败闭合回退对端。真实负载均衡拓扑、代理覆写策略、动态地址、CIDR/PROXY protocol 和生产防伪仍待验收。
