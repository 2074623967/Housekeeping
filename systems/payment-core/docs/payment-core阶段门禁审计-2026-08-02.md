## 3. 当前阻断 `test -> master` 的核心问题

### 3.1 范围问题

1. 当前实现仍集中在支付核心域，不是完整支付平台
2. 文档和代码都明确大量平台级模块仍未实现或仅有基础版

### 3.2 可靠性问题

1. 真实渠道接入、验签、公钥轮换、密钥托管仍不是生产级闭环
2. MQ 级可靠投递、失败重试、死信和补偿已补齐“死信补偿任务入账”“可重放任务人工复核 -> 定向重放 -> 任务状态收口”“非法演练报文人工结案”的真实证据，但仍缺更大范围、更多业务样本和更完整发布包层面的整包级证据
3. `settlement-system` 自动串联和整包级异常恢复证据仍不足

### 3.3 发布冻结问题

1. 当前还没有一版基于 `test` 最新状态的正式发布文档
2. 当前还没有一版面向 `master/release` 的完整回滚、发布后验证和风险收口包
3. 当前新增了 `wallet-account` 进入 `test`，说明整包仍在演进中，不适合此时宣告 `master` 冻结

## 4. 当前正确动作

当前建议动作不是发布，而是继续在 `test` 上推进两件事：

1. 以 `payment-core` 为主线，继续补支付交易闭环之外的平台级关键能力
2. 以 `wallet-account` 为代表，继续把下游资金类子系统接到 `payment-core` 的稳定输入输出边界上

## 5. 下一批最高优先级

建议后续优先推进：

1. `payment-core` 的支付请求管理、配置管理、日终处理、任务中心继续正式化
2. 支付成功事件到清分、结算、账务链路的自动化和补偿结案证据继续扩大样本范围
3. 多端支付入口与收银台统一口径复验
4. 对 `wallet-account / wallet-system / accounting-system` 的跨系统输入输出边界继续收口

## 6. 当前判定

截至 2026-08-02：

1. `payment-core` 可以继续作为 `test` 分支的主线系统推进
2. `payment-core` 当前 **不应直接推动 `test -> master`**
3. 当前整包仍应保持“持续迭代中的系统”状态，而不是过早冻结发布
