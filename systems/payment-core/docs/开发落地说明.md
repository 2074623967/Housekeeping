## 3. 工程规范

### 3.1 后端规范

后端统一采用：

`controller -> service -> serviceimpl -> mapper -> mapper.xml -> entity`

规则：

1. 禁止把业务逻辑放进 `mapper`。
2. 业务逻辑统一放在 `serviceimpl`。
3. `entity` 默认使用 Lombok `@Data`。
4. `entity / dto / vo` 禁止手写基础 `getter/setter`，统一由 Lombok 生成；仅允许保留 `getOffset/getLimit` 这类业务派生方法。
5. `entity` 必须保留表语义与字段语义注释。
6. `dto / vo / request / response` 字段必须带中文语义注释，便于研发、测试和 AI 直接理解。
7. `schema.sql` 所有表、字段必须带注释。
8. 每个系统独立数据库。

### 3.2 前端规范

1. `admin-web` 承载后台运营能力。
2. `app-web` 承载用户支付链路。
3. 页面结构、字段、状态标签必须与文档保持一致。
4. 所有关键操作必须有成功/失败反馈。

### 3.3 文档规范

1. 文档必须能直接指导开发和 AI 生成代码。
2. 文档要写清楚已实现、未实现和后续增强边界。
3. 所有系统后续都按同一套模板建设。

### 3.4 Maven 执行规范

后端构建与测试统一通过仓库工具链探测脚本执行，避免把某一台机器的 Maven/JDK 绝对路径写死：

```bash
tools/dev/backend-regression.mjs
```

执行要求：

1. 可通过 `MAVEN_BIN`、`MAVEN_HOME`、`JAVA_HOME` 显式锁定工具链；未配置时由脚本按 PATH、仓库相邻工具链和系统 JDK 探测，回归执行会显式注入可编译 JDK 的 `JAVA_HOME/PATH`。
2. `tools/dev/backend-regression.mjs` 支持 `MAVEN_REPO` 或 `HSP_MAVEN_REPO` 指定仓库，并按相邻仓库、用户仓库和工作区 `.runtime/maven-repository` 回退；每次测试显式传入 `-Dmaven.repo.local`，不依赖隐式 Maven 默认路径。
3. 本地全栈托管使用 `tools/dev/local-stack.sh`，支持 `HSP_MAVEN_BIN`、`HSP_MAVEN_REPO` 和 `HSP_JAVA_HOME` 覆盖；优先使用显式或已存在的可写 Maven 仓库，不可用时回退到工作区 `.runtime/maven-repository`，并由 `doctor` 检查可写性。
4. 不把本地 demo/H2/HTTP 运行结果解释为真实 RabbitMQ、生产 MySQL 或渠道事实。
5. 测试结果需要同步记录到自测与联调记录。

## 5. 当前版本真实边界

本期可以支撑开发与联调，但不应夸大为全部支付中台能力均已完成。

当前本地 V1 已具备相应代码骨架，但仍未达到生产验收的内容：

1. 微信、支付宝、银行等真实渠道协议、签名验签、证书/密钥托管和真实资金到账
2. 配置驱动路由的生产灰度审批、真实网关探活和多实例容量验证
3. 支付查单、退款查单、超时关单和失败事件的本地补偿任务已具备；真实渠道受理、RabbitMQ 投递确认、生产数据库并发和供应商 SLA 仍未验收
4. 退款回调、退款流水、清分、清算、结算、出款、账务和对账已由对应子系统承接；payment-core 只保留正向支付核心域及必要只读/事件边界
5. 可信身份、角色/字段级授权、正式审批签字、通知供应商最终送达、发布后现场核验和稳定观察结论

提交代码前必须同步具备：

1. 接口测试清单

4. 回归测试清单

## 7. 后续系统启动前提

只有在以下条件满足后，才允许并行推进其他系统：

1. `payment-core` 主链路已跑通
2. 前后端已完成一轮联调
3. 核心文档已进入冻结版
4. 数据库、接口、页面结构已稳定
5. 能为账务、清结算系统提供清晰输入输出边界

## 8. 结论

`payment-core` 是整个平台的资金入口域，后续所有账务、清分、结算、退款、对账能力都要以这里的对象和事件为起点。

因此本次落地要求不是“先搭起来”，而是：

1. 结构要正式
2. 数据要清晰
3. 主链路要闭环
4. 文档要可开发
5. 测试要能验收
