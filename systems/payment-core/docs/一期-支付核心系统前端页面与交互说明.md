# 一期-支付核心系统前端页面与交互说明

## 1. 文档定位

本文档用于指导 `payment-core` 冻结版 V1 的前端页面开发与联调，适用对象：

- 产品经理
- 前端开发
- 测试工程师
- 后端开发

本文档口径以当前已落地的 `admin-web`、`app-web`、`h5-web` 与 `pc-web` 为准，重点说明页面结构、字段映射、交互动作和当前版本边界。

## 4. 页面详细设计

### 4.1 工作台

路由：`/dashboard`

页面目标：

1. 让运营、支付负责人进入系统后快速看到支付健康度
2. 识别待处理风险与当天核心指标

页面区块：

1. 页面标题
2. 风险横幅
3. 四张指标卡
4. 今日重点事项
5. 健康度提示
6. 快捷入口区

接口映射：

| 展示项 | 接口字段 |
| --- | --- |
| 卡片标题 | `title` |
| 卡片值 | `value` |
| 角标样式 | `badgeType` |
| 角标文案 | `badgeText` |

交互要求：

1. 首屏自动请求 `/api/dashboard/summary`
2. 同时请求 `/api/payment-metrics/summary`，用于补齐支付总量、成功率、成功金额、待处理支付和已关闭支付等健康指标
3. 卡片区默认展示 4 张，若接口未返回卡片则前端显示兜底卡片，避免首页空白
4. 风险横幅固定展示在指标区上方
5. “今日重点事项”区支持跳转到异常中心、日终处理、服务者结算等处理页
6. “今日健康度”区需明确展示支付成功率、成功支付金额、待处理支付单数、已关闭支付单数
7. 页面底部需提供快捷入口区，直达支付异常中心、支付监控分析、任务中心、收银台会话页面

### 4.2 订单中心

路由：`/orders`

页面目标：

1. 统一查看家政订单支付状态与履约状态
2. 提供发起支付入口
3. 为支付排障提供订单侧入口

查询区字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| 订单号 | 输入框 | 精确查询 |
| 用户 ID | 输入框 | 当前为前端预留字段 |
| 服务品类 | 下拉框 | 已支持后端筛选，按服务品类精确匹配 |
| 订单状态 | 下拉框 | 已支持后端筛选，按订单状态精确匹配 |

列表区字段：

| 展示字段 | 接口字段 |
| --- | --- |
| 订单号 | `orderNo` |
| 账单号 | `billNo` |
| 用户 | `customerName` |
| 服务品类 | `serviceType` |
| 服务者 | `workerName` |
| 订单金额 | `orderAmount` |
| 已付金额 | `paidAmount` |
| 订单状态 | `orderStatus` |
| 履约状态 | `fulfillmentStatus` |
| 最近支付状态 | `latestPaymentStatus` |
| 最近收银台状态 | `latestCashierStatus` |
| 创建时间 | `createdAt` |

操作区：

1. 发起支付
2. 查看支付单
3. 查看账单
4. 查看支付记录
5. 打开当前收银台

交互要求：

1. 点击发起支付后调用 `POST /api/payments/prepay`
2. 成功后展示最新预付单与收银台入口，可直接打开 `app-web` 收银台
3. 订单状态标签使用接口返回的样式字段
4. 若订单已生成最新支付链路，则支持直接跳到支付单详情、支付记录详情和当前收银台
5. 点击“查看账单”时，账单中心应自动回填 `billNo / orderNo` 查询条件

| 客户名称 | 输入框 | 已支持后端筛选，按客户名称模糊匹配 |
| 账单状态 | 下拉框 | 已支持后端筛选，按账单状态精确匹配 |
| 排序字段 | 下拉框 | 已支持创建时间、到期时间、账单应收、待支付金额排序 |
| 排序方向 | 下拉框 | 已支持正序、倒序 |

列表区字段：

| 展示字段 | 接口字段 |
| --- | --- |
| 账单号 | `billNo` |
| 订单号 | `orderNo` |
| 客户名称 | `customerName` |
| 账单应收 | `billAmount` |
| 已支付 | `paidAmount` |
| 待支付 | `unpaidAmount` |
| 账单状态 | `billStatus` |
| 到期时间 | `dueAt` |
| 创建时间 | `createdAt` |

1. 首屏自动请求 `GET /api/bills`，查询条件通过 `billNo`、`orderNo`、`customerName`、`billStatus`、`sortField`、`sortOrder` 下推到服务端，并支持分页查看
2. 当前仅承接交易账单查询，不承接账务会计分录视图
3. 状态标签复用后台统一色值规范
4. 页面需提供账单总数、已支付/已结清数、待支付金额合计、账单应收合计指标卡，并支持“列表 + 右侧账单快照/运营建议”联动

### 4.4 支付流水查询

路由：`/payment-flows`

页面目标：

1. 聚合展示支付主链路中的关键过程流水
2. 支撑运营和测试查看支付尝试、回调、路由、事件收口过程
3. 让支付排障不再依赖单个详情页逐条翻查

查询区字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| 支付单号 | 输入框 | 已支持后端筛选，按支付单号模糊匹配 |
| 订单号 | 输入框 | 已支持后端筛选，按订单号模糊匹配 |
| 流水类型 | 下拉框 | 已支持后端筛选，按流水类型精确匹配 |
| 渠道编码 | 输入框 | 已支持后端筛选，按渠道编码模糊匹配 |
| 终端 | 下拉框 | 已支持 H5、PC、APP、小程序维度筛选 |
| 业务状态 | 下拉框 | 已支持后端筛选，按尝试状态、回调状态、路由结果和事件类型统一筛选 |
| 关键字 | 输入框 | 已支持按摘要、请求报文、响应报文检索 |
| 排序字段 | 下拉框 | 已支持创建时间、重试次数、流水类型排序 |
| 排序方向 | 下拉框 | 已支持正序、倒序 |

列表区字段：

| 展示字段 | 接口字段 |
| --- | --- |
| 流水编号 | `flowNo` |
| 支付单号 | `paymentOrderId` |
| 订单号 | `orderNo` |
| 预付单号 | `prepayOrderNo` |
| 流水类型 | `flowType` |
| 渠道编码 | `channelCode` |
| 业务状态 | `businessStatus` |
| 流水摘要 | `summary` |
| 创建时间 | `createdAt` |
| 操作 | 展开详情、查看支付单详情、查看支付请求、查看处理日志 |

交互要求：

1. 首屏自动请求 `GET /api/payment-flows`，查询条件通过 `paymentOrderId`、`orderNo`、`flowType`、`channelCode`、`terminal`、`businessStatus`、`keyword`、`sortField`、`sortOrder` 下推到服务端，并支持分页查看
2. 当前统一聚合支付尝试、渠道回调、路由记录、业务事件四类流水
3. 点击“展开详情”时，需要展示终端、客户端 IP、幂等键、回调类型、路由规则、下游系统、事件主题、发布状态、重试次数以及原始请求/响应报文
4. 展开详情后，支持直接联查支付单详情、支付请求管理和支付处理日志，减少运营和研发跨页排障成本
5. 状态标签与类型标签复用后台统一样式规范
6. 页面需提供流水总数、成功状态数、待关注状态数、流水类型数指标卡，并支持“列表 + 右侧链路快照/排障建议”联动

### 4.5 支付路由执行结果

路由：`/payment-routes`

页面目标：

1. 独立查看每笔支付命中的路由规则、落地渠道和命中结果
2. 将支付路由排障从支付流水页中拆成可独立使用的运营后台页
3. 支撑运营、研发、测试联合排查路由误命中、渠道落错和兜底选择问题

查询区字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| 支付单号 | 输入框 | 已支持后端筛选 |
| 订单号 | 输入框 | 已支持后端筛选 |
| 路由规则 | 输入框 | 已支持后端筛选，按规则关键字模糊匹配 |
| 渠道编码 | 输入框 | 已支持后端筛选 |
| 支付方式 | 下拉框 | 已支持微信、支付宝、银行转账维度筛选 |
| 终端 | 下拉框 | 已支持 H5、PC、APP、小程序维度筛选 |
| 路由结果 | 下拉框 | 已支持后端筛选 |
| 排序字段 | 下拉框 | 已支持创建时间、渠道编码、路由结果排序 |
| 排序方向 | 下拉框 | 已支持正序、倒序 |

列表区字段：

| 展示字段 | 接口字段 |
| --- | --- |
| 路由记录号 | `routeNo` |
| 支付单号 | `paymentOrderId` |
| 订单号 | `orderNo` |
| 预付单号 | `prepayOrderNo` |
| 支付方式 | `paymentMethod` |
| 命中渠道 | `channelCode` |
| 路由结果 | `routeResult` |
| 路由规则 | `routeRule` |
| 终端 | `terminal` |
| 创建时间 | `createdAt` |

交互要求：

1. 首屏自动请求 `GET /api/payment-routes`，查询条件通过 `paymentOrderId`、`orderNo`、`routeRule`、`channelCode`、`paymentMethod`、`terminal`、`routeResult`、`sortField`、`sortOrder` 下推到服务端，并支持分页查看
2. 点击“展开详情”时，需要展示客户名称、支付金额、终端、客户端 IP、幂等键和最近支付请求/响应报文
3. 展开详情后，支持联查支付单详情、路由流水、支付请求和支付渠道与路由配置页
4. 当前页面定位为支付路由独立排障台，V1.4 已展示短窗健康熔断口径和默认渠道加权命中，并在页头提供“导出路由”，按当前九项筛选与排序条件下载全量脱敏 CSV；配置中心同步展示渠道权重及括号、`AND / OR / NOT`、`IN`、比较运算语法，后续继续补规则编辑校验和真实网关探活信息
5. 页面需提供路由记录总数、命中成功数、需关注结果数、命中渠道数指标卡，并支持“列表 + 右侧路由快照/排障建议”联动
6. 导出不携带当前页码和每页条数；生产环境仍需补下载权限、审批、水印与审计，不以浏览器成功发起下载代表生产治理闭环

7. 异人声明批准成功后才刷新运行态；批准会把自检状态重置为 WARN。点击“执行自检”调用 `POST /api/payment-config/control-policies/self-check`，基于渠道与网关配置重算准入状态。
8. 点击“版本历史”调用 `GET /api/payment-config/control-policies/{sourceAppId}/versions` 展示不可变快照；历史列表只展示令牌是否配置。选择非最新版本回滚时调用 `POST /api/payment-config/control-policies/{sourceAppId}/rollback`，只提交候选，不直接刷新运行态。

补充说明：

1. 当前 V1.7 已治理来源应用控制策略新增、编辑、启停和历史回滚，后端会基于来源应用、支付方式、渠道、商户、令牌、自检状态和两级限流进行提交前校验。
2. 申请人与复核人仍是 `SELF_DECLARED`，不代表可信身份或正式审批；令牌仍保存在现有配置表和复核快照中，后续需接入专用密钥托管与轮换。
3. 自动/人工自检回写属于系统运行状态，不进入配置复核；后续继续补可信权限、令牌专用托管与轮换和多实例分布式限流。

2. 新增和编辑必须填写申请人声明与申请原因，成功后只刷新复核列表；不得把候选提交提示为已新增或已更新运行态。
3. 运行态按钮展示“申请启用/申请停用”，使用独立的启停申请人和原因；提交后运行态列表保持不变。
4. 页面进入时查询 `/issue-duty-rosters/reviews`，并覆盖加载、空、失败、待处理和已处理状态；列表展示完整候选摘要、基线、申请与复核记录。
5. 批准与驳回均要求复核人声明和意见；批准成功后刷新运行态，驳回只刷新复核列表。
6. 页面明确 `SELF_DECLARED` 只表示人员声明，不代表可信认证、授权审批、正式签字、真实排班中心或通知送达。

### 4.21 支付配置中心 - 告警通知供应商复核

路由：`/payment-config`

1. 页面展示供应商运行配置、完整新增/编辑候选表单和复核列表，覆盖通道、端点、模板、路由、优先级、重试、限流和状态。
2. 新增和编辑必须填写申请人声明与原因；成功后只刷新复核列表。运行态按钮显示“申请启用/申请停用”，并使用独立启停申请人和原因。
3. 页面进入时加载 `/alert-providers/reviews`，覆盖加载、空、失败、待处理和已处理状态；复核项展示候选摘要、基线、申请与处理记录。
4. 批准和驳回必须填写复核人声明与意见。批准后刷新运行态，驳回只刷新复核列表；后端拒绝同人声明与陈旧基线。
5. 页面版本为 V1.23，`SELF_DECLARED` 不代表可信身份、正式审批或真实供应商已配置和送达。

### 4.22 支付事件与死信任务敏感信息展示约束

1. 支付事件列表、事件 CSV 和重发后的刷新结果只消费服务端脱敏后的 `eventPayload`，页面不得提供原始载荷恢复或绕过脱敏的下载入口。
2. 死信任务列表及待重放、人工结案、重放动作响应只展示脱敏后的载荷与消息头快照；授权头、令牌、密钥、签名、私钥和 Cookie 等凭据显示为 `[REDACTED]`。
3. 畸形载荷或消息头统一展示 `[REDACTED]`；重放失败只展示固定处置摘要，不展示消息代理异常原文。
4. 服务端实际重放仍使用持久化原始载荷，前端展示值不是重放输入；当前页面不代表已具备生产 IAM、字段级授权、原文访问审计或隐私验收。

### 4.23 未知系统异常展示约束

1. 未预期系统异常统一展示服务端 `PAYMENT-500 / system error`，同时保留 `requestId` 作为反馈和排障关联号，不展示底层异常原文。
2. 明确业务异常继续展示业务错误码与业务提示，参数校验错误继续展示可操作校验信息，不因系统异常收敛而丢失正常纠错能力。
3. 页面不得从响应对象、控制台日志或兜底文案拼接异常堆栈、数据库地址、内部端点或凭据；当前 `requestId` 只形成关联基线，不代表集中日志 IAM 和生产故障观测已完成。

### 4.24 请求追踪号展示约束

1. 前端将 `requestId` 视为不透明字符串，只负责展示、复制和反馈，不按固定长度拆分，也不从时间前缀推导业务状态。
2. 新请求号格式为 `REQ + 17 位毫秒时间 + 8 位十六进制后缀`；所有成功和失败响应继续使用同一字段，不改变现有错误提示组件。
3. 页面不得自行生成或覆盖服务端请求号；当前格式升级只改善单服务关联可靠性，不代表浏览器、网关和跨服务 trace 已贯通。

### 4.25 SQL 与绑定参数日志展示约束

1. 管理端和各收银台不得依赖 MyBatis SQL 文本或绑定参数日志展示业务状态、错误详情或敏感配置；应用默认使用 `NoLoggingImpl` 阻断此类普通日志输出。
2. 页面排障继续使用业务状态、错误码和 `requestId`，不得以临时提高根日志级别作为恢复支付参数明文的手段。
3. 当前约束只定义前后端诊断边界，不代表生产指标、链路追踪、慢查询、日志权限与隐私治理已经完成。

### 4.26 主动查单失败快照展示约束

1. 支付详情轨迹中的主动查单失败响应快照只展示受控错误码和固定 `channel query failed` 文案，不展示下游端点、数据库地址、凭据或异常原文。
2. 页面动作仍消费接口返回的业务错误码和可操作提示；持久化快照最小化不改变查单失败反馈、失败状态或后续自动补偿展示。
3. 当前约束不提供历史快照清理、敏感原文恢复、字段级授权或生产真实渠道故障验收结论。

### 4.27 查询参数与服务端 SQL 绑定约束

1. 前端筛选、排序、页码和每页条数继续按接口字段传递，不拼接或提交 SQL 片段，也不依赖数据库列名作为页面契约。
2. 服务端 Mapper 使用参数绑定和固定排序分支，禁止 `${...}` 原始替换；无效排序值应落入服务端默认分支，而不是成为动态 SQL。
3. 该约束不代表页面身份授权、数据库账号最小权限、生产 SQL 审计或渗透测试已经完成。

### 4.28 三端收银台接入令牌传递约束

1. APP、H5、PC 业务入口在创建预付单前，将当前终端演示接入令牌按 `hsp.accessToken.{sourceAppId}` 写入 `sessionStorage`；路由 query 只保留业务场景等非敏感上下文。
2. 收银台提交从当前来源应用的会话键读取令牌，跳转支付结果页和返回收银台均不得把令牌重新放入 URL。
3. 兼容旧链接时，收银台和结果页先迁移 `accessToken`，再以 `router.replace` 清理当前地址；会话存储不可用时禁止从业务入口继续发起预付单，不降级为 URL 明文。
4. `sessionStorage` 只能降低历史记录、链接复制和 Referer 扩散，不抵御同源 XSS；当前演示令牌仍会进入前端构建产物，生产必须由可信登录、服务端会话或短期凭据替换。

### 4.29 运营列表分页边界

1. 后台列表页仍从第 1 页开始请求，每页最多 100 条；服务端将异常负数和超大页码统一收敛到 `1..1000`。
2. 页面应以接口返回的 `pageNo / pageSize / total` 为准更新分页状态，不假设调用方提交的极端页码会原样返回。
3. 当前最大 offset 为 `99,900`，用于避免整数溢出和无界深分页；大量历史数据查询仍应采用更窄筛选，后续再评估游标分页与归档查询。

## 5. 联调要求

1. 所有表格页必须保证字段顺序与文档一致。
2. 所有状态标签必须通过 `statusType` 映射样式。
3. 发起支付、提交支付、模拟回调、关闭支付的交互结果必须有成功/失败反馈。
4. `admin-web` 与 `app-web` 必须能完成一次闭环串联。
5. `h5-web` 必须与 `app-web` 保持同一套交易逻辑和接口口径。
6. `pc-web` 必须与 `app-web / h5-web` 保持同一套交易逻辑和接口口径，同时保留桌面端独立文案与交互提示。
7. 支付配置中心当前已补齐渠道、路由规则、协议、返回码、网关和来源应用控制策略治理；渠道与网关四类操作均具备 V1.4 唯一待办、不可变版本、受控回滚和双基线复验，渠道额外执行敏感字段脱敏；控制策略四类操作具备 V1.7 唯一待办、不可变版本、受控回滚、令牌脱敏和批准后自检失效；路由规则支持四类候选复核、版本、回滚、冲突检测和稳定百分比桶 V1.9；协议支持四类候选复核和不可变版本 V1.11；返回码 CSV 导入与单条启停分别具备 V1.4/V1.5 复核。上述提交和驳回均不刷新运行态，人员身份仅为 `SELF_DECLARED`。

## 8. 工作台与支付健康指标接口约束

### 8.1 工作台

路由：`/dashboard`

首屏必须调用 `GET /api/dashboard/summary`，用于加载工作台卡片。页面不得把前端 fallback 卡片当成真实业务统计，接口失败时只能展示错误提示和刷新入口。

### 8.2 支付健康指标

工作台同时调用 `GET /api/payment-metrics/summary`，用于展示支付单总量、成功单量、成功率、成功金额、处理中数量和已关闭数量。

指标字段口径：

| 字段 | 含义 | 使用约束 |
| --- | --- | --- |
| `totalCount` | 支付单总数 | 由支付核心指标服务返回，不以前端当前页数据计算 |
| `successCount` | 支付成功单数 | 与 `successRate` 使用同一统计范围 |
| `successRate` | 支付成功率 | 直接展示服务端格式化结果，避免前端重复计算产生口径差异 |
| `successAmount` | 成功支付金额 | 按支付核心金额口径展示 |
| `pendingCount` | 支付处理中单数 | 用于待收口和回调排查提示 |
| `closedCount` | 已关闭支付单数 | 用于超时关单和日终复盘提示 |

接口门禁要求：

1. 控制器只负责调用服务并包装统一响应，不在控制器内计算指标。
2. 控制器测试必须验证服务调用和响应数据透传。
3. 前端必须覆盖加载中、接口失败、成功数据和刷新状态。

## 9. 告警派发失败信息展示边界

1. 任务中心和异常中心只展示固定传输异常摘要与失败分类，不展示连接地址、签名异常、响应解析异常或其他底层异常原文。
2. 新增失败回执快照仅保留 `HTTP_TRANSPORT_ERROR:[REDACTED]` 或 `LOCAL_FAILURE:<分类码>:[REDACTED]`；前端不得把遮蔽字段解释为供应商真实响应。
3. 正常供应商 HTTP 回执仍按后端脱敏结果展示；敏感原文受控查看、可信身份和访问审计不属于当前前端基线已完成能力。

## 10. 告警供应商正常回执展示边界

1. 正常供应商回执在写入普通告警日志前已递归脱敏，页面只消费该脱敏事实，不请求或缓存原始手机号、姓名、银行卡号或凭据字段。
2. 回执号、投递状态和受控失败码继续独立展示，不要求前端从 `providerReceiptSnapshot` 反向解析业务状态。
3. 畸形或标量回执显示 `[REDACTED]`；页面不得将其解释为供应商成功、失败或真实原文已归档。

## 11. 告警供应商结果展示容量

1. 后端在落库前已限制回执号、投递状态、投递说明、渲染内容和回执快照长度，页面按服务端返回值展示，不尝试恢复被截断内容。
2. 投递结论使用独立状态字段，不能根据说明或快照是否完整推导成功；超长供应商失败结果仍应显示失败并允许查看备用通道结果。
3. 如需完整原始凭证，应进入独立受控设施，不在普通运营页面扩展原文展示入口。

## 12. 告警供应商诊断码展示

1. 页面只展示后端判定为安全标识符的供应商状态码、失败码和成功码差异值；自由文本或含换行值显示 `[REDACTED]`。
2. 派发结论始终读取独立的标准化状态字段，不根据诊断码是否被遮蔽重新判断。
3. 普通页面不提供供应商异常原文恢复入口；生产取证需由独立受控设施承接。

## 13. 超时关单批次结果展示

1. 任务中心执行超时关单后，按服务端结果展示处理、成功和失败数量，不再把已扫描数量等同于成功数量。
2. 存在失败时，任务日志显示告警状态、复跑建议和最多 3 个失败支付单号；页面不得据此宣称真实渠道已经完成关闭。
3. 未显示的失败单号不代表不存在更多失败，运营人员应以任务计数和支付列表复核为准；失败支付单可在后续调度轮次再次处理。

## 14. 失败退款重试批次结果展示

1. 任务中心执行失败退款重试后，展示扫描数量、成功提交渠道数量和失败数量，不把单纯状态变更描述为退款成功。
2. 存在失败时，任务日志展示告警级别、处置建议和最多 3 个失败退款单号；完整失败规模以 `failCount` 为准。
3. “成功提交渠道”只表示本地模拟或渠道受理动作完成，不表示用户资金已经到账；真实到账仍需退款回调或渠道查单事实确认。

## 15. 失败事件重发批次结果展示

1. 人工执行失败事件重发时处理全部失败事件，自动调度只处理已到重试时间的失败事件；页面统一展示本轮处理、成功和失败数量。
2. 存在失败时，任务日志展示告警级别、重发表处置建议和最多 3 个失败事件号；未展示的事件号不代表没有更多失败，完整规模以 `failCount` 为准。
3. “成功重发”只表示当前投递调用完成，不表示所有下游业务均已完成处理；页面不得把本地事务提交或任务接口成功解释为端到端交付成功。

## 16. 告警派发与回执隔离结果展示

1. 告警派发任务继续展示完全成功、部分失败和全部失败数量；存在未完全送达时，摘要最多列出 3 个告警号，完整规模以 `warningCount / failCount` 为准。
2. 回执回查任务展示处理、确认送达和回写失败数量，并在失败时最多列出 3 个供应商告警号；单条失败不表示后续告警停止处理。
3. 页面不得把“供应商已受理”解释为最终送达，也不得把本地事务回滚解释为供应商已撤销通知；重复通知排查应使用稳定 `alertNo` 关联供应商记录。

## 17. 支付业务编号展示约束

1. 支付单、预付单、账单、路由、支付尝试、事件和通知编号仍保留原业务前缀，但长度因随机后缀增加；页面不得按旧固定长度截取或解析时间。
2. 搜索、详情跳转、复制和 CSV 展示必须把业务编号作为完整不透明字符串传递，不能移除后缀或用前端重新生成编号。
3. 编号随机后缀仅用于降低碰撞风险，不代表编号含可信身份、顺序或安全凭据；页面不得据此推导业务状态和权限。

## 18. SLA 巡检部分失败展示

1. 异常 SLA 巡检结果同时展示发现数量、生成告警数量和失败数量，不再把任务接口返回成功等同于所有候选均已生成 outbox。
2. 存在失败时，摘要最多列出 3 个异常号或来源告警号；完整失败规模以 `failCount` 为准，运营人员应进入异常中心复核并按建议复跑。
3. “生成告警”只表示站内 outbox 已落库，不表示外部通知已送达；页面不得提前展示为短信、邮件或 IM 接收成功。

## 19. SLA 巡检并发重复展示

1. 数据库幂等键命中的并发重复候选进入 `warningCount`，任务摘要显示“并发重复跳过”，不展示为生成成功或系统失败。
2. `processedCount` 仍沿用逾期存量与升级候选口径，页面不得要求处理数必须等于成功数、告警数与失败数之和；并发期间候选快照可能包含已由另一请求落库的项目。
3. 初次告警确认后仍未收口时允许下一轮重新生成；升级告警按来源告警号只生成一次。页面应以告警日志事实为准，不从任务计数推断 exactly-once 或外部送达。

## 20. 渠道交易号展示约束

1. `channelTransactionNo` 作为渠道返回的不透明字符串完整展示、复制和传递，页面不得按旧版纯毫秒格式截取、排序或解析时间。
2. 本地模拟渠道当前使用业务前缀、毫秒时间与完整 UUID 随机段；前端不得依赖该格式，因为真实微信、支付宝和银行渠道会返回各自协议定义的流水号。
3. 页面不得把渠道交易号存在解释为支付成功，也不得使用它替代平台支付单号或提交幂等键；最终状态仍以可信回调、主动查单和支付状态机为准。
