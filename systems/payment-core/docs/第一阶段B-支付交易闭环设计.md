### 6.1 主动查单收口设计

1. 渠道选择沿用既有 `PaymentChannelQueryAdapter` 链：启用时由高优先级 `GatewayAccessPaymentChannelQueryAdapter` 请求外部网关，未启用时回落到原有渠道模拟适配器。
2. 渠道结果作为独立 `PaymentChannelQueryResultDTO` 返回业务层，避免适配器直接修改支付核心聚合状态。
3. 非成功结果只沉淀查询事实，不把渠道失败、处理中或未知状态直接映射为内部记账动作。
4. 成功结果先通过 `status NOT IN ('SUCCESS', 'CLOSED')` 的条件更新抢占唯一收口权，再完成支付尝试、预付单、订单、账单和事件联动，保证重复及并发查单不重复记账。
5. 外部查询与内部成功收口均采用失败即报错策略；启用真实网关后不会在调用失败时静默回退到模拟结果。
6. 当前完成的是支付核心到统一网关的生产化接入契约。真实渠道签名、证书、商户凭证和渠道专有报文仍归 `gateway-access` 负责，需以真实联调证据验收。
7. 真实网关查单可启用数据库共享固定窗口限流。限流服务使用独立 `REQUIRES_NEW` 事务，通过渠道唯一桶和条件 `UPDATE` 原子占用配额并先行提交，再由外层流程调用 HTTP，避免在外部网络等待期间持有桶行锁。配额耗尽作为独立业务拒绝返回，不写入渠道失败事实和自动退避历史。

### 6.2 待回调自动查单补偿设计

1. 自动补偿只选择 `WAIT_CALLBACK`、预付单尚未过期且达到首次等待阈值的支付单，避免对新建支付单和已过期支付单发起无效查询。
2. 自动任务根据“已查单 / 查单失败”历史次数按 `基础间隔 × 退避系数^(历史次数-1)` 计算下一次查询间隔，并受最大间隔封顶；候选集先按渠道内创建时间排序和每渠道配额截断，再应用全局批次上限，避免单一渠道占满整轮任务。
3. 自动调度要求 `payment.channel-query.compensation.enabled` 与 `payment.channel-query.gateway-access.enabled` 同时开启。任一开关关闭时不发起自动查询，避免在模拟适配器环境中制造虚假补偿事实。
4. 人工补跑与自动调度复用同一查询执行器，但候选口径分离：人工补跑绕过自动退避窗口以支持立即复核，自动调度额外使用 `PAYMENT_PENDING_QUERY` 多实例租约并只选择已到期候选。
5. 每笔查询通过 `PaymentService.query` 独立执行，单笔运行异常只计入失败摘要，不阻断同批其他支付单；成功、仍处理中和查询失败分别计数并写入任务日志。
6. 任务日志最多记录三个失败支付单号，查询失败达到三笔记为 `P1`，存在失败或仍处理中记为 `P2`，全部成功收口或没有候选记为 `P3`。
7. 当前已完成指数退避、最大间隔封顶、单轮渠道配额、积压/到期数量展示，以及基于共享数据库的跨实例固定时间窗口限流基础版。
8. 任务中心直接从查询事实日志聚合最近 `1-168` 小时的总量、失败量、失败率与小时趋势，并以可配置失败笔数和“最小样本量 + 失败率”双阈值生成 P1/P2/P3 告警。限流拒绝通过独立日志表记录支付单、渠道和当时配额，按同一回看窗口统计并使用独立次数阈值告警，不污染真实渠道质量口径。
9. `PAYMENT_QUERY_MONITOR_ALERT` 按固定周期重新评估上述阈值，人工与自动入口共用租约；命中后写入 `IN_APP_OUTBOX`，同类未确认告警按可配置冷却窗口去重，再复用现有 IM、SMS、EMAIL 派发、重试和供应商回执链路。该设计不等同于真实外部渠道已经送达，生产 MySQL 压测、通知网关配置和真实渠道运行态验证仍属于后续增强项。
10. outbox 自动派发由独立开关控制，默认关闭；启用后调度器按固定间隔调用现有 `PAYMENT_ISSUE_ALERT_DISPATCH` 自动入口，继续使用任务租约和同一派发状态机。该开关只负责调度，不放宽供应商配置、重试、防重放、回执或人工确认约束。
11. 任务中心分别统计来源 outbox 待派发、其中派发异常和供应商已受理待回查数量，并计算两类积压中最老记录的等待分钟数。来源 outbox 仅统计待确认的已生成、部分失败和派发失败记录；待回查仅统计具备 `source_alert_no`、供应商状态为 `ACCEPTED` 且待确认的外发记录，避免把已确认或已送达记录误计入积压。
12. 派发与回执积压采用“数量 + 老化时长”双阈值：存在派发异常，或待派发数量/最老等待达到配置阈值时，派发告警升级 P1；待回查数量/最老等待达到配置阈值时，回执告警升级 P1。默认阈值分别为待派发 `10` 条/`15` 分钟、待回查 `10` 条/`30` 分钟，配置值统一限制为至少 `1`；其余非零积压按 P2 跟进，避免单条告警长期滞留却始终只判 P2。

### 6.3 渠道短窗健康路由设计

1. 路由健康信号复用 `t_payment_notify_log` 中 `已查单 / 查单失败` 事实，按配置回看窗口和原始渠道编码聚合，再按既有 `wx / alipay / bank` 规范化规则合并，兼容 `wx_jsapi`、`WX_H5` 等历史编码。
2. 熔断条件与主动查单监控使用同一组失败笔数、失败率和最小样本阈值，避免任务中心告警口径与交易路由口径分叉；所有配置值在服务内限制到合法范围。
3. 规则路由的目标渠道不健康时，仅在 fallback 同时满足启用、场景、健康和日限额约束时切换，并以 `_HEALTH_FALLBACK` 后缀记录本次决策原因。
4. 用户显式指定的渠道不健康时返回 `PAYMENT-1010`，不静默跨渠道或跨支付方式；未显式指定渠道时，同支付方式默认路由跳过不健康候选。
5. `HSP_PAYMENT_CHANNEL_ROUTE_HEALTH_ENABLED` 默认关闭，保证未校准生产阈值或未确认 fallback 覆盖前不改变现网路由。路由总览返回开关和实际阈值，管理端直接展示后端配置事实。
6. 当前健康判断来自主动查单结果，不代表 TCP/HTTP 探活、渠道证书状态、配额余量或供应商 SLA 已完成统一评分；这些信号仍属于后续真实网关治理范围。

### 6.4 渠道稳定加权路由设计

1. 加权只作用于“未命中规则、未显式指定渠道”的支付方式默认路由，规则目标与用户指定渠道继续保持强语义，不被流量权重覆盖。
2. 候选池先应用启停、支付方式、场景、短窗健康和单日限额过滤，再排除 `routeWeight <= 0` 的渠道；因此熔断、超限和人工摘流渠道不会占用权重区间。
3. 支付提交使用 `paymentOrderId` 作为稳定路由键，通过 JDK `CRC32` 映射到候选总权重区间。相同支付单和相同候选配置会稳定命中同一渠道，避免重试时随机漂移。
4. 空权重按数据库默认值 `100` 兼容；零权重表示仅退出默认候选池。全部候选权重为零时返回既有 `PAYMENT_ROUTE_UNSUPPORTED`，不静默恢复已摘流渠道。
5. 加权结果以 `PAYMENT_METHOD_WEIGHTED` 规则和“命中权重/总权重”结果说明落库，配置中心展示渠道权重并纳入治理快照导出。
6. 修改权重会改变后续路由区间，不承诺跨配置版本保持命中；真实动态调权、容量反馈和综合健康评分仍属于后续增强范围。

### 6.5 路由规则表达式设计

1. 表达式使用独立递归下降求值器，按 `NOT > AND > OR` 解析并支持嵌套括号，替代按字符串分段的平面判断，避免组合条件优先级含糊。
2. 字符串上下文支持 `= / != / IN`，金额支持完整等值与大小比较；字段限定为支付方式、客户类型、请求渠道、终端、支付场景和金额，未知字段不会被隐式接受。
3. 求值器复用既有渠道、终端和客户类型归一化口径；关键字大小写不敏感，带空格的值可用单引号或双引号包裹。
4. 解析和求值失败统一返回“不命中”，路由服务继续评估下一条已启用规则，再进入显式渠道或默认渠道路径，避免单条坏配置阻断全部支付提交。
5. 配置中心已提供规则候选新增、编辑、提交前语法校验与样例命中模拟；提交时校验规则编码、目标与兜底渠道存在性、渠道冲突和非负优先级，非法表达式不会形成待复核申请。
6. 编辑候选按规则编码绑定原记录，管理端锁定编码字段；校验与模拟复用运行态求值器和上下文归一化规则，但只返回合法性与样例命中结果，不产生路由记录或真实渠道调用。

### 6.6 路由规则版本与回滚设计

1. 复核通过的新增/修改、启停和回滚都向 `t_payment_route_rule_version` 追加包含灰度比例与分桶盐值的完整不可变快照；存量规则首次变更前先补 `BASELINE`，避免只有变更后状态而无法恢复。
2. 版本号按规则独立递增，更新、启停和回滚先通过 `SELECT ... FOR UPDATE` 锁定当前规则行，再读取最大版本号并写入快照，降低同一规则并发变更产生版本冲突的风险。
3. 回滚申请读取指定历史快照，重新执行当前表达式与渠道有效性校验，并把完整候选及 `sourceVersionNo` 写入复核表；异人复核通过后才恢复主配置并追加 `REVIEW_ROLLBACK` 版本，历史记录始终只增不改。
4. 版本记录只保存变更类型、来源版本、变更原因和配置事实。当前系统没有可靠登录身份与审批工作流，因此不增加伪操作人、伪审批人或伪发布结论字段。
5. 本能力提供轻量审计和恢复；新增、修改、启停和回滚均接入自声明 maker-checker，但不等同于正式审批、灰度发布或真实渠道运行态验证。

### 6.7 路由规则冲突检测设计

1. 检测入口读取当前全部规则后仅保留 `ENABLED` 且灰度比例大于 `0` 的规则，先逐条识别非法表达式，再对合法规则两两比较；该过程只读，不修改运行态路由、规则版本或启停状态。
2. 表达式通过去除无意义空白并统一关键字大小写形成规范串。只有规范串完全相同的规则才进入确定性重复、目标分歧和遮蔽判断，避免将静态扫描包装成任意布尔表达式的完整 SAT 或可满足性证明。
3. 场景沿用运行语义，以 `/` 分隔为 OR 集合，并归一化 `mobile / mobile_web / H5`、`web / pc_web / PC`、`app_native / APP` 三组终端别名；空场景表示全部场景。集合求交用于定位冲突范围，包含关系用于区分全部遮蔽和部分遮蔽。
4. 同表达式、同优先级、同目标与兜底渠道按场景范围返回 `DUPLICATE_RULE` 或 `OVERLAPPING_DUPLICATE`；渠道不同则返回阻断级 `ROUTE_DIVERGENCE`，提示运行结果依赖数据库记录顺序。
5. 同表达式、不同优先级时，只有 100% 的高优先级规则且场景完全包含才判定 `SHADOWED_RULE`；部分灰度高优先级规则判为 `PARTIAL_SHADOW`，避免把桶外仍可命中的低优先级规则误报为永不生效。
6. 场景有交集、优先级相同但表达式不同，只返回 `PRIORITY_COLLISION / REVIEW` 待人工判断表达式是否互斥。独立检测入口只用于治理排查；复核发布会阻断涉及候选的 `BLOCKER`，但仍不等同正式审批、灰度发布或真实渠道验证。

### 6.8 路由规则 maker-checker 复核设计

1. 新增、修改、启停与回滚统一提交完整候选快照到 `t_payment_route_rule_review`，不直接修改运行表；旧的直接运行态写入路径关闭，避免绕过复核。
2. 修改申请保存提交时的 `baseVersionNo`。复核通过前锁定申请并复查当前最新版本，基线变化时拒绝发布，要求重新提交。
3. 申请人、复核人和意见必填，系统强制申请人与复核人声明不同；二者都只是 `SELF_DECLARED`，当前没有可信认证、授权、电子签名或不可抵赖能力。
4. 通过前重新校验表达式、目标与兜底渠道、优先级，并将候选替换进当前规则集合执行冲突检测；涉及候选的 `INVALID_EXPRESSION` 或 `ROUTE_DIVERGENCE / BLOCKER` 会阻断发布。
5. 启停申请从当前规则复制候选并只改变状态；回滚申请从目标历史版本复制候选并记录 `sourceVersionNo`。重复状态、失效版本和同规则重复待复核申请在提交阶段拒绝。
6. 通过后在同一事务内写运行规则，按操作追加 `REVIEW_RELEASE / REVIEW_STATUS_CHANGE / REVIEW_ROLLBACK` 快照并完成申请；驳回只完成申请。申请状态条件更新用于阻止并发重复处理。
7. 代码内稳定百分比桶和四类变更复核已实现，可信身份、生产审批、真实渠道验证和发布后观察仍未实现。

### 6.9 路由规则稳定百分比灰度设计

1. 场景和表达式命中后，以 `ruleCode:rolloutSalt:paymentOrderId` 的 UTF-8 字节计算 JDK `CRC32`，再对 `100` 取模形成 `0..99` 的稳定桶。
2. `bucket < rolloutPercentage` 才进入当前规则目标与故障兜底逻辑；桶外继续评估后续规则，严格区分“未纳入灰度”与“目标渠道不可用”。
3. `rolloutPercentage=0` 表示保留配置但不承接流量，`100` 表示全量。部分灰度缺 `paymentOrderId` 时跳过规则，避免用随机值制造重试漂移。
4. 灰度比例和盐值进入运行配置、maker-checker 候选、版本快照、回滚、冲突检测、治理导出和管理端。盐值变化会重排桶位，必须按高风险变更复核。
5. 当前冲突扫描不能根据不同盐值或百分比证明两条规则的桶集合互斥；同优先级冲突仍按可能重叠处理，0% 规则除外。
6. 本设计仅提供代码内确定性分流能力，不形成生产灰度审批、渠道可用性验证、发布监控或稳定观察结论。

### 6.10 支付协议不可变版本与 maker-checker 设计

1. `t_payment_protocol_config` 继续保存当前运行态，`t_payment_protocol_version` 按协议编码保存只增不改的完整快照；模板信息、签约要素、电子签章服务商、适用范围、正文、状态和优先级必须一起版本化，避免只追踪模板版本字符串而无法还原真实条款。
2. 新增、编辑、启停和回滚统一把完整候选写入 `t_payment_protocol_review`，操作类型为 `CREATE / UPDATE / STATUS_CHANGE / ROLLBACK`；提交与驳回不修改运行表，也不追加运行版本。
3. 同一协议以 `pending_protocol_code` 唯一占位限制最多一条待复核申请。新建候选基线为空；存量候选提交时锁定协议、按需补 `BASELINE` 并保存 `baseVersionNo`；回滚候选额外保存 `sourceVersionNo`。

5. 日志模型保存的是处理发生当时的不可变摘要，后续状态变更通过新的回调或事件日志表达，不覆盖历史记录。支付提交摘要不复制客户端 IP、设备、手机号、幂等键和请求报文，通知摘要不复制渠道结果，事件摘要不复制事件载荷；原始内容仍只保留在对应来源事实中。
6. 上述数据最小化减少了通用查询和 CSV 导出中的敏感数据扩散，但不等于支付请求详情字段分级授权、外部日志检索平台或生产归档分区已经完成。

### 6.20 支付排障出参敏感数据最小化

1. 支付请求、支付流水和路由执行仍从原始事实表读取完整数据，服务层在三类列表及支付请求、支付流水 CSV 出参边界复制 DTO 后脱敏，不反向改写 Mapper 返回对象或数据库事实。
2. 统一脱敏组件使用 Jackson 递归遍历对象和数组，字段名大小写无关；覆盖客户端 IP、设备标识、付款手机号、通用电话、银行卡号、客户名称、幂等键和内嵌原始请求/响应字段。
3. 敏感字段为非字符串值时以固定掩码返回；报文不是合法 JSON 时整体返回 `[REDACTED]`，按失败闭合原则避免正则漏脱敏。
4. 支付流水摘要不再拼接请求、回调或事件原始载荷，只保留方式/状态、类型/状态或事件/发布状态；原始事实仍留在来源表供受控排障。
5. 本能力只降低列表、详情面板和导出的字段扩散风险，不代表统一身份认证、角色授权、字段级授权、下载水印或生产审计已经完成。

### 6.21 支付路由执行结果导出

1. 新增 `GET /api/payment-routes/export`，复用路由列表的支付单、订单、规则、渠道、支付方式、终端、路由结果和排序条件，直接查询全部匹配记录，不通过分页循环拼接。
2. 导出 Mapper 与列表共用 From、Where 和排序规则，列覆盖路由标识、关联交易、客户与金额、规则与结果、运营配置快照版本、终端、请求上下文和时间。
3. Service 在 CSV 编码前复用统一敏感数据脱敏器，客户名称、客户端 IP、幂等键和请求/响应报文与页面列表保持一致；数据库原始事实不被修改。
4. 管理端 V1.4 在页头提供“导出路由”，使用当前筛选条件生成下载 URL；导出不带当前页码和每页条数。
5. 当前仅形成 UTF-8 BOM 文件下载能力，不代表导出权限、审批、水印、下载审计或生产大数据量性能验收完成。

### 6.22 支付主对象出参敏感数据最小化

1. 支付单列表和 CSV 在 Service 出参边界复制 Mapper DTO，并脱敏客户名称；筛选仍使用数据库原始值，避免脱敏展示影响精确检索口径。
2. 支付详情统一在轨迹补齐后复制 DTO，脱敏客户名称、最近客户端 IP、幂等键及请求/响应 JSON；非法或标量 JSON 继续按统一规则失败闭合为 `[REDACTED]`。
3. `detail / callback / query / close` 四类返回支付详情的入口共享同一出参转换，避免只读详情已脱敏而动作响应再次暴露原始字段。
4. 回调验签、主动查单、支付状态收口、账单结清和关单仍使用 Mapper 原始事实；脱敏只发生在最终返回副本，不反向污染事务内业务判断或数据库对象。
5. 本能力是未接入可信身份前的数据最小化基线，不等于按角色查看原文、字段级授权、导出审批、水印、访问审计或生产隐私验收完成。

### 6.23 支付运营查询出参敏感数据最小化

1. 订单、账单、收银台会话、退款、服务者结算和支付异常列表统一在 Service 出参边界复制 Mapper DTO，再脱敏客户或服务者姓名；已有 CSV 使用同一转换结果。
2. 退款详情在装配操作日志时生成独立返回副本并脱敏客户姓名，Mapper 详情对象不写回操作日志或脱敏值。
3. 订单客户与服务者姓名同时最小化；查询条件仍使用调用方原始输入，内部路由判断、退款渠道下发、支付事件和结算事实继续使用原始业务数据。
4. 默认脱敏只降低后台运营展示和下载扩散风险，不替代可信身份、按角色字段授权、敏感原文受控查看、导出审批、水印和访问审计。

### 6.24 统一支付记录与退款动作出参最小化

1. 统一支付记录列表复制 Mapper DTO 后，将由客户名称拼接的 `userId / userPaymentChannelId` 转为只保留非敏感前缀的引用值；银行卡号继续沿用 Mapper 固定脱敏值。
2. 支付记录详情在独立副本上脱敏用户引用、最近客户端 IP、幂等键及请求/响应 JSON，再装配路由、回调和事件轨迹；Mapper 详情 DTO 不被补写或覆盖。
3. `apply / approve / success / fail / retry` 五类退款动作只在最终返回时复制并脱敏客户姓名，渠道提交、状态 CAS 更新和操作日志仍使用原始退款事实。
4. 当前默认最小化不提供敏感原文恢复能力，也不替代可信身份、字段级授权、访问审计或生产隐私验收。

### 6.25 异常告警供应商回执出参最小化

1. 异常告警查询、导出和确认动作在 Service 出口复制 `PaymentIssueAlertLogRowDTO`，只对副本中的 `providerReceiptSnapshot` 执行统一载荷脱敏。
2. 对象和数组 JSON 保留非敏感投递诊断字段并递归遮蔽敏感字段；无法可靠解析的任意供应商 HTTP 响应或传输快照失败闭合为 `[REDACTED]`。
3. 原始 DTO 继续用于回执状态判断和来源告警同步，避免脱敏副本影响事务逻辑；数据库结构、告警状态机和供应商派发流程均不改变。
4. 团队接收人和内部渲染告警正文保留运营可用性；生产敏感原文受控查看仍需可信身份、字段级授权、访问审计和隐私验收。

### 6.26 异常告警供应商回执格式归一化

1. `PaymentSensitiveDataMasker` 提供供应商回执专用转换：先识别受控大写来源前缀，再复用通用 JSON 递归脱敏逻辑，避免复制字段规则。
2. `HTTP_RESPONSE:` 后的对象或数组 JSON 保留来源和非敏感诊断字段；任何带前缀非 JSON 正文、JSON 标量或格式异常内容均失败闭合。
3. `PaymentIssueServiceImpl` 的列表、CSV 和确认响应继续共享单一 DTO 副本转换，真实存储格式兼容不会扩散到 Mapper 或通知器职责中。

### 6.27 异常告警故障证据与运营摘要分层

1. 通知器将原始传输异常写入内部 `providerReceiptSnapshot`，`providerDeliveryMessage` 只保留通道、超时配置和固定脱敏标记，实现故障证据与可见摘要分层。
2. 派发服务在持久化前统一清理 `transportError=` 后的内容，覆盖仓库内置通知器、自定义通知器和运行时异常三类入口。
3. 供应商业务状态、HTTP 状态、失败码和主备切换判断保持不变；本轮不改变派发事务、重试、熔断、限流或回执状态机。

### 6.28 支付事件与死信任务展示事实分层

1. 支付事件服务在列表、CSV 和重发刷新出口复制 DTO 后脱敏事件载荷；事件发布与重发仍读取 Mapper 原始事实，展示转换不进入派发路径。
2. 死信服务在列表和处置动作出口复制实体后脱敏载荷及消息头快照；定向重放在复制前读取原始任务，并只使用原始 `payloadSnapshot` 构造消息体。
3. 统一脱敏组件先移除字段名中的连字符和下划线并忽略大小写，再识别授权、令牌、API/访问密钥、密钥、签名、私钥和 Cookie 等凭据字段；无法可靠解析的结构整体失败闭合。
4. 重放失败的数据库可见处置说明固定遮蔽消息代理异常，避免后续列表和动作响应形成异常文本旁路；本轮不改变死信审核、CAS 状态流转、路由或发布确认机制。
5. 该分层只是默认出参最小化，不等于生产 IAM、字段级授权、原文审计、加密和保留期限已经落地。

### 6.29 未知系统异常诊断信息分层

1. 全局异常边界将可预期领域失败、参数校验失败和未知系统失败分层处理；前两类保留可操作提示，未知失败固定为 `PAYMENT-500 / system error`。
2. `ApiResponse` 生成的 `requestId` 同时写入系统错误日志，供调用方反馈与服务端记录关联；日志只保留异常类型，不复制异常消息或堆栈。
3. 不记录未知异常原文会降低当前本地根因细节，但可避免在尚无可信日志权限和敏感内容治理时扩大泄露面；后续受控错误详情能力应独立设计访问授权、加密、审计和保留期限。
4. 本轮不改变领域错误码、控制器契约、业务事务或状态机，也不宣称已经完成生产可观测性和故障演练。

### 6.30 请求追踪号并发安全

1. 请求号生成保留 `REQ` 和毫秒时间前缀，使用不可变 `DateTimeFormatter` 代替共享 `SimpleDateFormat`，避免并发格式化状态污染。
2. 后缀使用 8 位 UUID 十六进制片段代替三位随机数字，扩大同毫秒碰撞空间并适配多实例本地生成，不引入数据库序列或远程 ID 服务依赖。
3. `ApiResponse` 仍是成功和失败请求号的唯一创建边界，未知异常处理器复用响应请求号写最小化日志，避免生成两个无法关联的编号。
4. 该轻量方案适合当前单体支付核心基线；后续全链路追踪应另行处理入口透传、MQ 传播、trace/span、采样、集中检索和访问权限。

### 6.31 MyBatis 诊断日志安全默认值

1. 应用层在 MyBatis 配置边界指定 `NoLoggingImpl`，不把 SQL 语句、查询结果和绑定参数交给普通日志体系；该规则不随 root logger 级别升高而失效。
2. 仓库内手工构造 MyBatis `Configuration` 的 Mapper 集成测试显式复用相同实现，使应用运行与测试执行维持一致的数据最小化边界。
3. 配置契约测试直接读取 `application.yml` 并固定实现类名称，防止重构或环境配置整理时无意恢复默认日志适配器。
4. 禁用 MyBatis 日志会降低 SQL 文本和参数级排障便利性；生产观测应由指标、链路追踪、数据库慢查询或单独授权审计的诊断工具承接，本设计不扩张 `payment-core` 的系统职责。

### 6.32 主动查单失败事实与异常详情分层

1. 主动查单失败仍以 `BusinessException.code`、`QUERY_FAILED` 状态、渠道和支付单标识形成可统计事实，通知响应快照只记录固定失败文案，不承载任意异常详情。
2. 原业务异常继续向控制器异常边界传播，保证调用方获得既有错误码和业务提示；持久化最小化不改变渠道查询适配器、限流、事务 `noRollbackFor` 或补偿退避逻辑。
3. 该分层避免下游端点、数据库地址或凭据经异常包装进入支付轨迹；更详细的生产诊断应由具备授权、加密、审计和保留期限的独立设施承接。
4. 本轮不迁移历史通知日志，不修改表结构、接口字段或业务状态机，也不将本地模拟异常测试视为真实渠道故障验收。

### 6.33 Mapper SQL 参数化边界

1. 所有可作为 JDBC 参数的查询、写入、分页与业务条件使用 MyBatis `#{...}` 绑定，禁止 `${...}` 在解析阶段把调用方内容原样注入 SQL 文本。
2. 排序列、排序方向等结构位置继续通过 Mapper XML 的 `<choose>` 固定分支选择，调用方 DTO 只表达业务排序意图，不承载数据库 SQL 片段。
3. 契约测试通过 classpath 通配符发现全部 Mapper XML，不维护容易遗漏的静态文件清单；任何新增原始替换标记都会阻断后端测试。
4. 该边界不扩张现有 Mapper/Service 职责，也不替代数据库最小权限、业务行列授权、存储过程审计、WAF 或生产攻击验证。

### 6.34 三端支付接入令牌的浏览器传递边界

1. 三端业务入口以固定 `sourceAppId` 区分会话键，在调用预付接口前把演示令牌写入当前标签页的 `sessionStorage`；存储失败时不继续创建预付单。
2. 收银台只在提交 JSON 请求体时读取令牌，支付页面之间的路由仅传递预付单号、支付单号、支付方式、终端和业务场景，不承载令牌。
3. 旧 URL 令牌由收银台或结果页一次性写入对应会话键并立即替换当前路由，兼顾已有联调链接迁移与后续地址最小化。
4. 标签页会话存储减少浏览器历史、书签、复制链接和 Referer 泄露面，但仍受同源脚本与 XSS 影响；前端内置演示令牌只用于本地基线，生产方案仍需可信认证、服务端会话、短期凭据和 CSP 等防护。

### 6.35 运营查询分页资源边界

1. `PageQueryBounds` 作为 DTO 包内轻量公共规则，统一页码 `1..1000`、每页 `1..100` 和 offset 计算，避免 16 个查询对象继续复制易溢出的 `int` 算式。
2. 分页 DTO 显式覆盖 `getPageNo`，使 Service 二次归一化、分页返回元数据和 Mapper `getOffset` 消费同一上限；既有默认页码与默认每页数量不变。
3. 任务日志和死信任务虽然使用不同默认每页数量和 Mapper 参数形态，offset 仍走统一边界，死信 Mapper limit 同时补齐 100 条上限。
4. `99,900` 最大 offset 是当前 offset 分页的防御性边界，不是大数据查询性能承诺；高基数历史查询后续应结合归档、索引和游标分页演进。

### 6.36 告警派发失败事实的数据最小化边界

1. 传输异常和通知器内部异常属于本系统运行诊断信息，不作为供应商业务回执原文保存；失败事实只记录来源分类、失败状态和 `[REDACTED]` 标记。
2. 通道、超时、供应商、主备切换和触发来源等结构化运营字段继续留存，保证任务排查与重试决策不依赖异常字符串。
3. 正常 HTTP 响应仍作为供应商回执事实保存，并在对外查询边界递归脱敏；本轮不改变成功、受理或业务失败响应的审计口径。
4. 更详细的生产故障诊断应由具备加密、可信权限、访问审计和保留期限的独立设施承接，不能通过普通业务表恢复异常原文落库。

### 6.37 告警供应商正常回执的数据最小化边界

1. 通知器先在内存中从原始响应解析成功码、回执号、投递状态和失败码，再对写入 `providerReceiptSnapshot` 的副本执行结构化脱敏。
2. 三类通知器复用共享基类与现有 `PaymentSensitiveDataMasker`，避免通道间出现不同的敏感字段口径；非结构化响应失败闭合。
3. 业务状态字段与回执号保持独立事实，后续回执确认和主备切换不依赖脱敏后的 JSON 文本。
4. 普通告警表不承担原始供应商凭证库职责；生产如需原文取证，应单独设计加密、可信授权、访问审计和保留期限。

### 6.38 告警供应商结果的存储容量边界

1. 派发服务在通知器统一返回边界按 `t_payment_issue_alert_log` 列定义限制五个供应商结果字段，避免把数据库异常当作供应商业务失败处理。
2. 归一化发生在成功状态判断和日志构造之前，因此超长未知状态仍按失败处理，并允许继续尝试备用供应商。
3. 限制同时约束内置和扩展通知器，不把数据库列容量知识散落到各通道实现；未来 schema 变更需同步更新常量与契约测试。
4. 该应用层保护不替代 MySQL 严格模式、字符集字节容量、真实供应商契约和峰值派发压测。

### 6.39 告警供应商诊断码的信任边界

1. 供应商响应中的状态与失败码属于外部不可信输入，业务匹配可使用原始值，但普通日志展示必须经过独立安全标识符约束。
2. 共享基类只允许最多 64 位的 ASCII 诊断标识符进入 `providerDeliveryMessage`，其他内容固定遮蔽，避免换行注入和自由文本扩散。
3. 标准化投递状态是业务判断事实，诊断码只是辅助信息；主备切换和回执确认不得依赖被遮蔽文本。
4. 完整供应商原文如需取证，应进入具备加密、可信授权、访问审计和保留期限的独立设施。

### 6.40 超时支付逐笔关单事务边界

1. 批次查询只负责确定本轮候选，候选内每笔支付单使用独立 `REQUIRES_NEW` 事务更新支付单、支付尝试、预付单并追加事件和处理日志。
2. 任一写入异常会回滚该笔全部本地变更，但不回滚已成功支付单，也不阻止后续支付单执行；失败支付单保持候选条件，依靠后续调度轮次自然重试。
3. 服务返回批次处理、成功、失败数量及最多 3 个失败支付单号，任务中心据此形成告警级运行事实；截断失败标识只限制摘要长度，不改变失败总数。
4. 事件号使用时间戳加随机后缀降低碰撞风险。该设计未引入真实渠道关单调用，也不替代生产数据库、多实例调度、锁竞争和峰值稳定性验证。
