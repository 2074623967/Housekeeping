# payment-core 微信小程序支付端

## 定位

原生微信小程序支付骨架，覆盖充值、提现补款、转账补款、余额补款、预付单、收银台、支付提交、结果刷新、主动查单、受限关单和退款进度只读查询。

## 本地运行

1. 保持 `payment-core` demo 后端运行在 `18081`。
2. 在微信开发者工具中导入本目录，使用测试号运行。
3. 本地调试时关闭开发者工具的合法域名校验；真机联调必须把 `paymentApiBaseUrl` 改为设备可访问且已配置为合法域名的 HTTPS 地址。

默认 API 地址为 `http://localhost:18081`。也可以在开发者工具控制台执行：

```js
wx.setStorageSync("paymentApiBaseUrl", "https://your-payment-api.example.com")
```

## 本地 demo 身份

- 来源应用：`housekeeping-mini-program`
- 支付方式：微信支付
- 渠道：`wx_h5`
- 商户号：`MCH_WX_10001`
- 终端：`MINI_PROGRAM`

小程序通过 `app.js` 的 `globalData.paymentAccessToken` 读取支付访问令牌，仓库默认留空。真实环境必须由受控配置、用户登录态和安全后端注入，不能把示例令牌发布到生产小程序。

## 当前边界

前端已支持在提交响应包含完整微信 `wx.requestPayment` 参数时拉起原生支付；后端本地渠道适配器当前只返回支付受理与待回调事实，因此本地 demo 会跳过原生拉起并继续进入结果页。真实接入需由 `gateway-access` 返回受签名保护的微信支付参数，并补齐 AppID/商户绑定、openid、合法域名、证书与回调验签。

结果页的主动查单或关闭请求报错后，会按当前支付单和业务场景只读获取详情。匹配的读回结果可更新状态；读回失败或归属不符时，旧状态仅供核对，操作保持禁用，需手动刷新确认。此处不把请求错误推断为支付失败或成功。

收银台支付提交或原生支付步骤报错后也会按原预付单读回。若读回为待回调、风控复核或终态，则进入结果页继续核实；读回失败时旧收银台显示“待核查”并禁止重复提交，手动刷新确认后再恢复导航。支付访问令牌和渠道受理事实仍须由可信后端提供。

收银台页面隐藏时停止倒计时、失效本轮读取和提交响应，并锁定旧快照；重新显示时按原预付单读回，原提交仍在途时即使读到待支付也不开放按钮，旧请求结束后再只读核对。迟到的旧提交/原生支付回调不能覆盖恢复后的状态或再次跳转；进入结果页跳转后倒计时也不能重新开放支付。不自动重复发送支付 POST，仍沿用原预付单的固定幂等键。该逻辑仅在本地页面模拟验证，原生支付 UI 与真机生命周期仍需微信开发者工具及真机验收。

若进入结果页的导航失败，收银台保持只读并提示刷新核实；手动刷新读回原支付单后可重试结果页导航，不会重发支付提交。旧页面可见周期的迟到导航失败回调不会覆盖新一轮已核实状态。

小程序固定使用 `MINI-${prepayOrderNo}` 作为该预付单的显式支付幂等键；页面销毁后重进和响应丢失后的同内容重试不再生成新键，页面也不提供手动换键。若已提交后需要改变支付内容，应先核对原支付单、渠道和尝试事实，再由受控业务流程创建新预付单。升级前客户端生成的随机键无法仅凭小程序页面恢复；可信收银台状态、后端幂等和查单仍是防重复扣款的必要门禁。该固定键不是用户身份凭证。

## 自动化

```bash
npm test
```

退款进度页地址为 `/pages/refund-progress/index?refundOrderId=...`，只调用 `GET /api/refunds/{refundOrderId}` 展示状态、渠道退款单号和处理轨迹；审核、主动查单和失败重试仍由运营后台负责。
