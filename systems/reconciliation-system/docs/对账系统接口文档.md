# 对账系统接口文档

基础地址：`http://127.0.0.1:18150`

| 接口 | 方法 | 用途 |
| --- | --- | --- |
| `/api/reconciliation/overview` | GET | 工作台摘要 |
| `/api/reconciliation/batches` | GET | 批次列表 |
| `/api/reconciliation/batches/{batchNo}` | GET | 批次详情 |
| `/api/reconciliation/batches/{batchNo}/export` | GET | 导出批次详情快照 |
| `/api/reconciliation/batches` | POST | 创建批次 |
| `/api/reconciliation/batches/{batchNo}/channel-records` | POST | 写入渠道账单记录 |
| `/api/reconciliation/batches/{batchNo}/internal-records` | POST | 写入平台支付事实 |
| `/api/reconciliation/batches/{batchNo}/readiness-check` | POST | 检查批次是否满足正式对账准入 |
| `/api/reconciliation/batches/{batchNo}/run` | POST | 执行自动对账 |
| `/api/reconciliation/differences` | GET | 查询差异 |
| `/api/reconciliation/differences/{differenceNo}/resolve` | POST | 人工结案 |
| `/api/reconciliation/cross-system/facts` | POST | 上报跨系统事实快照 |
| `/api/reconciliation/cross-system/chains/{businessChainId}` | GET | 查询统一业务链路事实、链路状态和下一动作 |

创建批次示例：

```json
{
  "businessDate": "2026-08-04",
  "channelCode": "WECHAT",
  "billSource": "CHANNEL_FILE"
}
```

批次详情返回内容：

1. 批次基础信息
2. 渠道账单记录列表
3. 平台支付事实列表
4. 差异明细列表
5. 未结案 / 已结案差异数量
6. 对账准入状态、结论、建议动作、责任方和链路计数

对账准入规则：

1. 系统按批次内平台支付事实的 `paymentOrderId` 解析默认链路 ID：`CHAIN-{paymentOrderId}`。
2. 对每条链路查询支付、清分、结算、账务四个关键事实。
3. 所有链路均为 `COMPLETED` 时，批次准入状态为 `READY`，允许执行 `/run`。
4. 存在 `IN_PROGRESS` 或 `WAITING` 链路时，状态为 `CONDITIONAL`，`/run` 直接阻断并返回建议动作。
5. 存在 `EXCEPTION` 链路或平台支付事实为空时，状态为 `BLOCKED`，责任方和处理动作必须回显。
6. 准入检查结果持久化在 `t_reconciliation_batch`，列表、详情、导出和执行门禁使用同一份快照。

批次准入返回字段：

| 字段 | 说明 |
| --- | --- |
| `readinessStatus` | `NOT_CHECKED` / `BLOCKED` / `CONDITIONAL` / `READY` |
| `readinessSummary` | 当前批次是否可进入正式对账的结论 |
| `readinessSuggestedAction` | 当前建议动作 |
| `readinessBlockingOwner` | 阻断责任方 |
| `readinessChainCount` | 纳入判断的业务链路数 |
| `readinessCompletedChainCount` | 已完成四阶段事实的链路数 |
| `readinessAbnormalChainCount` | 存在异常事实的链路数 |
| `readinessPendingChainCount` | 尚未完成关键事实的链路数 |
| `readinessCheckedAt` | 最近一次准入检查时间 |

执行约束：

- `/batches/{batchNo}/run` 会先自动刷新准入快照。
- `readinessStatus != READY` 时不会将批次推进到 `RUNNING`，也不会写入差异结果。
- 准入检查是幂等读写，重复检查只更新当前快照，不产生额外批次或事实。

跨系统事实快照上报示例：

```json
{
  "businessChainId": "CHAIN-PAY202607200001",
  "systemCode": "payment-core",
  "factType": "PAYMENT_SUCCESS",
  "factNo": "PAY202607200001",
  "businessNo": "ORD202607200001",
  "factStatus": "SUCCESS",
  "amount": 168.00,
  "snapshotVersion": 12,
  "occurredAt": "2026-08-09T10:00:00",
  "payload": "{\"paymentOrderId\":\"PAY202607200001\"}"
}
```

链路诊断规则：

1. `businessChainId + systemCode + factType + factNo` 为幂等键，重复上报不增加事实数量。
2. 任一事实状态包含 `FAILED`、`ERROR`、`ABNORMAL` 或“失败/异常”时，禁止直接进入财务收口。
3. `payload` 仅保存脱敏摘要，不保存银行卡号、证件号等敏感原文。
4. 系统按四个关键阶段计算统一链路状态：
   - `payment-core|PAYMENT_SUCCESS`
   - `clearing-system|CLEARING_GENERATED`
   - `settlement-system|SETTLEMENT_CREATED`
   - `accounting-system|ACCOUNTING_POSTED`
5. 状态机口径：
   - `WAITING`：尚未收到任何事实，责任状态为 `UNASSIGNED`
   - `IN_PROGRESS`：已收到部分正常事实，责任状态为 `PENDING`
   - `EXCEPTION`：存在失败或异常事实，责任状态为 `MANUAL_REVIEW`
   - `COMPLETED`：四个关键阶段全部正常，责任状态为 `CLOSED`
6. `financialCloseable=true` 仅允许在 `COMPLETED` 状态返回，避免下游事实不齐时提前财务收口。
7. 关键阶段只有事实状态为 `SUCCESS`、`COMPLETED`、`SUCCESSFUL`、`成功` 或 `已完成` 时才计为已完成；`PENDING`、空值和未知状态不会推动阶段收口。

链路状态返回新增字段：

| 字段 | 说明 |
| --- | --- |
| `chainStatus` | `WAITING` / `IN_PROGRESS` / `EXCEPTION` / `COMPLETED` |
| `responsibilityStatus` | `UNASSIGNED` / `PENDING` / `MANUAL_REVIEW` / `CLOSED` |
| `nextAction` | 当前责任方下一步动作 |
| `abnormalFactCount` | 异常事实数量 |
| `completedStageCount` | 已完成关键阶段数 |
| `expectedStageCount` | 关键阶段总数，当前为 `4` |
| `financialCloseable` | 是否允许进入财务收口 |
| `lastFactAt` | 最近一条事实发生时间 |

批次详情快照导出内容：

1. 批次汇总行
2. 渠道账单记录明细
3. 平台支付事实明细
4. 差异明细

## 跨系统事实自动上报边界

本地 HTTP 联调 profile 下，以下系统在自身业务事实成功提交后调用 `/api/reconciliation/cross-system/facts`：

| 来源系统 | `factType` | `factNo` | 上报时机 | 业务链路口径 |
| --- | --- | --- | --- | --- |
| `payment-core` | `PAYMENT_SUCCESS` | `paymentOrderId` | 支付成功事件完成清分/账务 HTTP 投递，或 AMQP 发布确认后 | `CHAIN-{paymentOrderId}` |
| `clearing-system` | `CLEARING_GENERATED` | `clearingNo` | 清分结果完成结算/账务投递，或 AMQP 发布确认后 | `CHAIN-{paymentOrderId}` |
| `settlement-system` | `SETTLEMENT_CREATED` | `settlementNo` | 消费清分生成事件并成功创建结算单后 | 复用请求中的 `businessChainId` |
| `refund-center` | `REFUND_SUCCESS` | 退款成功 outbox `eventId` | 退款成功 outbox 派发并完成账务投递后 | `CHAIN-{paymentOrderId}` |

四类上报均使用 `businessChainId + systemCode + factType + factNo` 幂等键；重复 HTTP/消息消费不得增加事实数量。各来源通过配置注入地址：

- `HSP_PAYMENT_DOWNSTREAM_RECONCILIATION_FACT_URL`
- `HSP_CLEARING_DOWNSTREAM_RECONCILIATION_FACT_URL`
- `HSP_SETTLEMENT_DOWNSTREAM_RECONCILIATION_FACT_URL`
- `REFUND_CENTER_RECONCILIATION_FACT_URL`

未配置地址时，单元测试和非联调环境不主动外呼；这不表示对账事实已完成。地址配置只证明本地接口联通，不能替代真实消息代理、生产数据库、渠道账单、资金到账或正式财务收口证据。
