# 结算出款系统接口文档

## 1. 接口说明

### 1.1 批次管理

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `GET /api/settlements/dashboard` | 查询结算工作台聚合数据 | 统一返回指标、最近批次、风险出款、最近结算单和最近事件 |
| `POST /api/settlements/batches` | 创建结算批次 | 按天、按周期生成待出款结算任务 |
| `GET /api/settlements/batches` | 查询结算批次列表 | 查看批次状态、处理进度和异常情况 |
| `GET /api/settlements/batches/{batchNo}` | 查询结算批次详情 | 查看某个批次的结算范围、金额和结果 |

### 1.2 结算单管理

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `GET /api/settlements/orders` | 查询结算单列表 | 查看服务者/商家的应结、实结和审核状态 |
| `GET /api/settlements/orders/{settlementNo}` | 查询结算单详情 | 查看单笔结算的金额构成和扣减明细 |
| `GET /api/settlements/orders/{settlementNo}/full` | 查询结算单全量详情 | 返回结算单摘要、金额明细项、审核日志，支撑运营同页下钻 |
| `POST /api/settlements/orders/{settlementNo}/audit` | 审核结算单 | 财务审核通过后进入出款阶段 |
| `POST /api/settlements/orders/{settlementNo}/reject` | 驳回结算单 | 结算异常、资料不全或金额有误时退回 |

### 1.3 出款管理

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `POST /api/settlements/payouts` | 创建待出款批次 | 汇总审核通过且待出款的结算单，生成出款草稿批次 |
| `GET /api/settlements/payouts` | 查询出款批次列表 | 查看出款成功、失败、处理中状态 |
| `GET /api/settlements/payouts/export` | 导出出款批次快照 | 按当前筛选条件留存批次清单，支撑运营留档和问题交接 |
| `POST /api/settlements/payouts/{payoutBatchNo}/execute` | 执行出款批次 | 将待出款草稿批次提交给银行或支付通道 |
| `POST /api/settlements/payouts/{payoutBatchNo}/retry` | 重试出款批次 | 针对失败批次进行人工重试或补发 |
| `POST /api/settlements/payouts/inspect` | 巡检出款批次 | 返回待出款、失败待重试和已完成批次清单；只读，不自动伪造银行回执 |
| `GET /api/settlements/payouts/{payoutBatchNo}/records` | 查询出款记录列表 | 查看某个出款批次下的出款单明细和重试情况 |
| `GET /api/settlements/payouts/{payoutBatchNo}/records/export` | 导出出款记录快照 | 按当前筛选条件留存某批次的出款记录明细 |

### 1.4 事件消费

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `POST /api/settlements/events/clearing/generated` | 消费清分生成事件 | 接收清分结果后自动生成结算单或待出款单 |

## 2. 统一返回

```json
{
  "code": "0",
  "message": "success",
  "data": {},
  "requestId": "REQ..."
}
```

## 3. 核心要求

1. 审核必须幂等，避免重复流转。
2. 创建草稿批次与执行出款必须分步处理，避免未审核订单直接出款。
3. 出款必须幂等，避免重复打款。
4. 失败重试必须保留原记录和重试链路。
5. 结算单列表必须支持按 `clearingNo` 过滤，支撑事件到结算单的链路核对。
6. 工作台接口应由后端统一聚合，不再由前端分别拉取批次、结算单、出款和事件后自行拼装指标。
7. 出款批次和出款记录必须支持导出快照，便于财务留档、运营交接和人工排查。

## 4. 清分消费后的对账事实确认

配置对账事实地址时，清分事件消费生成的结算单必须可按清分单与收款对象回查；找不到对应结算单不得静默跳过事实上报。`POST /api/reconciliation/cross-system/facts` 只有 HTTP 2xx、`code=0`，且 `data` 为本业务链快照，`facts` 中含同链、同结算单、同支付单、同支付场景、同净结金额的 `settlement-system/SETTLEMENT_CREATED/SUCCESS` 事实时，才确认上报。错链、错金额或非结构化回执向上游抛错以供重试；并不要求整个跨系统链在此时已财务收口。未配置地址时保留既有可选行为。

## 5. 清分生成事件 HTTP 入站签名

`POST /api/settlements/events/clearing/generated` 在创建结算事件或订单前，以 `HSP_CLEARING_GENERATED_HTTP_SECRET` 对原始 UTF-8 JSON body 校验 `X-HSP-Clearing-Event-Signature` 的 HMAC-SHA256 Base64 值。密钥缺失、未签名或正文变更返回 HTTP 403，不调用结算事件服务；合法签名仍需既有链路、金额与幂等校验。此门禁不覆盖 AMQP、其他事件、TLS、生产密钥轮换或时间重放防护。

## 6. 清分生成 AMQP 入站签名

结算消费者在解析 `CLEARING_GENERATED` JSON 前，用 `HSP_CLEARING_GENERATED_AMQP_SECRET` 验证原始 body 的 HMAC-SHA256/Base64 签名头 `X-HSP-Clearing-Event-AMQP-Signature`。缺密钥、缺签名、篡改时不创建结算单，原消息送 DLQ 并 ACK；死信发送抛错时 NACK/requeue。合法消息沿用既有信封、幂等和业务失败重试规则。签名只覆盖 body，不能替代 Rabbit ACL/TLS、密钥轮换、重放防护或死信持久确认。

## 7. 清分 AMQP 消费转发确认

结算消费者的 retry/DLQ（含未验签死信）转发须收到关联 publisher ACK 且无 mandatory return 才 ACK 原 delivery；异常、NACK、超时或不可路由均 NACK/requeue。配置 correlated confirms、publisher returns 与 mandatory；`HSP_SETTLEMENT_AMQP_FORWARD_CONFIRM_TIMEOUT_MS` 默认 5000ms，上限 60000ms。broker 确认不是结算创建、持久队列或出款到账证明；重投重复需保持结算业务幂等，并以真实 RabbitMQ 验证路由和故障行为。
