# 退款中心接口文档

基础地址：`http://127.0.0.1:18140`

## 1. 退款列表

`GET /api/refunds`

参数：`refundOrderId`、`paymentOrderId`、`status`、`refundMethod`、`pageNo`、`pageSize`。

`refundOrderId` 和 `paymentOrderId` 在列表与总数查询中按字面量子串匹配，`%`、`_`、`!`、反斜杠和引号只代表原字符，不扩大或改变匹配范围；服务端对绑定的 LIKE 模式编码并显式使用 `ESCAPE '!'`。`status` 和 `refundMethod` 仍为精确筛选，详情和操作使用下述原字符字节精确匹配，不受列表模糊条件影响。

## 2. 工作台摘要

`GET /api/refunds/overview`

返回退款总量、审核中、处理中、失败数量和成功退款金额。

## 3. 发起退款

`POST /api/refunds/apply`

```json
{
  "paymentOrderId": "PAY-DEMO-1001",
  "refundAmount": 68.00,
  "refundMethod": "ORIGINAL",
  "refundReason": "客户取消服务",
  "idempotencyKey": "ORDER-HK-1001-REFUND-1"
}
```

`idempotencyKey` 可省略，由服务生成；若显式提供，去除首尾空白后必须非空、不超过 128 字符，且不能包含控制字符。重试同一申请时应传回原键；显式传空白值不会生成新键。
幂等键按原始 UTF-8 字节精确区分大小写；例如 `Refund-A` 与 `refund-a` 是两次不同申请，只有原键和申请内容一致时才重放原退款单。
原支付单号也按原字符长度与字节精确归属：大小写或字符不同的别名不能借用支付成功事实发起退款，累计退款额度只统计原支付单号精确归属的退款。
退款单号在详情、导出、审核、提交、重试及回调中同样按原字符长度与字节精确匹配；大小写别名不能读取或推进原单，详情日志仅包含精确归属的流水。

## 4. 退款动作

- `POST /api/refunds/{refundOrderId}/approve`
- `POST /api/refunds/{refundOrderId}/submit`
- `POST /api/refunds/{refundOrderId}/retry`
- `POST /api/refunds/{refundOrderId}/callback`
- `GET /api/refunds/{refundOrderId}/export`
- `GET /api/refunds/outbox`
- `POST /api/refunds/outbox/{eventId}/dispatch`

回调示例：

```json
{
  "result": "SUCCESS",
  "channelRefundId": "WX-REFUND-001",
  "rawMessage": "channel success"
}
```

渠道退款流水号最多 128 字符、失败码最多 64 字符，二者不得包含控制字符；渠道原始回执摘要最多 500 字符。以上字段超出库列容量时在状态更新前拒绝，不截断写入；首次成功回调仍必须携带非空渠道退款流水号。

回调仅供可信的渠道结果适配器调用，不接受后台浏览器直接模拟。适配器和退款中心需配置独立 `HSP_REFUND_CALLBACK_HTTP_SECRET`，不得复用支付事实投影或退款成功事件密钥。对 `规范 UTC Unix 秒数 + 换行符 + URL 解码后的退款单号 + 换行符 + 原始 UTF-8 JSON 正文` 计算 HMAC-SHA256/Base64，分别发送 `X-HSP-Refund-Callback-Timestamp` 和 `X-HSP-Refund-Callback-Signature`；服务在解析 JSON、修改退款状态前校验。缺密钥/签名、路径或正文篡改、畸形/重复时间戳、超过 300 秒的过期/超前请求返回 HTTP 403。窗口内原样重试仍依赖既有状态机幂等，签名不替代渠道原生验签；实际渠道适配器必须先独立验证渠道通知并规范化结果。本地九服务演示脚本只是受控模拟发送方，不能视作真实渠道验收。现有无签名调用不兼容，部署前需同步适配器、时钟与密钥，并治理重试/切换期间的未决退款。

补充说明：

1. `SUCCESS` 或 `FAIL` 的同结果、同已保存事实重复回调会直接返回当前退款单，不重复推进状态。
2. 重复回调不会新增操作日志，也不会重复写 `REFUND_SUCCESS` outbox 事件。
3. 首次 `SUCCESS` 回调必须在同一事务内恰好写入一条成功 outbox；写入失败时回调状态和审计日志回滚，可在故障排除后用原回调重试。
4. 首次绑定渠道退款流水号需要退款申请时从原支付成功事实保存的渠道快照；同一渠道的相同退款流水号不能归属两张退款单，冲突返回人工核查错误且不写成功事件。不同渠道同号不互相占用；历史缺快照的退款单不得由回调推定归属。
5. `POST /api/refunds/{refundOrderId}/submit` 对缺渠道快照的已审核退款返回“退款单缺少原支付渠道事实，待人工核查”，保持 `APPROVED`、不新增提交日志；历史已进入 `PROCESSING` 的缺快照单仍在渠道号回调绑定时失败闭合。
6. `FAIL` 终态重复回调仅在渠道退款流水号（包括缺省）与失败码均和首笔失败事实一致时幂等返回；任一字段变化均拒绝，不覆盖已保存的失败事实。
7. `POST /api/refunds/{refundOrderId}/retry` 只允许原渠道快照存在且失败回调未绑定渠道退款流水号的退款单重入 `PROCESSING`，并清除本次处理中不应保留的失败码和终态时间。已有渠道流水的失败单保持 `FAIL` 和原流水、终态时间、审计记录不变，返回“失败退款已有渠道流水，须人工核查后再处理”；不得用自动重试覆盖上一次渠道事实。

## 5. 退款成功事件出站

成功回调写入的 `payloadJson` 是标准 JSON，包含字符串字段 `refundOrderId`、`paymentOrderId`、`payScene` 和 `refundAmount`；缺失支付场景沿用空字符串，特殊字符按 JSON 规则转义。

`GET /api/refunds/outbox`

参数：`eventId`、`aggregateId`、`status`、`pageNo`、`pageSize`。

事件列表及总数中的 `eventId` 和 `aggregateId` 按字面量子串筛选；`%`、`_`、`!`、反斜杠和引号仅作为原字符，服务端对绑定的 LIKE 模式编码并显式指定 `ESCAPE '!'`。`status` 保持精确筛选，查询不派发事件，也不改变下述派发入口的原字符字节精确匹配。

`POST /api/refunds/outbox/{eventId}/dispatch`

派发事件号按原字符长度与字节精确匹配，大小写别名不能派发或回放原事件；派发后按精确事件号回读状态，不使用列表的模糊搜索结果。

```json
{
  "simulateResult": "SUCCESS",
  "remark": "本地派发成功"
}
```

说明：

1. `PENDING / FAIL` 状态支持重新派发。
2. `SUCCESS` 状态会直接返回当前事件，不重复派发。
3. `FAIL` 模式会增加重试次数并写入最近错误信息。
4. 非 `FAIL` 模式会真实调用账务系统和对账系统；两端均须返回 HTTP 200、业务码 `0` 和匹配本次退款的业务回执后才将 outbox 标记为 `SENT`。HTTP 202 即使带成功码也不能代表同步记账或事实落库。
5. 账务侧以 `REFUND_SUCCESS + refundOrderId` 幂等，生成借方冲回流水；对账侧以业务链路、系统、事实类型和事实编号联合幂等。
6. 任一下游调用失败时 outbox 保持 `FAIL`，重试时允许再次调用两端；已经成功的一端不得重复入账或重复生成事实。

下游契约：

- `POST /api/accounting/events/refunds/success`
- `POST /api/reconciliation/cross-system/facts`

本地默认账务账户为 `ACT10003`，可通过 `REFUND_CENTER_ACCOUNTING_REFUND_SUCCESS_ACCOUNT_NO` 覆盖。

账务回执 `data` 须包含当前 `businessChainId`、`eventType=REFUND_SUCCESS`、`bizNo=refundOrderId` 和 `eventStatus=已消费`。对账回执 `data` 须是当前业务链快照，`facts` 中存在同一 `businessChainId`、`systemCode=refund-center`、`factType=REFUND_SUCCESS`、`factNo=eventId`、`businessNo=refundOrderId`、`factStatus=SUCCESS`、支付场景和金额均精确匹配的事实。缺失、串单、金额不符或 HTTP 202 均使 outbox 留在 `FAIL` 等待受控重试；账务或对账已成功的一端必须靠原有幂等避免重复资金动作。旧版仅返回成功码的下游不兼容，混版切换前须成对验证。

向账务派发 `REFUND_SUCCESS` 时，必须配置 `HSP_REFUND_SUCCESS_HTTP_SECRET`；缺失或空白密钥时在调用下游前拒绝，outbox 保持失败可重试，不向受控 mock 或真实账务发送无签名请求。每次 outbox 派发/重试生成当前 UTC Unix 秒数字符串，写入 `X-HSP-Refund-Event-Timestamp`；对 `时间戳 + 换行符 + 实际发送的原始 UTF-8 JSON body` 计算 HMAC-SHA256/Base64，写入 `X-HSP-Refund-Event-Signature`。账务侧使用相同密钥验证规范十进制秒数、签名及不超过 300 秒的时钟偏差；缺失、畸形、过期/超前、旧版仅签 body 或正文篡改均返回 403。新旧协议不兼容，须协调退款中心和账务的部署/回滚及待派发 outbox 接管，不能直接混合滚动；300 秒内重放仍依赖账务幂等。对账事实不受本协议保护，正式部署另需时钟同步、密钥安全分发/轮换、TLS 和服务间网络隔离。

## 6. 退款详情快照导出

`GET /api/refunds/{refundOrderId}/export`

导出内容：

1. 退款单汇总信息
2. 退款操作日志
3. 退款成功事件出站记录

## 7. 支付成功事实投影

`POST /api/refunds/internal/payment-success`

内部支付成功事实投影，不能由前端调用。默认拒绝无签名请求；受控发送方和退款中心分别配置相同的专用 `HSP_PAYMENT_REFUND_PROJECTION_HTTP_SECRET`（不得复用退款事件或对账事实密钥），将 UTF-8 JSON 原始正文与规范 UTC Unix 秒数按 `时间戳 + 换行符 + 正文` 计算 HMAC-SHA256/Base64，并携带 `X-HSP-Payment-Projection-Timestamp` 和 `X-HSP-Payment-Projection-Signature`。密钥缺失、签名/时间戳缺失、正文篡改、过期/超前（超过 300 秒）或非规范时间戳返回 HTTP 403，不写入可退款支付来源；通过后才解析并执行原有幂等和事实一致性校验。payment-core 可在支付成功事件派发时配置 `HSP_PAYMENT_DOWNSTREAM_REFUND_PROJECTION_URL` 与同名独立密钥自动发送；未配置 URL 时仍不投影。部署前须完成密钥轮换、混版切换、时钟同步、TLS、窗口内重放和历史成功支付事实补投治理。

投影成功或同事实幂等重放时返回 HTTP 200、`code="0"`，且 `data.paymentOrderId` 为校验后的规范原支付单号（去掉请求值首尾空格）；来源冲突不返回成功回执。受控发送方须使用不带首尾空格的单号并检查回执与发送单号精确一致，缺失或不一致时事件保留待重试，不推进对账和完成阶段。旧版仅返回业务码的退款中心与新版发送方混布会失败闭合，须成对验证并安排受控切换；该回执不等于渠道到账证明。
