# 清分清算系统接口文档

## 1. 接口说明

### 1.1 批次管理

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `POST /api/clearing/batches` | 创建清分批次 | 按天、按小时、按业务线发起清分任务 |
| `GET /api/clearing/batches` | 查询清分批次列表 | 查看批次进度、状态、处理结果 |
| `GET /api/clearing/batches/{batchNo}` | 查询批次详情 | 查看单个批次的订单范围和结果统计 |
| `POST /api/clearing/batches/{batchNo}/rerun` | 重新运行批次 | 批次失败后人工重跑或补偿重算 |

### 1.2 清分结果

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `GET /api/clearing/orders` | 查询清分明细列表 | 查看每笔订单的应分、实分、差额 |
| `GET /api/clearing/orders/{clearingNo}` | 查询清分明细详情 | 排查某笔清分结果的计算过程 |
| `GET /api/clearing/orders/export` | 导出清分明细快照 | 按当前筛选条件留存清分结果清单 |
| `GET /api/clearing/orders/{clearingNo}/export` | 导出清分详情快照 | 导出单笔清分结果、费用规则快照和分账明细 |

### 1.3 规则管理

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `GET /api/clearing/rules` | 查询清分规则列表 | 查看当前生效的清分、分账、扣费规则 |
| `POST /api/clearing/rules` | 新增清分规则 | 配置新业务线或新合作方规则 |
| `POST /api/clearing/rules/{ruleNo}/enable` | 启用规则 | 发布前的规则上线 |
| `POST /api/clearing/rules/{ruleNo}/disable` | 停用规则 | 规则下线、异常止损、业务切换 |

### 1.4 费用与分账

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `GET /api/clearing/fees` | 查询费用规则 | 查看渠道费、平台服务费、补贴费 |
| `POST /api/clearing/fees` | 新增费用规则 | 配置渠道费率、固定费用、封顶规则 |
| `GET /api/clearing/shares` | 查询分账明细 | 查看平台、商家、服务者的分账结果 |

### 1.5 事件消费

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `POST /api/clearing/events/payments/success` | 消费支付成功事件 | 收到支付成功后触发清分入队或直接清分 |
| `POST /api/clearing/events/replay-failed` | 重放失败派发事件 | 人工提前重放待重试/失败的清分结果 outbox 事件 |

支付成功事件请求体沿用支付核心业务字段，并可携带 `eventNo`、`eventType=PAYMENT_SUCCESS`、`schemaVersion=1` 和 `businessChainId` 进行跨系统排障；历史调用缺少这些追踪字段时，清分系统继续按支付单号兼容生成链路 ID。

## 2. 返回规范

统一返回：

```json
{
  "code": "0",
  "message": "success",
  "data": {},
  "requestId": "REQ..."
}
```

## 3. 核心要求

1. 清分批次必须带幂等键，避免重复创建批次。
2. 单笔支付清分必须支持重复消费，避免重复分账。
3. 重跑清分必须保留历史版本，便于审计与追溯。
4. 清分结果列表必须支持按 `paymentOrderId` 查询，用于事件链路核验。
5. 清分结果列表和单笔详情都必须支持导出快照，便于财务核验、产品对账和测试留档。

## 4. 清分结果下游确认

1. HTTP 模式按结算、账务、可选对账事实的顺序派发。结算和账务的统一响应必须为 HTTP 2xx、`code=0` 且 `data` 为已消费事件：`eventType=CLEARING_GENERATED`、`bizNo={清分单号}`、`businessChainId={清分单业务链路}`、非空 `eventNo` 和 `eventStatus=已消费`。非空响应或成功码本身不证明本单已消费。
2. 配置对账事实地址时，`data` 必须为同业务链快照，`facts` 中包含 `clearing-system/CLEARING_GENERATED/SUCCESS`、清分单号、支付单号、支付场景和金额均与本次提交一致的事实。整条链路此时无需完成财务收口；未配置对账地址仍保持既有可选行为。
3. 任一确认失败时 outbox 保持可重试；此前已成功的下游可能被再次调用，消费者必须保持幂等。AMQP 生产者确认不是最终消费确认，本地模拟响应不替代真实资金和生产消息验证。

## 5. 支付成功 HTTP 入站签名

`POST /api/clearing/events/payments/success` 要求 `X-HSP-Payment-Event-Signature`：用 `HSP_PAYMENT_SUCCESS_HTTP_SECRET` 对原始 UTF-8 JSON body 计算 HMAC-SHA256 并以 Base64 编码。密钥缺失、未签名或正文修改均返回 HTTP 403，且不创建清分订单、批次或事件。签名通过不替代已有业务号、金额、场景及重放校验；AMQP 消费、其他事件、TLS/网络隔离、密钥轮换与生产权限仍需独立治理。

## 6. 清分生成事件 HTTP 出站签名

HTTP 派发到结算和账务时，配置 `HSP_CLEARING_GENERATED_HTTP_SECRET` 后，对各自发送的原始 UTF-8 JSON body 计算 HMAC-SHA256，以 Base64 放入 `X-HSP-Clearing-Event-Signature`；两端须配置相同密钥。发送端未配置密钥时仍能向受控 mock 发送旧格式，但真实结算与账务入口默认返回 HTTP 403，清分 outbox 不应记为成功。对账事实 HTTP 和 AMQP 仍是独立协议；正式部署另需安全分发/轮换密钥、TLS、网络隔离和时间重放防护。

## 7. 清分生成事件 AMQP 出站签名

清分 AMQP 模式必须配置独立的 `HSP_CLEARING_GENERATED_AMQP_SECRET`；未配置时不发布消息，outbox 沿既有失败/重试规则处理。发送端在 Rabbit 消息转换后对实际 `message.getBody()` 计算 HMAC-SHA256/Base64，写入 `X-HSP-Clearing-Event-AMQP-Signature`。账务和结算消费者使用同一密钥验签；缺密钥、缺签名或正文篡改不进入资金服务，原消息发送各自 DLQ 后 ACK，发送抛错则 NACK/requeue。合法消息继续信封校验、业务幂等与重试。签名仅覆盖 AMQP `CLEARING_GENERATED` body，不认证消息头、不提供时间重放防护或死信持久发布确认；正式 Rabbit ACL/TLS、密钥安全分发/轮换和目标环境联调仍需单独验收。
