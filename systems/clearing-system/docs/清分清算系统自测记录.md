### 本轮修正

1. `ClearingMemoryStore` 新增按 `paymentOrderId` 查询既有清分单与支付成功事件的幂等判断，避免同一支付成功事件被重复消费时再次生成清分单、分账项和本地事件。

1. `payment-core` 重投递再次命中 `clearing-system` 时，不会再把本地清分单、分账项和事件台账重复膨胀。
2. 当前仍未覆盖真实消息总线、消费回执、失败重试、死信补偿与下游系统生产级幂等，因此仍不触发 `test -> master` 或 `release/*`。

## 2026-08-02 清分结果重复派发护栏补强

### 验证结果

| 项目 | 结果 |
| --- | --- |
| 后端全量测试 | `14` 个测试通过，`0` failures，`0` errors，`0` skipped |
| 后台前端构建 | `npm run build` 通过 |
| 真实 HTTP 幂等复验 | 临时实例 `18121` 上，同一支付成功事件 `PAY-CLEARING-IDEMPOTENT-20260802-001` 连续提交两次后，仅生成 `1` 笔清分单 `CLO20002`、`1` 条 `PAYMENT_SUCCESS` 事件和 `1` 条 `CLEARING_GENERATED` 事件 |

### 本轮修正

1. `ClearingEventDispatchServiceImpl` 新增 outbox 派发成功短路：当 `CLEARING_GENERATED` 事件的 `publishStatus=SUCCESS` 时，直接返回成功，不再向下游账务/结算重复派发。
2. 新增回归测试覆盖“清分结果事件已成功投递后，再次触发派发时不得再次调用下游接口”的场景。
3. 保留原有“同一支付成功事件不重复生成清分单、分账项和支付成功事件”的本地幂等护栏。

### 本轮事实

1. 新的真实 HTTP 回归确认了清分本地工件不会因重复消费而膨胀。
2. 新增的派发层回归测试补上了“本地工件不重复，但下游可能被重复通知”的缺口。
3. 当前这轮仍未把 AMQP 真消息总线下的投递确认、失败重试和死信补偿整包跑完，因此依旧不触发 `test -> master` 或 `release/*`。
