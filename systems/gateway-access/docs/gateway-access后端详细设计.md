# gateway-access 后端详细设计

## 1. 目标

提供支付网关接入治理能力，包括应用、渠道、证书和权限。

## 2. 设计原则

1. 接入治理与支付交易解耦
2. 配置优先，当前已使用 MyBatis + H2 持久化实现，后续可平滑切换 MySQL
3. 输出统一接口返回结构
4. 为 `payment-core` 提供真实接入边界

## 3. 第一版实现

1. MyBatis 持久化仓储
2. 统一总览接口
3. 列表查询接口
4. 启停接口

## 4. 后续扩展

1. MyBatis + MySQL 生产化切换
2. 证书版本治理
3. 灰度发布
4. 限流与签名策略

## 5. 2026-07-28 调用方审计增强

1. 新增调用方审计台账，记录应用、网关、操作类型、签名算法、来源 IP、结果和风险提示。
2. 审计查询支持按请求流水号、应用编码和结果状态筛选，便于排查签名失败、停用渠道等接入问题。

## 6. 2026-07-28 环境隔离与灰度发布增强

1. 新增灰度发布路由台账，记录网关在 `PROD / GRAY / UAT` 环境下的发布策略、流量占比和发布时间窗口。
2. 路由台账支持按环境和状态筛选，并支持启停操作，便于发布窗口内快速切流和回退。

## 7. 2026-08-06 启停依赖门禁补强

1. 证书启停不再是孤立开关。启用证书前必须满足两个前置条件：
   - 证书未过期
   - 证书归属网关处于 `ENABLED`
2. 权限启停增加应用依赖校验。若接入应用已停用，则不允许单独启用其权限，避免形成“应用停用但权限恢复”的治理裂缝。
3. 灰度路由启停增加网关依赖校验。若关联网关未启用，则不允许启用路由，避免把灰度流量错误切到停用渠道。
4. 上述门禁全部在服务层显式校验，并通过 MyBatis 实体查询获取依赖对象状态，为后续接入真实审批流、证书轮换流程和发布管控奠定基础。

## 8. 2026-09-12 交易提交未知审计语义补强

1. 支付与退款提交代理在进入 `RestTemplate` 上游调用前维护调用边界标记；参数或治理门禁拒绝继续记录 `FAILED / danger`。
2. 已进入上游调用后发生空响应、非确定响应、字段校验失败或运行时异常时记录 `UNKNOWN / warn`，与 payment-core“先查单、禁止盲目重提”的处理语义保持一致。
3. 成功审计仍要求上游返回确定受理结果并通过稳定字段校验；查单失败仍记录 `FAILED`，因为查单不产生新的支付或退款提交。
4. 审计状态不改变异常响应码、交易状态或资金事实，也不证明真实渠道已受理；生产仍需通过渠道查单、回调和对账确认结果。

## 9. 2026-09-12 退款尝试身份透传

1. 退款提交与退款查单请求新增必填 `refundAttemptNo`，与 `refundOrderId` 分别表示单轮渠道请求身份和平台退款业务归属；两者均做非空、`64` 字符上限和 ISO 控制字符校验。
2. gateway-access 不生成、不替换该编号，校验后原样转发配置的上游地址，使渠道适配层可将其映射为商户退款请求号；同一轮调用前失败重试由 payment-core 复用该值。
3. 提交进入上游后仍按既有规则把不确定结果审计为 `UNKNOWN / warn`；调用方必须用同一 `refundAttemptNo` 查单，不能把换号重提当作恢复策略。
4. 字段透传与本地自动化不证明具体渠道支持该幂等键或按该键查单，生产接入仍需逐渠道映射、签名、超时、重复请求和账单核验。
