## 2026-10-03 账务同账户并发入账冲突定位与行锁回归

补齐账务统一异常处理的固定类别日志后，再次九服务冷启动在支付事件 `CLEARING_ACCEPTED/FAILED` 失败；同一秒账务两次返回 `BALANCE_UPDATE_CONFLICT`，清分和支付核心分别记录账务响应 `HTTP_CODE_OR_STRUCTURE`、`HTTP_CODE_OR_DATA`。该次复现确认两个下游失败均经过账务余额 CAS 冲突分支，而非对账事实回执拒绝；更早未记录类别的失败不据此追溯归因。

原有入账先普通读取同一账户余额，再按旧余额 CAS 更新；支付和清分事件并行记入同一账户时，两者都可能读到旧值，后更新者被拒。新增 `SELECT ... FOR UPDATE` 余额读取，在事务内先串行化同账户余额变更，再保留原 CAS 和不足额保护；贷记、借记、冻结、解冻与审批调账共用该边界。新并发回归让第一笔贷记占用余额行锁时启动第二笔，修复前稳定出现 `BALANCE_UPDATE_CONFLICT`，修复后两笔均入账、余额和流水一致。账务定向回归与全量 Maven `64/64` 通过；修复后两次独立九服务冷启动 happy-path 均通过，对账事实七项、阶段 `4/4`，退出九服务全部停下。

以上仅定位并修复本次捕获的 H2 并发冲突；两次通过不证明所有间歇场景已消失，也未验证目标 MySQL 8 的行锁行为、多实例重试、正式资金、生产消息或可信授权，不构成生产发布放行。

## 2026-10-03 已消费账务事件异账户重放归属校验

## 2026-10-03 结算补偿重放业务事实与输入门禁
