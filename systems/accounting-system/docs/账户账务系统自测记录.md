## 2026-07-31 重复消费幂等收口

### 验证结果

| 项目 | 结果 |
| --- | --- |
| 定向后端测试 | `AccountingEventServiceImplTest` 共 `2` 个用例通过，`0` failures，`0` errors，`0` skipped |

### 本轮修正

1. `AccountingDataMapper` 新增按 `accountNo + bizType + bizNo` 查询账务流水、按 `eventType + bizNo` 查询事件台账的能力。
2. `AccountingEventServiceImpl` 在消费 `PAYMENT_SUCCESS` 和 `CLEARING_GENERATED` 事件前，先检查既有流水是否已存在，避免重复入账；事件台账也改为重复消费时复用既有事件记录。
3. 新增重复消费单测，确认同一支付成功事件重复进入后，余额不会再次增加，事件台账也不会重复写入。

### 当前判断

1. `payment-core` 或 `clearing-system` 的补偿重放再次命中 `accounting-system` 时，不会再把同一业务单号重复记账。
2. 当前仍未覆盖真实总账、凭证、会计期间关闭、差异调账审批和 MQ 级消费确认，因此仍不触发 `test -> master` 或 `release/*`。

## 2026-08-02 事件台账优先幂等修复

### 验证结果

| 项目 | 结果 |
| --- | --- |
| 后端全量测试 | `11` 个测试通过，`0` failures，`0` errors，`0` skipped |
| 后台前端构建 | `npm run build` 通过 |
| 真实 HTTP 幂等复验 | 临时实例 `18111` 上，同一支付成功事件 `PAY-HTTP-IDEMPOTENT-20260802-001` 连续提交两次后，账户 `ACT10001` 余额保持 `¥120.00`，事件列表仅 `1` 条 |

### 本轮修正

1. `AccountingEventServiceImpl` 新增“事件台账优先”幂等护栏，先按 `eventType + bizNo` 判断是否已经消费。
2. 保留原有“账务流水存在则不再记账”的护栏，形成“事件台账 + 流水”双重保护。
3. 新增“历史已有事件但缺少对应流水时，不得再次加钱”的自动化回归用例，覆盖旧版本演练数据场景。

### 本轮事实

1. 当前 `18110` 常驻实例存在历史演练数据，曾暴露出“事件已存在但仍可再次加钱”的旧行为风险。
2. 新代码在临时实例 `18111` 上已完成真实 HTTP 复验：两次提交返回同一 `eventNo=EVT50002`，余额不再二次增长。
3. 这说明 `accounting-system` 针对支付成功事件重放的幂等保护已经从“仅依赖单测”升级到“有真实接口回归证据”的状态。
