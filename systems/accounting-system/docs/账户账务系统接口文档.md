# 账户账务系统接口文档

## 1. 接口说明

### 1.1 主体管理

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `POST /api/accounting/subjects` | 新增账户主体 | 新用户、商家、服务者、平台主体入账前建档 |
| `GET /api/accounting/subjects` | 查询主体列表 | 主体检索、运营维护、财务核对 |
| `GET /api/accounting/subjects/{subjectId}` | 查询主体详情 | 查看某主体的状态、类型、归属信息 |

### 1.2 账户管理

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `POST /api/accounting/accounts/open` | 开立账户 | 为主体创建可用、冻结、在途余额账户 |
| `GET /api/accounting/accounts` | 查询账户列表 | 按主体、类型、状态检索账户 |
| `GET /api/accounting/accounts/{accountNo}` | 查询账户详情 | 查看账户归属、状态、币种、余额信息 |
| `GET /api/accounting/accounts/{accountNo}/export` | 导出账户详情快照 | 导出账户汇总、余额快照和最近流水 |
| `POST /api/accounting/accounts/{accountNo}/close` | 关闭账户 | 账户注销、异常处理、业务终止 |

### 1.3 余额操作

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `POST /api/accounting/balances/credit` | 余额入账 | 支付成功、退款到账、补贴发放 |
| `POST /api/accounting/balances/debit` | 余额出账 | 提现、扣款、服务费划转 |
| `POST /api/accounting/balances/freeze` | 余额冻结 | 预占金额、争议款、待确认资金 |
| `POST /api/accounting/balances/unfreeze` | 余额解冻 | 冻结解除、支付撤销、审核通过 |

### 1.4 流水查询

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `GET /api/accounting/ledgers` | 查询流水列表 | 对账、审计、资金追踪 |
| `GET /api/accounting/ledgers/export` | 导出流水快照 | 导出账户流水、业务类型和金额变化留档 |
| `GET /api/accounting/ledgers/{ledgerNo}` | 查询流水详情 | 查看某一笔资金变更的完整轨迹 |

### 1.5 冻结调账

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `POST /api/accounting/freezes` | 创建冻结单 | 创建冻结原因、金额、业务单关联 |
| `POST /api/accounting/freezes/{freezeNo}/unfreeze` | 冻结单解冻 | 释放冻结金额并恢复可用余额 |
| `POST /api/accounting/adjustments` | 创建调账单 | 人工修正、系统补偿、差错处理 |
| `POST /api/accounting/adjustments/{adjustNo}/approve` | 审批调账单 | 财务审核后让调账生效 |

### 1.6 事件消费

| 接口 | 说明 | 典型用途 |
| --- | --- | --- |
| `POST /api/accounting/events/payments/success` | 消费支付成功事件 | 支付核心推送成功支付结果后自动入账 |
| `POST /api/accounting/events/clearing/generated` | 消费清分结果事件 | 清分系统推送分账/应收结果后生成账务动作 |
| `POST /api/accounting/events/refunds/success` | 消费退款成功事件 | 退款中心推送成功事实后按退款单号幂等生成借方冲回流水 |
| `POST /api/accounting/events/settlements/compensations` | 消费结算补偿事件 | 结算差异补差、冲回或人工补偿入账 |

配置 `HSP_ACCOUNTING_DOWNSTREAM_RECONCILIATION_FACT_URL` 后，事件成功入账会向对账系统上报 `ACCOUNTING_POSTED` 事实，事实编号使用账务事件 `eventNo`。重复消费会重复尝试上报，由对账系统按业务链路和事实编号幂等收口；未配置地址时不主动外呼。

支付成功事件请求体沿用支付核心业务字段，并可携带 `eventNo`、`eventType=PAYMENT_SUCCESS`、`schemaVersion=1` 和 `businessChainId` 进行跨系统排障；历史调用缺少这些追踪字段时，账务系统继续按支付单号兼容生成链路 ID。

支付成功事件首次消费须提供非空、无首尾空格的业务订单号。台账 payload 使用 JSON 序列化存储原样订单号、支付场景和金额；同一支付单号重放必须与原账务事件的订单号、场景、数值金额、链路及已入账账户一致。历史台账若没有可核对的 `orderNo`，不再凭相同支付单号默认确认重放，应人工核查后处理。此业务幂等门禁不构成 HTTP/AMQP 发送方身份认证，正式部署仍须限制入口并接入可信服务间鉴权。

`POST /api/accounting/events/payments/success` 在业务消费前要求 `X-HSP-Payment-Event-Timestamp` 为规范十进制 UTC Unix 秒数，且接收时与本机时钟偏差不超过 300 秒；`X-HSP-Payment-Event-Signature` 为使用 `HSP_PAYMENT_SUCCESS_HTTP_SECRET` 对 `时间戳 + 换行符 + 原始 UTF-8 JSON body` 计算的 HMAC-SHA256/Base64。缺密钥、缺头、旧版仅签 body、时间过期/超前或正文篡改均返回 HTTP 403，不入账；通过后仍需业务幂等。需与支付核心及清分协调切换、接管旧 outbox 并同步时钟，不可混用新旧版本；300 秒内合法请求仍可重放。该门禁只覆盖此 HTTP 路由，AMQP 与其余账务事件另需可信队列权限、链路隔离和生产密钥轮换。

`POST /api/accounting/events/refunds/success` 独立使用 `HSP_REFUND_SUCCESS_HTTP_SECRET`，要求 `X-HSP-Refund-Event-Timestamp` 为规范十进制 UTC Unix 秒数、与接收时钟偏差不超过 300 秒，`X-HSP-Refund-Event-Signature` 为对 `时间戳 + 换行符 + 原始 UTF-8 JSON body` 计算的 HMAC-SHA256/Base64。缺密钥、缺头、旧版仅签 body、过期/超前、畸形时间或正文篡改均返回 HTTP 403，不调用冲回服务；通过后仍执行退款单与账务幂等核验。此协议须与退款中心协调切换、接管待派发 outbox 并同步时钟，不可混合部署；300 秒内仍可重放合法请求。共享密钥安全分发与轮换、TLS/网络隔离及其他事件鉴权须另行治理。

`POST /api/accounting/events/clearing/generated` 使用独立 `HSP_CLEARING_GENERATED_HTTP_SECRET`，要求 `X-HSP-Clearing-Event-Timestamp` 为规范十进制 UTC Unix 秒数、与接收时钟偏差不超过 300 秒，`X-HSP-Clearing-Event-Signature` 为对 `时间戳 + 换行符 + 原始 UTF-8 JSON body` 计算的 HMAC-SHA256/Base64。缺密钥/头、旧版仅签 body、过期/超前/畸形时间或正文篡改返回 HTTP 403，不创建清分账务事件与流水。通过后仍执行清分单号、链路及业务幂等核验；须与清分、结算协调切换，不能混合部署，窗口内仍依赖幂等。本门禁不替代 AMQP、结算补偿入口及生产密钥轮换、时钟同步和网络治理。

`POST /api/accounting/events/settlements/compensations` 默认拒绝未认证调用；只有配置独立 `HSP_SETTLEMENT_COMPENSATION_HTTP_SECRET` 并携带 `X-HSP-Settlement-Compensation-Signature`（对原始 UTF-8 JSON body 计算的 HMAC-SHA256 Base64）时才解析补偿请求。密钥缺失、签名缺失或正文被修改均返回 HTTP 403，不调用账务补偿服务；签名通过后继续业务字段与幂等校验。仓库内没有该人工补偿路径的发送端，需受控调用方安全持有密钥并实现审批、操作人身份归属、审计和重放防护后才能生产使用；仅持有密钥不证明请求中 `operatorName` 的真实身份，也不代表已获批准。

结算补偿请求必须提供非空结算补偿单号、原业务单号和正金额，`compensationDirection` 仅接受 `借方` 或 `贷方`；不合法请求在事件或流水写入前拒绝。同一补偿单号重放时，账户须与已有业务流水一致，原业务单号、数值意义上的金额及补偿方向须与原事件载荷一致，否则拒绝复用已消费事件。历史有事件但无流水时仍沿用兼容行为，不能仅凭该路径确认账户归属。

## 2. 统一返回

建议统一为：

```json
{
  "code": "0",
  "message": "success",
  "data": {},
  "requestId": "REQ..."
}
```

## 3. 关键约束

1. 所有入账接口必须带幂等键，避免重复记账。
2. 所有流水查询必须支持分页和时间范围过滤。
3. 所有冻结/解冻必须记录操作人、操作来源和原因。
4. 所有事件消费必须支持重复投递和乱序到达。

## 4. 账务事实对账回执

配置对账事实地址时，支付成功、清分生成和退款成功的账务消费均要求对账接口返回 HTTP 2xx、`code=0` 及结构化业务链快照。`data.businessChainId` 必须等于本账务事件链路，`data.facts` 中至少有一条 `accounting-system/ACCOUNTING_POSTED/SUCCESS`，其事实号为账务事件号，业务号、支付场景和金额与本次提交一致；退款冲回的对账业务号为原支付单号。仅成功码、其他链路或其他事实的快照不构成本次入账确认。失败向上游抛出以便重试，不要求整条业务链已完成财务收口；未配置地址时保持既有可选行为。

## 5. 清分生成 AMQP 入站签名

账务消费者在解析 `CLEARING_GENERATED` JSON 前，用 `HSP_CLEARING_GENERATED_AMQP_SECRET` 验证原始 body 的 HMAC-SHA256/Base64 签名头 `X-HSP-Clearing-Event-AMQP-Signature`。密钥缺失、未签名或正文被篡改不进入账务服务，原消息送 DLQ 并 ACK；死信发送抛错时 NACK/requeue。合法消息仍按既有信封、幂等和失败重试规则处理。签名不覆盖消息头，不等于时间重放防护、Rabbit ACL/TLS、密钥轮换或持久死信确认。

## 6. 资金 AMQP 消费转发确认

支付成功和清分生成两个消费者在转发 retry/DLQ（含未验签死信）后，等待关联 publisher confirm 且要求 mandatory 消息未被退回，再 ACK 原 delivery。发送异常、broker NACK、确认超时或不可路由时 NACK/requeue。设置 correlated confirms、publisher returns、mandatory；`HSP_ACCOUNTING_AMQP_FORWARD_CONFIRM_TIMEOUT_MS` 默认 5000ms、上限 60000ms。该确认只证明当前 broker 接收并可路由，不保证业务入账、队列持久化或故障切换；不确定发布时重复投递仍须由账务幂等处理。真实 RabbitMQ 与生产权限、路由、持久化策略需另验。
