# 系统痛点与版本迭代池

## 1. 文档定位

本文档用于把各支付相关子系统在交付后的真实痛点、结构性缺口、下一步版本改造和验收标准统一收口。

它不是临时备注，而是后续持续迭代的唯一需求池入口之一。

## 2. 维护原则

1. 每个系统交付后，都要先写出当前版本的痛点。
2. 能在当前版本修掉的，直接进入当前迭代。
3. 需要改结构的，进入下一版本。
4. 不能立即落地但有明确价值的，保留为路线图。
5. 每一条痛点都要明确归属系统、影响范围、建议版本和验收标准。

## 3. 当前高优先级痛点

### 3.1 payment-core

当前痛点：

- 仍有部分运营能力与正式生产版之间存在差距
- 真实渠道接入、对账前置事实收口、任务中心正式告警链路还需要继续增强
- 三端收银台、结果页、异常处理页的体验仍需继续细化

建议版本：

- `V1.1`：补齐正式版告警、路由和监控细节
- `V1.2`：补齐真实渠道接入与稳定性治理
- `V2`：支付中台能力外溢到其他子系统联动

### 3.2 deposit-system

当前痛点：

- V1 只能支撑单主体单账户闭环
- 多规则、多品类、历史账户结转需要结构性升级

建议版本：

- `V1`：保持稳定交付
- `V2`：总保证金账户、规则绑定、旧账户结转

### 3.3 wallet-account

当前痛点：

- 账户和业务对象之间的扩展口径仍需补齐
- 需要进一步统一余额、流水、营销资金、钱包核销的展示方式

建议版本：

- `V1`：账户中心稳定闭环
- `V1.1`：扩展筛选、流水口径、资金来源标识
- `V2`：统一钱包与营销资金协同

### 3.4 accounting-system / clearing-system / settlement-system

当前痛点：

- 业务链路已打通，但生产级真实性仍要继续补齐
- MySQL 实库迁移、MQ 可靠投递、补偿链路、回滚链路仍是重点

建议版本：

- `V1`：保持当前联调基线
- `V1.1`：补真实库、真实 MQ、真实补偿
- `V2`：形成业财协同与批量处理闭环

## 4. 迭代排序规则

优先级从高到低：

1. 影响主链路支付成功率的问题
2. 影响资金安全和审计的问题
3. 影响跨系统联动的问题
4. 影响运营效率的问题
5. 影响页面完整度和体验的问题

## 5. 版本判定口径

- `V1`：能稳定运行的最小闭环
- `V1.1`：补齐明显缺口但不改架构主干
- `V2`：需要结构升级、模型升级或多系统协同升级
- `Release`：可以作为阶段冻结版交付包

## 6. 执行方式

后续每轮开发都应先从本文件挑选本轮最高优先级项，再同步更新：

- 系统级设计文档
- 接口文档
- 数据库设计
- 自测记录
- 发布说明
