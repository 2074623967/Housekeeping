# 系统痛点与版本迭代池

## 1. 文档定位

本文档用于把各支付相关子系统在交付后的真实痛点、结构性缺口、下一步版本改造和验收标准统一收口。

它不是临时备注，而是后续持续迭代的唯一需求池入口之一。

## 2. 维护原则

1. 每个系统交付后，都要先写出当前版本的痛点。
2. 能在当前版本修掉的，直接进入当前迭代。
3. 需要改结构的，进入下一版本。
4. 不能立即落地但有明确价值的，保留为路线图。
5. 每一条痛点都要明确归属系统、影响范围、建议版本和验收标准。
6. 痛点不只来自缺陷，也来自产品、财务、架构、前端、测试和运营视角的结构性观察。
7. 明显涉及模型升级、流程重构、展示口径统一或迁移成本下降的内容，优先归入 `V2`，不要强行挤进 `V1`。
8. 每一轮迭代都要主动补充“本轮新发现的痛点”，形成持续推进机制，而不是只做需求清单的被动实现。

## 3. 当前高优先级痛点

### 3.1 payment-core

当前痛点：

- 仍有部分运营能力与正式生产版之间存在差距
- 真实渠道接入、对账前置事实收口、任务中心正式告警链路还需要继续增强
- 三端收银台、结果页、异常处理页的体验仍需继续细化
- 虽然正式来源应用和下游联动链路已有多轮 smoke 证据，但最新页面矩阵和最新主链路之间还缺一版统一验收记录
- 作为冻结版交付标准，目前更缺的是“页面级验收 + 版本级发布说明”，而不是继续零散补单点接口

建议版本：

- `V1.1`：补齐正式版告警、路由和监控细节
- `V1.2`：补齐真实渠道接入与稳定性治理
- `V2`：支付中台能力外溢到其他子系统联动

### 3.2 deposit-system

当前痛点：

- V1 只能支撑单主体单账户闭环
- 多规则、多品类、历史账户结转需要结构性升级
- 旧版“多个保证金账户并行”模型在规则归集、展示口径和迁移成本上越来越重
- 当前 V1 仍偏向“能用”，但对后续真实业务扩张来说，缺少总账户归集、规则绑定、迁移追溯和运营视图统一
- 如果继续只在 V1 上打补丁，后续会把规则、账户和历史迁移越堆越乱，测试和运营口径也会越来越难对齐

建议版本：

- `V1`：保持稳定交付
- `V2`：总保证金账户、规则绑定、旧账户结转
- `V2` 具体升级项：多个保证金账户收敛为总保证金账户，保留规则维度明细和历史结转链路
- `V2` 还应补齐：迁移预览、绑定预览、历史映射、总账户详情、运营台统一展示口径

### 3.3 wallet-account

当前痛点：

- 账户和业务对象之间的扩展口径仍需补齐
- 需要进一步统一余额、流水、营销资金、钱包核销的展示方式
- 钱包能力当前还存在“账户中心”和“资金动作中心”视角分裂的问题，后续需要补统一台账和导出留痕
- 如果营销、红包、核销继续直接耦合在账户层，后续会拉高账务侧复杂度

建议版本：

- `V1`：账户中心稳定闭环
- `V1.1`：扩展筛选、流水口径、资金来源标识
- `V2`：统一钱包与营销资金协同

### 3.4 accounting-system / clearing-system / settlement-system

当前痛点：

- 业务链路已打通，但生产级真实性仍要继续补齐
- MySQL 实库迁移、MQ 可靠投递、补偿链路、回滚链路仍是重点
- 这三类系统之间的交接边界还需要进一步以“事件 + 台账 + 对账”方式固化，避免后续靠人工口径对齐
- 面向大厂级落地标准，还需要把幂等、审计、重试、追踪、回单、批量作业和日终处理补成统一规范
- `clearing-system` 虽然已经补了失败派发重放入口和诊断字段，但目前还只是“能力点补齐”，没有形成同批次 replay / retry / DLQ / 人工结案的冻结版闭环证据
- `settlement-system` 与 `accounting-system` 目前更需要围绕“补偿完成后下游事实是否一致”补统一核验口径，而不只是各自继续长页面功能

建议版本：

- `V1`：保持当前联调基线
- `V1.1`：补真实库、真实 MQ、真实补偿
- `V2`：形成业财协同与批量处理闭环

### 3.5 发布治理与交付包

当前痛点：

- 当前 `test` 分支增量已经较多，但“最近一批次统一门禁复跑”和“可直接交付的发布候选包”之间仍有落差
- 发布文档已有模板和草案，但缺少基于当前代码基线、当前阻断项、当前数据库/接口/前端变化的正式候选版本说明
- 如果继续只做功能堆叠，不同步更新门禁审计和版本归属，后续自动判断何时合 `master`、何时切 `release/*` 会越来越失真

建议版本：

- `V1.1`：补齐 test 基线整包门禁复跑与发布候选说明
- `Release`：在补偿闭环、页面矩阵和版本文档同时达标后再冻结

## 3.6 本轮新发现痛点（2026-08-08）

1. 当前最大的阻断已经不再是“没有代码”，而是“最新代码基线缺少同批次统一证据”。
2. `master / release` 判定更需要版本治理能力，而不是继续依赖历史零散 smoke 记录。
3. 对冻结版来说，运行态补偿闭环、发布文档和页面矩阵复核已经成为比新增普通接口更高优先级的事项。

## 4. 迭代排序规则

优先级从高到低：

1. 影响主链路支付成功率的问题
2. 影响资金安全和审计的问题
3. 影响跨系统联动的问题
4. 影响运营效率的问题
5. 影响页面完整度和体验的问题

## 5. 版本判定口径

- `V1`：能稳定运行的最小闭环
- `V1.1`：补齐明显缺口但不改架构主干
- `V2`：需要结构升级、模型升级或多系统协同升级
- `Release`：可以作为阶段冻结版交付包

## 6. 执行方式

后续每轮开发都应先从本文件挑选本轮最高优先级项，再同步更新：

- 系统级设计文档
- 接口文档
- 数据库设计
- 自测记录
- 发布说明
