# 发布门槛与版本治理规范

## 1. 文档定位

本文档用于约束家政服务支付系统从 `feature/*` 到 `test`、从 `test` 到 `master`、再到 `release/*` 的正式发布门槛，避免“代码做了很多，但没有统一发版标准”的情况。

## 2. 分支推进门槛

### 2.1 `feature/*` 合入 `test`

必须同时满足：

1. 对应系统的需求文档、接口文档、前端交互说明、数据库设计至少完成本轮变更覆盖。
2. 代码实现完成，并与既有技能规范一致：
   - 后端遵循 `java-ponytail`
   - 前端遵循 `frontend-craftsman`
3. 本轮涉及的后端测试通过。
4. 本轮涉及的前端构建通过。
5. 自测记录已回填到对应系统文档。
6. `git diff --check` 通过。

### 2.2 `test` 合入 `master`

必须同时满足：

1. 本轮需求已达到“可给产品、前端、后端、测试直接使用”的冻结版交付标准。
2. 对应系统关键链路已完成至少一轮端到端自测。
3. `test` 分支无阻断级已知问题。
4. 核心文档齐全：
   - 需求/范围说明
   - 前端页面与交互说明
   - 后端详细设计
   - 接口文档
   - 数据库设计
   - 自测与联调记录
   - 当前交付状态说明
5. 同类产品对标后，没有明确遗漏但应进入本轮的 P0/P1 项。
6. 合并说明中写清楚版本范围、影响系统、风险点和回滚边界。

### 2.3 `master` 切 `release/*`

必须同时满足：

1. `master` 已经完成对应版本范围内的稳定收口。
2. 发布文档已经准备完成。
3. 数据库变更、接口变更、前端入口变更已明确。
4. 已形成已知风险清单。
5. 已形成发布后验证清单与回滚说明。

## 3. 发布文档要求

每次创建 `release/*` 时，必须在 `docs/releases/` 下新增对应版本文档，至少包括：

1. 版本号
2. 发布日期
3. 发布范围
4. 本次功能清单
5. 数据库变更
6. 接口变更
7. 前端变更
8. 测试结论
9. 已知风险
10. 回滚说明
11. 发布后验证项

## 4. 当前执行原则

截至 `2026-08-08`：

1. 当前自动化开发主线仍为本地 `test`，且相对 `origin/test` 已持续积累多轮增量提交，说明系统处于持续迭代收口而非单点补丁阶段。
2. `master / release/*` 仍停留在更早的发布基线，尚未接收这一轮持续演进中的冻结版候选范围。
3. `payment-core`、`clearing-system`、`settlement-system`、`accounting-system`、`wallet-account`、`deposit-system` 等子系统都在继续补“冻结版证据”，而不只是补代码。
4. 在运行态补偿链路、最新整包门禁和正式发布候选文档未形成同批次闭环前，不得仅凭历史 smoke 或旧发布草案推进 `test -> master`。

后续自动化推进时，应优先继续补齐关键缺口，再择机推进 `test -> master -> release/*`。

## 5. 自动合并与自动发布判定规则

后续允许由 Codex 自动推进 `test -> master -> release/*`，但必须严格遵守以下判定，不以“开发做了很多”为依据，而以“冻结版质量是否达标”为依据。

### 5.1 允许自动合入 `master` 的条件

必须同时满足：

1. 当前 `feature/*` 对应的 P0/P1 范围已经形成阶段性闭环，不再是明显半成品。
2. `test` 分支已经包含本轮代码，且最新验证结果完整：
   - 后端自动化测试通过
   - 前端相关端构建通过
   - 自测与联调记录已更新
3. 对应系统文档已达到可直接给产品、前端、后端、测试、AI 开发共同使用的标准。
4. 当前已知问题中不存在阻断级缺陷、核心链路断裂、关键页面缺失、关键接口未实现这四类问题。
5. 同类产品对标后，本轮应该补进来的 P0/P1 项已经补齐，剩余缺口明确属于后续迭代而非当前冻结版阻断项。

### 5.2 允许自动创建 `release/*` 的条件

必须同时满足：

1. `master` 已完成一轮稳定观察，未发现新增阻断问题。
2. 版本范围、数据库变更、接口变更、前端入口变更、风险点、回滚方案均已写入发布文档。
3. 发布后验证项已经列明，并能覆盖核心支付链路、退款链路、配置链路和异常处理链路。
4. 本次版本可以被视为一个完整可交付里程碑，而不是单个零散功能点。

### 5.3 当前判断

截至 `2026-08-08`：

1. 当前仍不满足自动合入 `master` 条件。
2. 当前仍不满足自动创建 `release/*` 条件。
3. 当前“运行态补偿闭环”已从阻断项中移除，但“页面级冻结截图归档 + 最终人工回归归档 + 最终发布候选文档”仍未完成。
4. 当前正确策略是在本地 `test` 上继续推进“页面冻结证据 + 最终回归归档 + 发布候选包”三件事。
5. 若当前线程没有权限启动服务或消费 MQ，只允许完成静态核对、数据库结构补齐、单元测试和文档证据沉淀，不得伪造运行态通过结论。

## 6.1 2026-08-08 当前自动推进决策

结合最近一轮 `clearing-system` 失败派发重放补强、`deposit-system` V2 路线收敛和既有跨系统 smoke 证据，当前自动化推进应遵循以下顺序：

1. 继续允许把已验证通过的局部能力提交到 `test`。
2. 暂不自动把 `test` 合并到 `master`。
3. 暂不自动创建新的 `release/*`。
4. 只有当以下三类证据在同一阶段同时齐备时，才重新评估 `master / release`：
   - 最新 `test` 基线的整包统一回归结果
   - 页面级冻结截图与最终人工回归归档
   - 基于当前代码基线的正式发布候选文档

这意味着后续自动化开发不应该只追求“功能继续变多”，而要主动把系统往“可冻结、可发布、可回滚、可复核”的交付状态推进。

## 7. 运行态门禁补充

涉及 MySQL、RabbitMQ、Redis、Nacos、服务进程启动、真实 MQ 消费、补偿任务落库、发布后验证等动作时，必须遵守以下规则：

1. 明确区分“静态检查通过”“单元测试通过”和“真实运行态通过”。
2. 数据库迁移必须使用仓库内幂等脚本，执行后记录脚本路径、库名、表名和字段备注结果。
3. MQ 相关门禁必须记录 broker 地址、vhost、exchange、queue、routing key、消息 ID、业务单号和队列快照。
4. DLQ 消息不得直接删除；必须先核对补偿任务账本、下游事实和人工结案状态。
5. 若运行态动作被权限或审批系统拦截，应记录为“权限未授权”，不得降级描述为“已通过”。
6. 只有补偿链路真实完成后，才允许把该项从 `master/release` 阻断项中移除。
