## 3. 逐项闭环要求

### 3.1 正式版发布说明

来源约束：

1. 范围必须与 `docs/releases/v1.1.0-发布说明-候选版.md` 一致，不允许在正式放行阶段混入新功能
2. 测试结论必须引用 `docs/releases/evidence/test-20260809-regression/records/regression-summary.md`
3. 风险和回滚说明必须回链到正式回滚演练记录和现场核验记录

完成判定：

1. 正式文档存在且包含版本号、发布日期、范围、测试结论、风险、回滚、核验项
2. 文档中不再保留 `候选版`、`待确认`、`暂不切 release/*` 等表述

### 3.2 正式签字审批

来源约束：

1. 不得仅保留 `预审通过`
2. 审批结论必须建立在 `回滚演练实录 + 现场核验实录 + 观察结束结论` 三项真实记录之上

完成判定：

1. 产品、财务产品/资金、后端架构、前端、测试五类角色逐项签字
2. 清单明确最终结论为 `允许切版` 或 `继续暂缓`

### 3.3 回滚演练实录

最少覆盖：

1. 回退 `payment-core` 冻结候选增量
2. 回退后复核 `支付 -> 清分 -> 结算 -> 账务` 主链路
3. 恢复到候选基线后再次复核主链路

完成判定：

1. 有实际演练日期、执行人、步骤、结果
2. 若发现问题，已给出风险等级和后续动作
3. 若未发现问题，明确写明 `未发现阻断级问题`

### 3.4 发布后现场核验实录

最少覆盖：

1. 用户端 `App / H5 / PC` 支付入口和结果页
2. 后台 `订单中心 / 支付单 / 退款单 / 异常中心 / 任务中心`
3. 下游 `清分结果 / 结算单 / 账务承接`
4. 金额一致性：支付金额、清分金额、结算金额、账务金额

完成判定：

1. 每一项均有 `通过 / 不通过 / 需跟踪` 结论
2. 所有 `需跟踪` 项必须有责任人和期限

### 3.5 `master` 观察结束结论

最少覆盖：

1. 观察期是否出现新增阻断级缺陷
2. 是否存在资金事实不一致
3. 现场核验是否全部通过
4. 回滚演练后是否可恢复

完成判定：

1. 明确写出观察起止时间
2. 明确写出最终结论：`允许继续推进 release/v1.1.0` 或 `继续暂缓`

## 4. 今日建议执行顺序

1. 先完成回滚演练实录，因为它既是审批输入，也是正式版发布说明的回滚依据
2. 再完成发布后现场核验实录，补齐前端、财务、测试共同关注的事实上线检查
3. 随后由测试负责人形成 `master` 观察结束结论
4. 最后再升级审批清单和正式版发布说明
