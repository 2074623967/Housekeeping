# 2026-08-08 发布后验证清单

> 适用范围：当前 `test` 基线冻结候选包
> 状态：候选验证清单

## 1. 文档目的

本清单用于约束后续从 `master` 切 `release/*` 时，发布后必须核对哪些真实结果，避免“代码上线了，但没有统一验收闭环”。

## 2. 核心主链路验证

### 2.1 正向支付主链路

必须至少覆盖一笔真实样例：

1. 创建预付单
2. 提交支付
3. 进入 `WAIT_CALLBACK`
4. 渠道成功回调
5. 支付单收口为 `SUCCESS`

建议核对项：

| 验证项 | 通过标准 |
| --- | --- |
| `POST /api/payments/prepay` | 成功生成 `prepayOrderNo / paymentOrderId / billNo` |
| `POST /api/payments/submit` | 支付单进入 `WAIT_CALLBACK` |
| `POST /api/payments/callback/{channelCode}` | 支付单正确收口为 `SUCCESS` |
| `GET /api/payments/{paymentOrderId}` | 支付状态、渠道状态、结果页状态一致 |

### 2.2 风控与关闭链路

必须核对：

1. `RISK_REVIEW` 状态下不能继续错误提交
2. `SUCCESS` 状态下重复成功回调不会错误改写状态
3. `SUCCESS` 状态下关闭接口不会错误收口为 `CLOSED`
4. `CLOSED` 状态下不允许继续模拟成功回调

## 3. 页面验证

### 3.1 多端结果页

必须核对以下页面：

1. `app-web` 支付结果页
2. `h5-web` 支付结果页
3. `pc-web` 支付结果页

必须覆盖以下状态：

1. `WAIT_CALLBACK`
2. `RISK_REVIEW`
3. `SUCCESS`
4. `CLOSED`

通过标准：

1. 文案一致
2. 按钮禁用逻辑一致
3. 不把关键状态统一折叠成“处理中”

### 3.2 后台页

必须核对：

1. 订单中心能跳到支付单和收银台
2. 支付单详情能看到正确状态和建议动作
3. 支付流水、支付事件、异常中心都能定位同一笔主链路样例

## 4. 下游自动联动验证

### 4.1 清分系统

必须核对：

1. 生成 `PAYMENT_SUCCESS` 消费事件
2. 生成清分单
3. `CLEARING_GENERATED` 事件可追溯

### 4.2 结算系统

必须核对：

1. 清分结果进入结算单
2. 结算单状态正确
3. 出款批次与出款记录可查询

### 4.3 账务系统

必须核对：

1. 支付成功事件已消费
2. 清分生成事件已消费
3. 若有补偿事件，本轮样例中必须可追溯

## 5. 补偿链路验证

这部分已在当前 `2026-08-08` test 基线补齐，不再是当前最关键阻断项，但正式进入 `master / release` 时仍必须可复核：

1. retry 回流验证
2. DLQ 入池验证
3. 人工结案验证
4. replay 重放验证
5. 补偿完成后下游事实一致性验证

建议留档项：

| 项目 | 必须留档内容 |
| --- | --- |
| retry | 业务单号、队列快照、回流前后状态 |
| DLQ | 任务号、消息主题、失败原因、下游事实 |
| 人工结案 | 操作人、结案原因、结案前后状态 |
| replay | 触发时间、重放数量、重放后事实 |

## 6. 运维与回滚验证

发布候选包至少要能回答以下问题：

1. 哪些接口新增或调整了
2. 哪些前端入口受影响
3. 是否有数据库结构变更
4. 是否只需清理演练数据即可回滚
5. 回滚后需要重新验证哪些主链路页面和接口

## 7. 当前结论

这份清单的意义不是证明“现在已经能发版”，而是明确：

1. 后续要发版时必须验什么
2. 当前哪些项已经有证据
3. 当前哪些项仍然缺失

截至 `2026-08-08`，当前最关键的剩余项是：

1. 最新多端页面截图归档
2. 页面、接口、后台事实、下游事实统一口径的人工回归归档
3. 基于正式候选版本号的最终发布说明
