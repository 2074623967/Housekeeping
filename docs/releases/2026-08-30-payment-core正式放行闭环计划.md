# 2026-08-30 payment-core 正式放行闭环计划

> 适用范围：`payment-core` 优先，联动 `clearing-system / settlement-system / accounting-system`
> 当前日期：`2026-08-30`
> 当前结论：`test -> master = 是`，`release/* = 否`
> 目标：在不伪造审批和演练事实的前提下，补齐 `v1.1.0` 正式放行所缺治理证据

## 1. 当前门禁事实

依据 `2026-08-30` 统一门禁审计，当前结论如下：

| 项目 | 结果 |
| --- | --- |
| 回归证据包收口 | `是` |
| `test -> master` | `是` |
| release 材料结构完整性 | `通过` |
| `release/*` | `否` |

当前唯一顶层阻断为：`release 正式放行条件仍未闭环`。

展开后仍缺 `5` 项真实治理事实：

1. 候选版发布说明尚未升级为正式版
2. 正式签字审批结果尚未形成
3. 回滚演练缺少实际演练记录
4. 发布后现场核验缺少实际记录
5. `master` 稳定观察结束结论尚未形成

## 2. 本轮推进原则

1. 不补新功能，不扩大 `payment-core` 范围，先完成正式放行治理闭环
2. 不用“模板已齐”替代“实际已发生”
3. 所有新增记录必须能回链到现有候选版发布材料和回归证据包
4. 仍以 `payment-core` 为主系统，其余子系统只提供主链路配套证据

## 3. 角色闭环矩阵

| 角色 | 必做动作 | 输出物 | 完成判定 |
| --- | --- | --- | --- |
| 产品负责人 | 确认本版范围不再混入其他子系统新增需求 | `v1.1.0` 正式版发布说明 | 发布说明状态改为正式版，范围与候选版一致 |
| 财务产品/资金负责人 | 复核支付、清分、结算、账务主链路资金事实一致性 | 发布后现场核验实际记录 | 关键资金口径逐项签字，无未解释差异 |
| 后端架构负责人 | 组织一次可回放的正式回滚演练 | 回滚演练实际记录 | 演练步骤、结果、风险和恢复结论完整 |
| 前端负责人 | 配合发布后核验，确认四端入口与后台关键页可用 | 发布后现场核验实际记录 | 四端主入口和后台关键页核验完成 |
| 测试负责人 | 汇总观察期问题、回归结果和现场核验结论 | `master` 稳定观察结束结论 | 明确允许或不允许继续推进 `release/v1.1.0` |
| 发布审批人 | 基于以上事实完成正式签字 | 发布审批清单实际签字结果 | 审批状态变为 `正式签字完成` 或 `审批完成` |

## 4. 建议执行顺序

### 4.1 第一步：完成正式回滚演练

目标：

1. 证明当前 `payment-core` 主链路冻结候选具备可回退能力
2. 为正式签字审批提供真实输入，而不是继续停留在方案状态

最少覆盖：

1. 回退 `payment-core` 相关冻结候选增量
2. 回退后复核 `支付 -> 清分 -> 结算 -> 账务` 主链路
3. 演练后恢复到当前候选基线

应补文档：

1. `docs/releases/2026-08-09-v1.1.0回滚演练记录.md`

### 4.2 第二步：完成发布后现场核验实录

目标：

1. 把模板改成真实记录
2. 覆盖产品、前端、财务、测试共同关注的上线即检项

最少覆盖：

1. 用户支付链路：`App / H5 / PC`
2. 后台核心运营链路：订单中心、支付单、退款、异常中心、任务中心
3. 下游事实链路：清分结果、结算单、账务承接
4. 资金一致性核验：支付金额、清分金额、结算金额、账务金额

应补文档：

1. `docs/releases/2026-08-09-v1.1.0发布后现场核验记录模板.md`

### 4.3 第三步：形成 `master` 稳定观察结束结论

目标：

1. 给出观察期结束后的正式结论
2. 明确是否允许继续推进 `release/v1.1.0`

最少覆盖：

1. 观察期内是否出现新增阻断级缺陷
2. 是否存在资金事实不一致
3. 是否存在回滚后无法恢复的问题
4. 现场核验是否全部通过

应补文档：

1. `docs/releases/2026-08-09-master稳定观察结束结论模板.md`

### 4.4 第四步：完成正式签字审批

目标：

1. 以实际演练和实际核验为基础完成签字
2. 把当前“预审完成”推进为正式结论

应补文档：

1. `docs/releases/2026-08-09-v1.1.0发布审批清单.md`

### 4.5 第五步：升级正式版发布说明并决定是否切版

前提：

1. 上述 `4` 项记录均已形成真实结果
2. 观察结束结论明确允许继续推进 `release/v1.1.0`

应补文档：

1. `docs/releases/v1.1.0-发布说明-候选版.md`
2. 若正式放行成立，再新增 `docs/releases/v1.1.0-发布说明.md`

## 5. 各角色最小验收口径

### 5.1 财务产品经理

1. 支付成功金额、清分金额、结算金额、账务金额一致
2. 退款与补偿链路无未解释差异
3. 现场核验记录可用于审计追溯

### 5.2 架构师 / 后端

1. 当前 Java 改动和相关测试通过
2. 门禁脚本结论与发布文档结论一致
3. 回滚演练后可恢复到候选基线

### 5.3 前端

1. 四端支付入口和结果页可用
2. 后台关键页无阻断级展示错误
3. 截图、文案、状态字段与 PRD 口径一致

### 5.4 测试

1. 观察期缺陷已收口或明确不阻断
2. 现场核验项逐项有结果
3. 最终结论能支持“允许切版”或“继续暂缓”二选一

1. 以 `2026-08-30` 的事实，`payment-core` 已达到 `test -> master` 门槛
