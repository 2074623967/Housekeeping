# 2026-08-08 补偿闭环执行与验收手册

> 适用范围：当前 `test` 基线冻结候选包
> 目标：把 `retry / DLQ / replay / 人工结案` 从“已有历史证据”推进为“后续每轮都可重复执行的标准手册”

## 1. 文档定位

本手册不是为了重复解释 MQ 原理，而是为后续 `test -> master -> release/*` 提供一套统一的补偿闭环执行标准。

它解决三个问题：

1. 当前系统已经具备哪些补偿能力
2. 每次新版本要怎么重新演练
3. 什么情况下才算真正补齐“补偿闭环”门禁

## 2. 当前已具备能力

基于现有代码和历史证据，当前已经具备：

1. `payment-core` 死信补偿任务台账
2. `payment-core` 人工结案入口
3. `payment-core` 审核后定向 replay 入口
4. `clearing-system` 失败派发人工重放入口
5. RabbitMQ 隔离拓扑脚本
6. RabbitMQ 快速 retry TTL 演练能力
7. `payment.success.*` 与 `clearing.generated.*` 两条链路的历史补偿演练证据

## 3. 本轮冻结候选必须覆盖的补偿链路

### 3.1 `payment.success.*`

必须覆盖：

1. consumer 失败后进入 retry
2. retry TTL 到期回流主队列
3. 达到上限后进入 DLQ
4. `payment-core` intake 生成补偿任务
5. 补偿任务人工结案或审核后 replay

### 3.2 `clearing.generated.*`

必须覆盖：

1. `settlement-system` 消费失败后的 retry / DLQ
2. `accounting-system` 消费失败后的 retry / DLQ
3. `payment-core` intake 生成补偿任务
4. 必要时人工结案
5. 必要时 replay 或下游补事实

### 3.3 下游事实核验

如果本轮演练选择 replay 或补偿成功场景，则必须继续核对：

1. `clearing-system` 事件状态
2. `settlement-system` 结算/出款事实
3. `accounting-system` 事件和账务流水事实

不能只停留在“消息重发成功”，还要核对“业务事实是否正确收口”。

## 4. 标准执行步骤

### 4.1 声明隔离拓扑

常规演练：

```bash
bash infra/rabbitmq/declare_isolated_topology.sh <suffix>
```

快速 retry 演练：

```bash
RETRY_TTL_MS=2000 bash infra/rabbitmq/declare_isolated_topology.sh <fast-suffix>
```

执行要求：

1. 每轮必须使用新的后缀，禁止复用历史后缀污染证据。
2. 必须记录 suffix、声明时间、使用的 TTL。

### 4.2 记录初始快照

```bash
bash infra/rabbitmq/queue_snapshot.sh '<suffix>|payment.compensation'
```

必须记录：

1. 主队列数量
2. retry 队列数量
3. DLQ 数量
4. 消费者在线状态

### 4.3 注入演练消息

至少要覆盖两类：

1. 非法 JSON / 主数据缺失
2. 可被人工审核后 replay 的有效补偿样例

必须记录：

1. `messageId`
2. `correlationId`
3. `exchange`
4. `routingKey`
5. payload 摘要
6. headers，尤其是 `x-retry-count`

### 4.4 补偿任务核验

通过 `payment-core` 的死信任务查询页或接口，核对：

1. 是否生成补偿任务
2. 任务状态是否为 `PENDING_REVIEW`
3. 是否保留原始头信息、死信路由和错误摘要

### 4.5 人工处置

根据消息类型二选一：

1. 非安全消息：人工结案
2. 可恢复消息：`ready-to-replay -> replay`

必须记录：

1. 操作人
2. 操作时间
3. 操作备注
4. 处置后状态

### 4.6 下游事实核验

如果执行了 replay，必须继续核对：

1. replay 后是否进入专属 replay / retry 路径
2. 是否串错到其他消费者
3. 目标系统是否生成预期业务事实
4. 是否触发重复事实膨胀

## 5. 留痕模板

每轮演练至少要留以下字段：

| 分类 | 必填字段 |
| --- | --- |
| 基本信息 | 日期、执行人、复核人、分支、提交号、suffix、TTL |
| 消息证据 | `messageId`、`correlationId`、exchange、routing key、payload 摘要 |
| 队列证据 | 演练前快照、演练后快照、主/retry/DLQ 数量 |
| 任务证据 | `taskNo`、任务状态、错误原因、头信息快照 |
| 处置证据 | 人工结案或 replay 的接口、操作人、备注、结果 |
| 业务证据 | clearing / settlement / accounting 的事实编号与状态 |

## 6. 冻结版通过标准

只有同时满足以下条件，补偿闭环门禁才可判定为“通过”：

1. `payment.success.*` 和 `clearing.generated.*` 两条链路都完成本轮演练
2. retry、DLQ、任务入账、人工处置四个环节都留下真实证据
3. replay 场景能证明不会串消费者，也不会造成事实重复膨胀
4. 人工结案场景能证明原始审计副本仍保留
5. 证据属于当前代码基线，不是仅引用历史旧批次

## 7. 当前仍未完全关闭的点

截至 `2026-08-08`，现有仓库已经有历史补偿证据，但从冻结候选角度仍有两个缺口：

1. 缺少与最新 `2026-08-08` test 基线完全同批次的补偿闭环复跑记录
2. 缺少把补偿闭环与多端页面验收、发布候选包统一绑定后的最终版本判断

这也是为什么现在仍不应推进 `test -> master` 或 `release/*`。
