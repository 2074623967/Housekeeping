# 整包数据库初始化与回滚演练

## 1. 文档定位

本文档用于沉淀家政服务支付系统在 `2026-07-29` 当前基线下的整包数据库初始化、基础回滚和发布前演练口径，避免进入 `master / release` 前只验证代码和页面，却没有验证数据库交付包。

## 2. 当前纳入演练范围的系统

| 系统 | 数据库名 | 初始化脚本 |
| --- | --- | --- |
| `payment-core` | `housekeeping_payment_core` | `systems/payment-core/database/schema.sql` + `data.sql` |
| `wallet-system` | `housekeeping_wallet` | `systems/wallet-system/database/schema.sql` + `data.sql` |
| `gateway-access` | `housekeeping_gateway_access` | `systems/gateway-access/database/schema.sql` |
| `clearing-system` | `housekeeping_clearing` | `systems/clearing-system/database/schema.sql` |
| `settlement-system` | `housekeeping_settlement` | `systems/settlement-system/database/schema.sql` |
| `accounting-system` | `housekeeping_accounting_system` | `systems/accounting-system/database/schema.sql` |

## 3. 初始化原则

1. 每个系统独立数据库，不允许多系统共库。
2. 先执行 `schema.sql`，再执行 `data.sql`；没有 `data.sql` 的系统只执行建表脚本。
3. 初始化失败时，只回滚当前系统库，不影响其他系统库。
4. 发布前至少完成一轮“空库初始化 -> 核心查询验证 -> 删除库回滚”的演练。

## 4. 推荐初始化顺序

1. `payment-core`
2. `wallet-system`
3. `gateway-access`
4. `clearing-system`
5. `settlement-system`
6. `accounting-system`

说明：

- 先初始化支付核心和钱包，有利于后续演练支付主链路与资金侧依赖。
- 再初始化接入、清分、结算、账务四个后续联动系统。

## 5. 初始化命令模板

以本机 MySQL 为例：

```bash
mysql -uroot -p < systems/payment-core/database/schema.sql
mysql -uroot -p housekeeping_payment_core < systems/payment-core/database/data.sql

mysql -uroot -p < systems/wallet-system/database/schema.sql
mysql -uroot -p housekeeping_wallet < systems/wallet-system/database/data.sql

mysql -uroot -p < systems/gateway-access/database/schema.sql
mysql -uroot -p < systems/clearing-system/database/schema.sql
mysql -uroot -p < systems/settlement-system/database/schema.sql
mysql -uroot -p < systems/accounting-system/database/schema.sql
```

## 6. 发布前最小验证项

初始化完成后，至少验证：

1. 六个数据库均可正常创建。
2. `payment-core` 可查询到支付渠道、路由规则、支付单、退款单演示数据。
3. `wallet-system` 可查询到钱包账户、流水、充值单、提现单演示数据。
4. `gateway-access / clearing-system / settlement-system / accounting-system` 的主表均已创建成功。
5. 任一系统重复执行 `schema.sql` 不应因已存在对象而直接阻断。

## 7. 回滚口径

### 7.1 代码回滚

1. 若仅为文档或脚本问题，直接回滚对应 Git 提交。
2. 若伴随代码改动，按系统维度回滚对应提交，不跨系统联动回退无关模块。

### 7.2 数据回滚

当前阶段按“系统级删库重建”口径回滚：

```sql
DROP DATABASE IF EXISTS housekeeping_payment_core;
DROP DATABASE IF EXISTS housekeeping_wallet;
DROP DATABASE IF EXISTS housekeeping_gateway_access;
DROP DATABASE IF EXISTS housekeeping_clearing;
DROP DATABASE IF EXISTS housekeeping_settlement;
DROP DATABASE IF EXISTS housekeeping_accounting_system;
```

说明：

1. 当前适用于本地、自测、联调和预发布演练环境。
2. 进入正式发布阶段后，需要把“删库重建”升级为“增量 DDL 回滚 + 数据修复脚本”。

### 7.3 配置回滚

1. 回滚各系统 `application.yml` 到上一个稳定版本。
2. 校验连接库名、用户名、密码、端口是否恢复为上版值。
3. 若涉及前端环境变量或网关地址，也需同步回退。

## 8. 当前判断

1. 目前整包数据库交付结构已从“部分系统有脚本、部分系统没有标准目录”补齐到六个系统均具备可引用的数据库初始化入口。
2. 当前仍未完成真实 MySQL 演练证据、增量 DDL 版本脚本和正式发布回滚包，因此这一步属于发布门槛补强，而不是直接触发 `master / release`。

## 10. 2026-07-31 payment-core 增量 DDL 演练

### 10.1 背景

在 `2026-07-31` 的真实 backend 联调中，`payment-core` 四块导出已经完成真实下载验证；同时也暴露出原始运行库 `housekeeping_payment_core` 曾缺少 `t_payment_task_lease`，以及历史递归升级告警可能把 `alert_content` 推高到字段上限，导致最新 backend 的任务中心自动任务无法稳定落库。

### 10.2 本轮增量脚本

| 系统 | 增量脚本 | 作用 |
| --- | --- | --- |
| `payment-core` | `systems/payment-core/database/migrations/2026-07-31-add-payment-task-lease.sql` | 给原始运行库补齐 `t_payment_task_lease`，让任务中心租约锁能力可落库 |

### 10.3 本轮演练口径

1. 保留原始 `housekeeping_payment_core` 业务数据，不执行整库重建。
2. 只执行单表增量 DDL：`t_payment_task_lease`。
3. 执行后需验证三件事：
   - 原始运行库已可查询到 `t_payment_task_lease`
   - 最新 backend 连接原始运行库后，不再因该表缺失报错
   - 四块导出接口仍可正常返回下载响应
4. 本轮实际复验结果：
   - 原始运行库已可查询到 `t_payment_task_lease`
   - 最新 backend 已在 `2026-07-31 19:36:42` 成功写出 `PAYMENT_ISSUE_ESCALATE` 自动任务日志，不再报 `t_payment_task_lease` 缺表或 `alert_content` 越界
   - 历史递归升级告警清理脚本 `systems/payment-core/database/migrations/2026-07-31-ack-legacy-recursive-issue-alerts.sql` 已执行，原始运行库中的 `7` 条递归 outbox 告警已从 `待确认` 收口为 `已确认`
   - 清理后保留了 `ack_operator=data-fix-20260731` 与 `triggered_by=payment-core-alert-cleanup-2026-07-31` 审计痕迹，便于后续复核
