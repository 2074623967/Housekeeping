# 本地可运行骨架与功能矩阵

更新时间：2026-09-13

## 1. 本轮目标

本轮先完成“整套系统有架子且能用”，再进入并发治理、真实外部集成和正式发布。

这里的“能用”必须同时满足：

1. 后端能够启动，核心查询接口返回成功。
2. 前端能够启动，并通过同源代理访问对应后端。
3. 用户可以进入核心页面，查看真实接口数据，并执行当前阶段已经实现的主要动作。
4. 本地运行、状态检查、冒烟和停止方式统一，不依赖逐个系统手工拼命令。

它不等于生产就绪。真实渠道、生产数据源、统一身份权限、真实 MQ、分布式一致性、容量验证和发布审批仍需单独验收。

## 2. 统一运行基线

```bash
tools/dev/local-stack.sh doctor all
tools/dev/local-stack.sh up all
```

运行中检查：

```bash
tools/dev/local-stack.sh status all
tools/dev/local-stack.sh smoke all
tools/dev/local-stack.sh happy-path
```

停止方式：

- `up`：在托管终端按 `Ctrl-C`，脚本清理本次启动的进程。
- `start`：执行 `tools/dev/local-stack.sh stop all`。
- 可以用 `backends`、`frontends` 或系统目录名替换 `all`，只控制目标范围。

本地运行产物：

- 日志：`.runtime/local-stack/logs/`
- PID：`.runtime/local-stack/pids/`

## 3. 功能矩阵

状态口径：

- `A-闭环演示`：本地数据源下可以走通主要业务状态变化，并有较完整自动化测试。
- `B-功能骨架`：页面、接口、持久化和主要动作均已落位，可用于功能联调；外部依赖仍是本地实现或受控边界。
- `C-生产待接`：真实渠道、生产中间件、权限、容量或运营审批尚未完成，不可据此判断生产可用。

## 4. 2026-09-13 本地验证结果

统一脚本已验证：

- 12 个后端核心查询接口均为 `READY`。
- 15 个前端入口均为 `READY`。
- 15 条前端到后端代理冒烟均通过。
- `payment-core` demo 工作台、监控和任务中心使用真实后端查询，不再依赖页面静态兜底。
- 本地支付成功可自动生成清分单、待审核结算单，并触发支付成功与清分结果记账；可用 `happy-path` 重复验证。
- 本地退款成功 outbox 可真实派发到账务和对账系统，生成唯一借方冲回流水与 `REFUND_SUCCESS` 对账事实；重复派发不重复记账。
- `wallet-system` 和 `wallet-account` 的真实 Spring + H2 Mapper 集成测试通过。
- 15 个前端生产构建通过。
- 支付后台、钱包账户、钱包后台在 `1440px` 和 `390px` 视口下均无整页横向溢出；宽表保留在表格容器内部滚动。
- `gateway-access`、`risk-control-system` 与 `wallet-system` 的业务表格已补齐零数据空态；钱包账户加载和详情请求失败后可结束 loading 并展示错误，不会卡死页面。
- `deposit-system`、`ops-config-system` 与 `reconciliation-system` 的业务表格已补齐零数据空态；`refund-center` 的日志空态和关键动作进行中状态已补齐，可防止重复提交。
- `wallet-account` 的账户、最近流水、流水查询和导出任务已补齐零数据空态，查询过程中按钮会锁定并显示进行中状态。

## 5. 下一步顺序

1. 项目级跨系统 happy path 已覆盖支付成功到清分、结算、账务，以及退款成功到记账与对账事实。
2. 下一步补全 12 个系统的加载、空态、失败态和关键动作验收，确保不是只有首页可访问。
3. 然后深挖 `payment-core` 并发幂等、状态竞争、补偿一致性和容量基线。
4. 最后重新执行 `test -> master -> release` 门禁审计；审批、签字、现场核验和正式发布结论只能使用真实证据。
