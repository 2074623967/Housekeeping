# 家政服务支付系统痛点雷达与持续迭代清单

> 目标：把财务、产品、架构、前端、测试和运营视角发现的问题，统一沉淀为可执行的需求池，并绑定设计、开发、测试、证据和发布门禁。
>
> 当前基线：`test`，日期：`2026-08-09`

## 1. 使用原则

每个痛点必须形成一条可追溯的闭环：

`问题事实 -> 业务影响 -> 需求编号 -> 方案设计 -> 代码变更 -> 自动化测试 -> 运行证据 -> Git 提交 -> 发布门禁`

禁止只记录“以后优化”，不允许没有负责人、验收标准和优先级的泛化待办进入冻结版。

## 3. 当前迭代顺序

### Iteration A：冻结版阻断项

1. 补齐 `REG-01 ~ REG-06 / REG-09` 的失败回滚或补偿证据。
2. 完成 `REG-10` 日终真实批次、数据库事实、事件台账和页面截图。
3. 将当前证据包审计结果与 Git 提交号自动绑定。
4. 重新运行回归审计；未满足条件前不合并 `master`，不创建 `release/*`。

### Iteration B：财务闭环

1. 对账系统接入支付日终事实快照。
2. 建立渠道账单、内部支付事实、清分事实、结算事实、账务事实的统一差异模型。
3. 建立差异认领、责任分派、补单、退款、冲正、调账和人工结案流程。
4. 增加保证金账户、合并保证金账户、保证金扣款/退还与支付链路的统一追踪。

本轮已落地：

- `PAIN-001`：批次级对账准入门禁已完成，后续继续补渠道账单自动接入、日终批次批量导入和差异工单编排。

### Iteration C：运营产品化

1. 建设统一支付运营工作台。
2. 将异常、补偿、日终、对账和配置变更统一为待办与任务。
3. 增加权限、双人复核、操作原因、影响范围和审计导出。
4. 接入真实通知通道和值班表，并验证升级、回执和静默策略。

### Iteration D：规模化与稳定性

1. 增加高并发支付、重复回调、重复消费、超时、数据库故障和 broker 故障演练。
2. 完善分库分表、归档、读写分离和批次化日终策略。
3. 建立 SLO：支付回调收口、事件投递、补偿处置、日终完成和对账准入。
4. 将所有系统的发布前检查统一接入自动化门禁。

## 5. 当前禁止事项

1. 不得把历史截图或历史补偿记录直接标记为当前版本通过。
2. 不得用“接口返回成功”替代数据库事实和下游业务事实。
3. 不得覆盖用户未提交的审计、交付状态和自测记录。
4. 不得在真实补偿、页面冻结、稳定观察和审批未完成前推进 `master/release`。
