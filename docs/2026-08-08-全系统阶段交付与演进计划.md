# 2026-08-08 全系统阶段交付与演进计划

> 适用范围：家政服务支付平台全系统
> 计划基线日期：`2026-08-08`
> 目标：让系统持续看起来像真实公司内部持续迭代中的支付平台，而不是一次性拼凑的演示工程

## 1. 计划定位

本计划用于统一回答三个问题：

1. 现在先交付哪个系统、为什么
2. 每个系统当前属于 `冻结收口 / V1 稳定化 / V2 架构升级` 哪个阶段
3. 后续如何在不打乱主线的情况下持续推进其他子系统

## 2. 当前总体策略

当前采用“三层并行推进”策略：

1. `Layer 1`：先把 `payment-core + clearing-system + settlement-system + accounting-system` 打造成首个可冻结交付主链路
2. `Layer 2`：把 `ops-config-system + risk-control-system + gateway-access` 打造成支撑型治理层
3. `Layer 3`：把 `deposit-system + wallet-account / wallet-system + refund-center + reconciliation-system` 打造成业财资金域扩展层

## 3. 阶段划分

### 3.1 Phase A：冻结候选主链路收口

目标：

1. 让支付主链路具备 `test -> master` 的重新评估基础
2. 把当前阻断从“功能是否存在”收敛到“冻结证据是否完整”

覆盖系统：

1. `payment-core`
2. `clearing-system`
3. `settlement-system`
4. `accounting-system`

当前重点：

1. 页面级冻结截图
2. 一体化人工回归归档
3. 冻结候选发布说明与放行结论

### 3.2 Phase B：治理层正式化

目标：

1. 把运营配置、风控、接入治理从“功能骨架”补成“真实治理层”
2. 减少 `payment-core` 内部继续堆叠过多泛治理逻辑

覆盖系统：

1. `ops-config-system`
2. `risk-control-system`
3. `gateway-access`

必须补的能力：

1. 配置版本治理、审批、灰度窗口和跨系统下发
2. 风控人工复核与支付主链路的跨系统正式 smoke
3. 渠道接入、证书治理、签名验签、环境路由和发布阶段控制

### 3.3 Phase C：资金域扩展与架构升级

目标：

1. 把资金类子系统从“单功能能用”推进到“多系统协同可扩展”
2. 主动吸收文档中已经出现的架构升级信号

覆盖系统：

1. `deposit-system`
2. `wallet-account`
3. `wallet-system`
4. `refund-center`
5. `reconciliation-system`

关键升级主题：

1. 保证金账户从“多个账户并行”演进到“总保证金账户 + 规则明细 + 历史结转映射”
2. 钱包能力从“账户视角”演进到“统一台账 + 营销资金协同 + 资金动作中心”
3. 退款从支付核心附属功能演进到独立退款治理中心
4. 对账从方案文档演进到独立对账系统

## 4. 当前系统分层判定

| 系统 | 当前阶段 | 当前判断 | 下一阶段重点 |
| --- | --- | --- | --- |
| `payment-core` | `Phase A` | 最成熟，但仍缺冻结证据收口 | 冻结截图、回归归档、正式候选说明 |
| `clearing-system` | `Phase A` | 主链路已打通 | 冻结证据、批次治理、真实库与 MQ 稳定化 |
| `settlement-system` | `Phase A` | 已有结算与出款骨架 | 冻结证据、回单回写、失败补偿正式化 |
| `accounting-system` | `Phase A` | 已具备联动基线 | 冻结证据、审计与幂等正式化 |
| `ops-config-system` | `Phase B` | 已具备配置变更申请、审批、灰度窗口和发布留痕基线 | 配置快照版本、下游刷新通知与真实权限审计 |
| `risk-control-system` | `Phase B` | 风控治理骨架已起 | 跨系统复核、告警、实时决策与压测 |
| `gateway-access` | `Phase B` | 接入治理骨架已起 | 签名验签、证书轮换、灰度发布和真实渠道编排 |
| `deposit-system` | `Phase C` | 已能支撑 V1，但模型还不够未来化 | 总账户模型、迁移方案、统一运营视图 |
| `wallet-account / wallet-system` | `Phase C` | 资金视角仍分裂 | 统一台账、红包营销资金协同、渠道出入金治理 |
| `refund-center` | `Phase C` | 需从支付核心中继续独立化 | 独立退款流程、失败补偿、差错治理 |
| `reconciliation-system` | `Phase C` | 仍处于需要落地的重点系统 | 方案落地、批次作业、差异闭环与业财核验 |

## 5. 自动推进原则

后续自动化开发时，按以下原则推进：

1. 任何新系统开发前，先检查四类资料：`图稿 / 笔记 / 支付相关沉淀 / 专家资料`
2. 任何实现必须同时考虑产品、财务、后端架构、前端和测试五个视角
3. 任何进入 `test` 的能力，都必须伴随文档、接口、数据库、页面和测试记录更新
4. 任何出现“模型升级、账户合并、口径统一、历史迁移、新终端形态”信号的内容，都要直接登记到版本池，不等线上问题暴露后再改

## 6. 近期执行顺序

### 6.1 第一优先级

1. 继续把 `payment-core` 冻结候选包补完整
2. 重新评估 `test -> master`

### 6.2 第二优先级

1. 把 `Phase B` 治理层补成可联调、可截图、可文档化的正式治理系统
2. 形成与支付主链路之间的跨系统证据

### 6.3 第三优先级

1. 进入 `Phase C` 的资金域架构升级
2. 逐步把保证金、钱包、退款、对账做成真实业务中台能力

## 7. 版本演进约束

1. `V1` 关注“最小稳定闭环”
2. `V1.1` 关注“冻结补齐与治理增强”
3. `V2` 关注“模型升级、结构升级、跨系统协同升级”
4. 只有完成冻结证据、人工回归和发布说明，才允许把某一阶段视为“可发版”
